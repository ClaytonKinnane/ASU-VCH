# База данных

> **Классификация:** `TARGET ARCHITECTURE`.
>
> Документ описывает целевую модель и исторические исходные решения. Он не является перечнем уже существующих таблиц. Текущее физическое состояние определяют [DATABASE-CURRENT.md](DATABASE-CURRENT.md), executable migrations, installer и профильные checker'ы.

## 1. Назначение документа

Документ определяет архитектуру базы данных АСУ-ВЧ и является источником требований для:

- ER-диаграмм;
- миграций и сидеров;
- репозиториев и сервисов;
- проверок целостности;
- тестов модели данных.

Изменения схемы сначала согласуются в документации и ADR, затем реализуются миграциями.

Отдельные разделы ниже отражают первоначальную target architecture и могут быть шире текущего runtime. Факт реализации подтверждается только current-state sources и Test Evidence.

## 2. Технологическая база

- СУБД: MySQL 8.4.
- Кодировка: `utf8mb4`.
- Изменение структуры выполняется только контролируемыми миграциями.
- Учетные данные подключения не хранятся в репозитории.
- MySQL `ENUM` в проекте не используется.

## 3. Цели модели данных

Модель должна обеспечивать:

- целостность и непротиворечивость данных;
- расширяемость без разрушения существующих модулей;
- минимизацию дублирования;
- аудит критических действий;
- безопасное разграничение доступа;
- хранение истории отдельно от текущего состояния.

## 4. Общие правила проектирования

### 4.1 Нормализация

- Минимальный уровень — третья нормальная форма.
- Денормализация допускается только при наличии измеримой необходимости и отдельного архитектурного обоснования.
- Один факт хранится в одном месте.
- Одна таблица описывает одну доменную сущность или одну явно определенную связь.

### 4.2 Первичные ключи

Для основных сущностей используется:

```sql
id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
```

Внутренний идентификатор:

- не несет бизнес-смысла;
- не отображается пользователю как предметный номер;
- не изменяется в течение жизни записи.

### 4.3 Общие временные поля

Для изменяемых сущностей применяются:

```text
created_at
updated_at
deleted_at
```

`deleted_at` допускается не во всех таблицах. Временные и инфраструктурные данные могут удаляться физически.

### 4.4 Soft delete

Soft delete обязателен для:

```text
users
soldiers
military_units
departments
positions
roles
reference_groups
reference_values
soldier_identifiers
```

Физическое удаление допускается для:

```text
sessions
tokens
cache
временных технических данных
```

Журнал аудита и записи истории физически не удаляются штатными средствами приложения.

### 4.5 Текущее состояние и история

Основные таблицы хранят актуальное состояние. Исторические изменения хранятся в отдельных таблицах.

Пример:

```text
soldiers.position_id               — текущая должность
soldier_position_assignments       — история назначений
```

Тот же принцип применяется к подразделениям, званиям, ролям, идентификаторам и будущим предметным модулям.

### 4.6 Транзакции

Операции, изменяющие несколько связанных сущностей, выполняются в одной транзакции.

К ним относятся, в частности:

- первая регистрация и назначение владельца системы;
- передача роли владельца;
- назначение и отзыв ролей;
- кадровые назначения;
- изменение идентификаторов военнослужащего;
- операции, формирующие запись аудита вместе с предметными изменениями.

## 6. Модель доступа RBAC

### 6.1 Общие принципы

- Пользователь и военнослужащий являются разными сущностями.
- Роли назначаются пользователям через `user_roles`.
- Разрешения назначаются ролям через `role_permissions`.
- Прямые разрешения пользователям не выдаются.
- В `users` отсутствуют поля роли, администратора и владельца.
- Должность военнослужащего не является ролью доступа.

### 6.2 Таблица `users`

```text
users
├── id
├── soldier_id
├── username
├── email
├── password_hash
├── status_id
├── last_login_at
├── password_changed_at
├── created_at
├── updated_at
└── deleted_at
```

Правила:

- `soldier_id` — nullable FK на `soldiers.id`;
- `username` обязателен и уникален;
- `email` nullable и уникален при наличии;
- хранится только хеш пароля;
- один военнослужащий связан не более чем с одной учетной записью;
- системные пользователи могут существовать без карточки военнослужащего;
- удаление военнослужащего не удаляет учетную запись автоматически;
- владелец системы не может быть удален до передачи роли.

Для связи один-к-одному применяется:

```sql
UNIQUE (soldier_id)
```

### 6.3 Таблица `roles`

```text
roles
├── id
├── code
├── name
├── description
├── is_system
├── created_at
├── updated_at
└── deleted_at
```

Правила:

- `code` обязателен, уникален и используется в авторизации;
- системные роли создаются миграцией или обязательным сидером;
- системную роль нельзя переименовать или удалить штатными средствами;
- числовой `id` роли не используется как магическое значение в коде.

### 6.4 Роль `system_owner`

Владелец системы представлен специальной системной ролью:

```text
roles.code = system_owner
roles.is_system = true
```

Правила:

- первый зарегистрированный пользователь автоматически получает роль;
- в системе существует ровно один активный владелец;
- назначение первого владельца выполняется в одной транзакции;
- защита от гонки обеспечивается не только сервисной логикой, но и механизмами БД;
- передача роли выполняется атомарно;
- активный владелец не может быть удален, заблокирован или лишен роли без успешной передачи полномочий.

Активная роль `system_owner` дает абсолютный доступ на уровне авторизации без перечисления каждого разрешения.

Она не отменяет:

- валидацию;
- ограничения базы данных;
- CSRF-защиту;
- подтверждение опасных операций;
- аудит;
- транзакционные правила.

### 6.5 Таблица `permissions`

```text
permissions
├── id
├── code
├── name
├── description
├── module
├── is_system
├── created_at
└── updated_at
```

Правила:

- разрешения не удаляются после начала использования;
- `code` уникален и неизменяем;
- рекомендуемый формат:

```text
module.resource.action
```

Примеры:

```text
users.view
users.create
users.update
users.block
roles.assign
audit.view
```

### 6.6 Таблица `user_roles`

```text
user_roles
├── id
├── user_id
├── role_id
├── assigned_by
├── assigned_at
└── revoked_at
```

Правила:

- связь многие-ко-многим;
- назначение не удаляется физически;
- активность определяется отсутствием `revoked_at`;
- `assigned_by` nullable только для системного назначения первого владельца;
- все назначения и отзывы ролей журналируются;
- повторное активное назначение одной роли одному пользователю запрещено;
- одновременно допускается только одна активная связь с ролью `system_owner`.

Точный DB-механизм обеспечения единственного владельца определяется при проектировании миграций и фиксируется отдельным ADR или разделом ERD.

### 6.7 Таблица `role_permissions`

```text
role_permissions
├── role_id
├── permission_id
├── granted_at
└── granted_by
```

Первичный ключ:

```sql
PRIMARY KEY (role_id, permission_id)
```

Суррогатный `id` для этой таблицы не используется.

## 7. Универсальные справочники

### 7.1 Принцип

Небольшие классификаторы, содержащие только код, название, описание и порядок, реализуются через универсальные справочники.

Сущность с собственной бизнес-логикой, дополнительными атрибутами, связями или историей получает отдельную таблицу.

### 7.2 Таблица `reference_groups`

```text
reference_groups
├── id
├── code
├── name
├── description
├── is_system
├── created_at
├── updated_at
└── deleted_at
```

### 7.3 Таблица `reference_values`

```text
reference_values
├── id
├── group_id
├── code
├── name
├── description
├── sort_order
├── is_system
├── created_at
├── updated_at
└── deleted_at
```

Ограничение уникальности:

```sql
UNIQUE (group_id, code)
```

Примеры групп:

```text
user_status
department_status
military_unit_status
position_status
service_status
department_type
rank_category
```

Предметные таблицы ссылаются на `reference_values.id` через явно названные поля, например `status_id`, `type_id`, `category_id`.

Сервисный слой обязан проверять, что выбранное значение относится к требуемой группе.

## 8. Воинские части

### 8.1 Таблица `military_units`

```text
military_units
├── id
├── code
├── name
├── short_name
├── official_number
├── parent_unit_id
├── status_id
├── created_at
├── updated_at
└── deleted_at
```

Правила:

- `code` обязателен и уникален среди действующих записей;
- `official_number` nullable;
- `parent_unit_id` — nullable FK на `military_units.id`;
- часть не может быть родителем самой себя;
- циклическая иерархия запрещена;
- архивная часть недоступна для новых назначений;
- даже однопользовательская установка работает через эту сущность, без жестко заданной части.

## 9. Подразделения

### 9.1 Таблица `departments`

```text
departments
├── id
├── military_unit_id
├── parent_department_id
├── code
├── name
├── short_name
├── type_id
├── status_id
├── sort_order
├── created_at
├── updated_at
└── deleted_at
```

Правила:

- подразделение принадлежит одной воинской части;
- `parent_department_id` nullable для верхнего уровня;
- родитель и дочернее подразделение принадлежат одной части;
- циклы запрещены;
- код уникален в пределах части;
- `sort_order` влияет только на отображение.

Ограничение:

```sql
UNIQUE (military_unit_id, code)
```

## 10. Воинские звания

### 10.1 Таблица `ranks`

```text
ranks
├── id
├── code
├── name
├── short_name
├── category_id
├── level
├── sort_order
├── is_system
├── created_at
└── updated_at
```

Правила:

- `code` уникален и неизменяем;
- категория хранится в универсальном справочнике;
- `level` отражает относительный уровень звания;
- `sort_order` используется для отображения;
- использованное звание не удаляется физически;
- системные записи создаются сидером;
- изменение порядка и уровня журналируется.

## 11. Штатные должности

### 11.1 Таблица `positions`

В первой версии каждая запись представляет конкретную штатную позицию в конкретной части или подразделении.

```text
positions
├── id
├── military_unit_id
├── department_id
├── code
├── name
├── short_name
├── required_rank_id
├── parent_position_id
├── is_command
├── status_id
├── created_at
├── updated_at
└── deleted_at
```

Правила:

- должность принадлежит воинской части;
- `department_id` nullable для должностей уровня части;
- подразделение и должность должны принадлежать одной части;
- `required_rank_id` nullable;
- иерархия должностей не должна содержать циклы;
- `is_command` не предоставляет права в информационной системе;
- одна штатная позиция может быть вакантной;
- одновременное занятие одной позиции несколькими военнослужащими запрещено, если позже не будет отдельно введено совместительство.

Ключевое разграничение:

```text
position != role
```

## 12. Военнослужащие

### 12.1 Таблица `soldiers`

```text
soldiers
├── id
├── military_unit_id
├── department_id
├── position_id
├── rank_id
├── last_name
├── first_name
├── middle_name
├── birth_date
├── service_status_id
├── service_start_date
├── service_end_date
├── created_at
├── updated_at
└── deleted_at
```

Правила:

- учетные данные аутентификации здесь не хранятся;
- ФИО не используется как уникальный идентификатор;
- `birth_date` хранится без времени;
- действующий военнослужащий обязан быть связан с частью;
- подразделение, должность и военнослужащий должны относиться к одной части;
- увольнение или исключение из списков не удаляет карточку;
- кадровые изменения подлежат аудиту.

Поля `department_id`, `position_id` и `rank_id` отражают текущее состояние. История будет храниться в отдельных таблицах:

```text
soldier_department_assignments
soldier_position_assignments
soldier_rank_history
```

Они проектируются отдельной итерацией.

## 13. Идентификаторы военнослужащего

### 13.1 Решение

Личный номер не хранится отдельным полем в `soldiers`.

Для всех предметных идентификаторов применяется расширяемая модель:

```text
identifier_types
soldier_identifiers
```

Это позволяет хранить личный номер, номер жетона, военного билета, пропуска и идентификаторы внешних систем без изменения таблицы `soldiers`.

### 13.2 Таблица `identifier_types`

```text
identifier_types
├── id
├── code
├── name
├── description
├── validation_pattern
├── allow_duplicates
├── allow_history
├── is_primary_allowed
├── is_system
├── created_at
└── updated_at
```

Правила:

- `code` уникален и неизменяем;
- системные типы создаются сидером;
- тип не удаляется после использования;
- правила уникальности и истории могут различаться по типам.

Примеры кодов:

```text
personnel_number
service_card
dog_tag
military_id
hr_id
access_card
```

### 13.3 Таблица `soldier_identifiers`

```text
soldier_identifiers
├── id
├── soldier_id
├── identifier_type_id
├── value
├── is_primary
├── valid_from
├── valid_to
├── created_at
├── updated_at
└── deleted_at
```

Правила:

- военнослужащий может иметь несколько идентификаторов;
- история изменения сохраняется через `valid_from` и `valid_to`;
- активным считается идентификатор без `valid_to` и без `deleted_at`;
- допускается не более одного активного основного идентификатора каждого типа у одного военнослужащего;
- уникальность значения определяется политикой типа;
- все изменения журналируются;
- конкретные индексы и механизм условной уникальности определяются на этапе миграций с учетом возможностей MySQL 8.4.

## 14. Согласованность организационных связей

Система обязана предотвращать состояния, при которых:

- военнослужащий относится к одной части, а его подразделение — к другой;
- должность относится к другой части;
- должность относится к несовместимому подразделению;
- дочернее подразделение находится в другой части;
- иерархии подразделений, частей или должностей содержат циклы.

Контроль распределяется между:

- внешними ключами и уникальными индексами;
- `CHECK`-ограничениями, где они достаточны;
- транзакционным сервисным слоем;
- интеграционными тестами целостности.

Контроллеры не реализуют эти бизнес-правила.

## 15. Аудит

### 15.1 Таблица `audit_log`

```text
audit_log
├── id
├── occurred_at
├── actor_user_id
├── action
├── entity_type
├── entity_id
├── result
├── old_values
├── new_values
├── metadata
├── ip_address
└── user_agent
```

Рекомендуемые типы JSON:

```text
old_values
new_values
metadata
```

Правила:

- запись аудита неизменяема штатными средствами приложения;
- отсутствие авторизованного пользователя допускается для системных операций;
- чувствительные данные, пароли, токены и секреты в аудит не записываются;
- все даты фиксируются единообразно;
- идентификатор сущности хранится отдельно от ее типа;
- ошибки критических операций также журналируются, если это не нарушает атомарность и безопасность транзакции.

Обязательному аудиту подлежат:

- входы и неуспешные попытки входа;
- изменение пароля и статуса учетной записи;
- назначение и отзыв ролей;
- передача роли `system_owner`;
- изменение ролей и разрешений;
- создание, изменение, архивирование кадровых сущностей;
- изменение идентификаторов;
- изменение системных справочников;
- просмотр особо чувствительных данных, если это будет предусмотрено политикой доступа.

Политика хранения, экспорта и ограничения доступа к журналу уточняется в спецификации домена Audit.

## 16. Индексы

Минимальный набор индексов должен покрывать:

- все внешние ключи;
- уникальные машинные коды;
- поля активного состояния и soft delete, используемые в частых запросах;
- поиск пользователей по `username` и `email`;
- поиск военнослужащих по ФИО;
- поиск идентификаторов по типу и значению;
- выборку аудита по времени, пользователю, действию и сущности.

Индексы создаются только под подтвержденные сценарии запросов. Избыточное индексирование не допускается.

## 17. Запрещенные решения

Не допускается:

- использование MySQL `ENUM`;
- хранение роли непосредственно в `users`;
- поля `is_admin` или `is_system_owner` в `users`;
- прямое назначение разрешений пользователям;
- использование числовых идентификаторов как магических констант;
- хранение личного номера непосредственно в `soldiers`;
- физическое удаление аудита и кадровой истории;
- изменение схемы вручную вне миграций;
- дублирование бизнес-данных между таблицами без ADR.

## 18. Утвержденные решения

1. `users` и `soldiers` разделены.
2. `users.soldier_id` nullable и уникален при наличии.
3. Авторизация строится на RBAC.
4. Прямые пользовательские разрешения отсутствуют.
5. Первый пользователь получает роль `system_owner`.
6. В `users` отсутствует флаг владельца.
7. Активный владелец системы всегда один.
8. История назначения ролей сохраняется.
9. `system_owner` имеет специальную семантику абсолютного доступа.
10. Должность и роль доступа независимы.
11. Классификаторы реализуются через Reference Data или отдельные специализированные справочники.
12. MySQL `ENUM` не используется.
13. Личный номер и другие идентификаторы хранятся в `soldier_identifiers`.
14. Текущее состояние отделено от истории.
15. Кадровые сущности используют soft delete.
16. Критические операции журналируются.
17. Все изменения схемы выполняются миграциями.

## 19. Историческая последовательность первоначального проектирования

При первоначальном утверждении этого target-документа планировалась следующая последовательность:

1. архитектурное ревью;
2. создание ERD;
3. фиксация точных типов столбцов, внешних ключей, индексов и ограничений;
4. спецификация домена Security;
5. проектирование migrations;
6. реализация только после отдельного одобрения.

Эта последовательность является historical planning context, а не текущим project plan. Последующие documentation-first инкременты уже реализовали часть Security, специализированных Reference-каталогов и Organization Structure v1. Актуальные реализованные границы и оставшийся scope определяются `PROJECT-STATUS.md`, `DATABASE-CURRENT.md`, living indexes и отдельными утверждёнными increment documents.
