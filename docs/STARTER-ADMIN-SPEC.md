# Минимальная стартовая версия: база данных и панель администратора

> **Классификация:** `HISTORICAL IMPLEMENTED SPECIFICATION`.
>
> Increment: `feature/initial-site`. Functional PR: `#1`, merged.
>
> Документ сохраняет исходные требования стартовой версии и не является текущим implementation plan. Актуальное состояние определяется [PROJECT-STATUS.md](PROJECT-STATUS.md), [DATABASE-CURRENT.md](DATABASE-CURRENT.md), executable migrations и профильными Test Report.

## 1. Статус документа

- Этап: Specification
- Ветка: `feature/initial-site` — historical increment branch
- Результат: реализовано и объединено функциональным PR #1
- Назначение на момент создания: завершить минимальную стартовую версию сайта до продолжения проектирования бизнес-доменов.

## 2. Цель

Реализовать минимальный сквозной сценарий:

1. локальная база данных MySQL;
2. первичная регистрация владельца системы при пустой базе;
3. автоматическое назначение абсолютных прав первому пользователю;
4. автоматическое отключение публичной регистрации после создания первого пользователя;
5. вход существующего пользователя;
6. защищенная сессия;
7. переход в панель администратора;
8. отображение стартовых блоков настройки и управления;
9. выход из системы;
10. локальная проверка в Open Server Panel.

Решение должно учитывать уже утвержденные архитектурные правила Security, Reference, Audit, Organization и общие архитектурные паттерны, но не обязано реализовывать все замороженные домены в полном объеме.

## 3. Границы стартовой версии

### Входит

- подключение PHP-приложения к MySQL через PDO;
- минимальная миграция Security;
- таблицы `users`, `roles`, `permissions`, `user_roles`, `role_permissions`;
- системная роль `system_owner`;
- разрешение `system.*.*`, обозначающее полный доступ владельца системы;
- bootstrap-регистрация первого пользователя только при пустой таблице `users`;
- автоматическое назначение первому пользователю роли `system_owner`;
- автоматическое отключение регистрации после успешного создания первого пользователя;
- временный локальный пользователь `Admin` с паролем `12315` для тестового сценария;
- хранение пароля только как результата `password_hash()`;
- серверная авторизация;
- PHP-сессия;
- CSRF-защита форм регистрации, входа и выхода;
- главная страница панели администратора;
- диагностические блоки панели;
- сценарий установки/обновления минимальной БД;
- обновление сценария локального развертывания;
- инструкция локальной проверки.

### Не входит

- публичная регистрация второго и последующих пользователей;
- восстановление пароля;
- управление пользователями через интерфейс;
- полноценный редактор ролей и разрешений;
- реализация Organization, Documents, Orders и других бизнес-доменов;
- полноценный Audit;
- production-развертывание;
- постоянное использование тестового пароля.

## 4. Bootstrap-регистрация первого пользователя

После чистой установки система должна разрешать регистрацию только при одновременном выполнении условий:

```text
users_count = 0
AND
system_owner_not_assigned = true
```

Первый успешно зарегистрированный пользователь:

- становится владельцем системы;
- получает системную роль `system_owner`;
- получает полный доступ через разрешение `system.*.*`;
- считается главным пользователем установки;
- не может быть создан через обычный публичный регистрационный процесс повторно.

После фиксации пользователя, роли и разрешений в одной транзакции регистрация автоматически отключается.

Состояние регистрации определяется сервером по фактическим данным БД. Клиентская форма не является источником истины.

Повторный запрос к регистрации после создания первого пользователя должен возвращать отказ либо перенаправлять на форму входа.

Создание первого пользователя, назначение роли и отключение bootstrap-режима выполняются атомарно. При любой ошибке транзакция откатывается полностью.

## 5. Временный локальный пользователь

Для стартового тестирования используются учетные данные:

```text
Username: Admin
Password: 12315
Role: system_owner
Access: absolute test access
```

`Admin / 12315` является публично известным **local-only development fixture** текущего baseline, а не production credential или secret конкретной установки. Он существует для воспроизводимого локального bootstrap-сценария, разрешён только при `environment=local` и требует обязательной смены пароля при первом входе.

Этот пользователь создается через тот же bootstrap-механизм, который будет применяться при реальной установке. Допускается автоматизированный CLI-сценарий, имитирующий первичную регистрацию и вызывающий общий прикладной сервис.

Правила:

- имя пользователя при поиске канонизируется в нижний регистр;
- отображаемое имя может оставаться `Admin`;
- пароль никогда не хранится в БД в открытом виде;
- seed идемпотентен только для локального тестового окружения;
- повторный запуск не должен создавать второго владельца системы;
- учетная запись явно помечается как временная;
- известный fixture нельзя повторно использовать для иных учётных записей или окружений;
- перед production-этапом тестовая база пересоздается, либо пользователь удаляется, либо пароль заменяется;
- production-установка не должна автоматически создавать пользователя с известным паролем;
- реальные временные пароли пользователей, instance-specific credentials и содержимое `config/local.php` не публикуются.

Низкая сложность пароля допускается только для изолированной локальной стартовой версии по прямому решению владельца проекта. Возможная замена фиксированного fixture на interactive prompt или безопасную генерацию относится к отдельному будущему Security increment и не считается уже реализованной.

## 6. Минимальная модель данных

### `users`

- `id BIGINT UNSIGNED AUTO_INCREMENT`
- `username VARCHAR(100)`
- `username_canonical VARCHAR(100)`
- `email VARCHAR(255) NULL`
- `email_canonical VARCHAR(255) NULL`
- `password_hash VARCHAR(255)`
- `display_name VARCHAR(150)`
- `is_active BOOLEAN`
- `is_temporary BOOLEAN`
- `must_change_password BOOLEAN`
- `last_login_at DATETIME NULL`
- `created_at DATETIME`
- `updated_at DATETIME`
- `deleted_at DATETIME NULL`

Ограничения:

- уникальный `username_canonical` без повторного использования после soft delete;
- уникальный nullable `email_canonical` без повторного использования после soft delete;
- bootstrap-регистрация доступна только при отсутствии пользователей;
- обычная публичная регистрация после создания первого пользователя отсутствует.

### `roles`

- `id BIGINT UNSIGNED AUTO_INCREMENT`
- `code VARCHAR(100)`
- `name VARCHAR(150)`
- `description VARCHAR(500) NULL`
- `is_system BOOLEAN`
- `created_at DATETIME`
- `updated_at DATETIME`

### `permissions`

- `id BIGINT UNSIGNED AUTO_INCREMENT`
- `code VARCHAR(150)`
- `name VARCHAR(150)`
- `description VARCHAR(500) NULL`
- `is_system BOOLEAN`
- `created_at DATETIME`
- `updated_at DATETIME`

### `user_roles`

- `user_id BIGINT UNSIGNED`
- `role_id BIGINT UNSIGNED`
- `assigned_at DATETIME`

### `role_permissions`

- `role_id BIGINT UNSIGNED`
- `permission_id BIGINT UNSIGNED`
- `assigned_at DATETIME`

Все внешние ключи используют `ON DELETE RESTRICT ON UPDATE RESTRICT`.

## 7. Конфигурация

Непубличная конфигурация приложения располагается вне `public`.

Целевая структура развертывания:

```text
C:\OSPanel\home\asu-vch.local\
├── app\
├── config\
├── database\
├── storage\
└── public\
```

Локальные параметры БД читаются из файла:

```text
config/local.php
```

Файл с реальными локальными учетными данными не коммитится. В репозитории хранится `config/local.example.php`.

Рекомендуемая локальная БД:

```text
Database: asu_vch
Host: 127.0.0.1
Port: 3306
Charset: utf8mb4
```

## 8. Авторизация и регистрация

Маршруты стартовой версии:

```text
GET  /                  форма первичной регистрации либо входа
POST /register.php      bootstrap-регистрация первого пользователя
POST /login.php         вход
GET  /admin/            панель администратора
POST /logout.php        выход
GET  /health.php        техническая проверка приложения и БД
```

Правила:

- при отсутствии пользователей главная страница показывает первичную регистрацию;
- после создания первого пользователя вкладка и маршрут регистрации отключаются;
- сервер повторно проверяет отсутствие пользователей непосредственно внутри транзакции;
- конкурентные попытки первичной регистрации не должны создавать нескольких владельцев;
- при успешном входе выполняется `session_regenerate_id(true)`;
- неактивный или soft-deleted пользователь войти не может;
- пароль проверяется через `password_verify()`;
- запросы выполняются подготовленными выражениями PDO;
- при выходе сессия уничтожается;
- административная страница недоступна без аутентификации и роли `system_owner`;
- сообщения об ошибке входа не раскрывают, существует ли пользователь.

## 9. Главная страница панели администратора

Панель должна сохранить визуальный язык темы `asu-blue`.

Главная страница панели не должна одновременно показывать все будущие функции отдельными плитками. Она служит верхним уровнем навигации и содержит крупные плитки общих разделов. Вложенные функции отображаются на отдельных страницах соответствующих разделов.

### 9.1. Верхняя служебная область

На главной странице отображаются:

- имя и username текущего пользователя;
- роль и признак главного владельца системы;
- предупреждение о временной тестовой учетной записи;
- краткое состояние приложения и подключения к БД;
- кнопка выхода.

Служебная информация должна быть компактной и не конкурировать с основными навигационными плитками.

### 9.2. Плитки общих разделов

#### **Контент**

Раздел объединяет прикладные и предметные модули системы.

Будущие вложенные плитки:

- Справочники;
- Организационная структура;
- Военнослужащие;
- Документы;
- Приказы;
- Медицинский учет;
- Имущество и оборудование;
- Транспорт;
- Аудит и журнал событий.

В стартовой версии плитка раздела доступна для перехода на страницу-заглушку, а вложенные модули явно помечаются «В разработке».

#### **Пользователи**

Раздел объединяет управление безопасностью и доступом.

Будущие вложенные плитки:

- Пользователи системы;
- Роли;
- Разрешения;
- Назначение ролей;
- Матрица доступа;
- Состояние первичной регистрации;
- Сеансы и безопасность учетных записей.

На странице раздела стартовой версии отображаются реальные счетчики пользователей, ролей и разрешений. Изменение данных через интерфейс пока не реализуется.

#### **Настройки системы**

Раздел объединяет параметры самого приложения и его инфраструктуры.

Будущие вложенные плитки:

- Общие параметры системы;
- Темы оформления;
- Параметры окружения;
- База данных;
- Миграции;
- Диагностика;
- Обслуживание системы;
- Резервное копирование и восстановление;
- Журналы приложения.

На странице раздела стартовой версии отображаются реальные диагностические сведения:

- версия PHP;
- состояние MySQL;
- имя БД;
- серверное время;
- версия приложения;
- режим окружения;
- активная тема;
- часовой пояс;
- состояние debug;
- количество примененных миграций;
- дата последней миграции.

### 9.3. Правила навигации

- главная страница содержит только плитки верхнего уровня;
- каждая плитка ведет на страницу соответствующего общего раздела;
- вложенные страницы используют тот же визуальный язык и предоставляют кнопку возврата в панель;
- неготовые функции не имитируют работающий интерфейс;
- недоступные действия отключаются или получают явную отметку «В разработке»;
- структура должна позволять добавлять новые общие разделы без перестройки существующих страниц;
- доступность плиток в будущем определяется RBAC, а не жестко заданным списком в шаблоне.

## 10. Миграции и bootstrap

Сценарий:

```text
database/install.php
```

должен:

1. создать БД при наличии соответствующих полномочий либо подключиться к существующей;
2. создать таблицу `migrations`;
3. применить минимальную миграцию;
4. создать системную роль `system_owner` и разрешение `system.*.*`;
5. не создавать production-пользователя автоматически;
6. сообщить, доступна ли первичная регистрация;
7. в локальном тестовом режиме создать `Admin / 12315` через общий bootstrap-сервис;
8. вывести проверяемый итог без раскрытия password hash;
9. завершаться ненулевым кодом при ошибке.

Установка запускается только из CLI.

Production-режим оставляет систему без пользователей и ожидает первичную регистрацию через защищенный bootstrap-маршрут.

## 11. Локальное развертывание

`deploy/Deploy-Local.ps1` дополнительно копирует:

```text
app\      -> C:\OSPanel\home\asu-vch.local\app
config\   -> C:\OSPanel\home\asu-vch.local\config
database\ -> C:\OSPanel\home\asu-vch.local\database
```

Локальный `config/local.php` должен сохраняться при повторном развертывании либо автоматически создаваться из example-файла только при отсутствии.

Сценарий не должен копировать локальные секреты обратно в репозиторий.

## 12. Проверка

Минимальная приемка:

1. миграция выполняется без ошибок;
2. повторная миграция идемпотентна;
3. чистая БД показывает первичную регистрацию;
4. первый пользователь получает роль `system_owner` и абсолютное разрешение;
5. после создания первого пользователя регистрация исчезает;
6. прямой повторный запрос к `/register.php` отклоняется;
7. конкурентный повторный bootstrap не создает второго владельца;
8. `/health.php` сообщает успешное подключение к БД;
9. неверный пароль отклоняется;
10. локальный `Admin / 12315` выполняет вход;
11. после входа открывается `/admin/`;
12. анонимный запрос к `/admin/` перенаправляется на `/`;
13. главная страница панели показывает плитки `Контент`, `Пользователи` и `Настройки системы`;
14. страницы общих разделов открываются и сохраняют единый визуальный язык;
15. раздел `Пользователи` показывает реальные счетчики БД;
16. раздел `Настройки системы` показывает реальные диагностические сведения и состояние миграций;
17. интерфейс показывает, что первичная регистрация отключена;
18. выход уничтожает сессию;
19. после выхода `/admin/` снова недоступен;
20. в репозитории отсутствует открытый password hash и локальный конфигурационный файл;
21. PHP-файлы проходят `php -l`.

## 13. Ограничение проверки

GitHub является источником истины, однако фактическая проверка в `C:\OSPanel` должна выполняться на локальной машине владельца проекта после `git pull` и развертывания. Результат локального прогона фиксируется отдельно до признания стартовой версии завершенной.

## 14. Критерий завершения

Стартовая версия считается завершенной только после:

```text
Specification approved
Implementation completed
Static checks passed
Local Open Server test passed
Bootstrap registration verified
Registration auto-disable verified
Test credentials verified
Documentation updated
Commit and push completed
```

Исторически этот критерий был выполнен в рамках functional PR #1 и последующих Security increments. Current project plan определяется living documentation, а не последней строкой этой исходной Specification.

После завершения стартовой версии проект вернулся к доменной работе. Упоминание ранее отложенного домена Orders сохраняется как historical planning context и не означает, что Orders является текущим активным инкрементом.
