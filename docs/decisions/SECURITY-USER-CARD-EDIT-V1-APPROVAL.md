# Approval — Security / User Card & Edit v1

Дата утверждения: **2026-07-25**  
Статус: **Approved**  
Дизайн: `docs/design/SECURITY-USER-CARD-EDIT-V1-DESIGN.md`  
Review: `docs/design/SECURITY-USER-CARD-EDIT-V1-REVIEW.md`

## 1. Решение

Дизайн компактного списка, карточки и редактирования пользователя утвержден для реализации.

## 2. Утвержденные границы

Реализуются:

- таблица пользователей из четырех колонок;
- переход в карточку по отображаемому имени;
- полная административная карточка для `system_owner` и `administrator`;
- ограниченная карточка для остальных пользователей с `security.users.view`;
- изменение логина, отображаемого имени, email и флагов учетной записи;
- назначение и снятие разрешенных ролей;
- блокировка и разблокировка подтвержденной учетной записи;
- подтверждение пользователя из карточки;
- desktop/mobile-представление.

Не реализуются в этом инкременте:

- сброс пароля;
- обязательная смена пароля после входа;
- архивирование и восстановление;
- отклонение ожидающей учетной записи;
- история изменений.

## 3. Разрешения

- просмотр карточки: `security.users.view`;
- изменение основных данных: `security.users.update`;
- изменение ролей: `security.users.assign_roles`;
- блокировка и разблокировка: `security.users.block`;
- подтверждение ожидающей учетной записи: `security.users.update`.

## 4. Защита system_owner

Утверждено:

1. Только действующий владелец может назначать или снимать `system_owner`.
2. Невладелец не может обойти ограничение прямым POST-запросом.
3. Невладелец не может снять существующую роль владельца при сохранении других ролей.
4. Последнего активного подтвержденного владельца нельзя лишить роли.
5. Последнего активного подтвержденного владельца нельзя заблокировать.

## 5. Видимость данных

Полные email, последний вход и аудит доступны только пользователям с активной ролью `system_owner` или `administrator`.

Для ограниченного просмотра доступны:

- отображаемое имя;
- логин;
- основной статус;
- роли.

Чувствительные значения не должны попадать в HTML и возвращаемый результат репозитория.

## 6. Разрешение на реализацию

Разрешено создать и изменить файлы, перечисленные в разделе 10 дизайна. Новая миграция не требуется.

После реализации обязательны локальные автоматизированные проверки, ручная desktop/mobile-проверка, отдельный commit/push и актуализация pull request до перехода к следующему инкременту.
