# Security / Migration 003 — User Approval and Audit Metadata Design

Статус: **Draft for review**  
Домен: **Security**  
Связанный дизайн: `docs/design/SECURITY-USER-CREATE-V1-DESIGN.md`  
Уточнение: `docs/design/SECURITY-USER-CREATE-V1-AUDIT-METADATA-ADDENDUM.md`

## 1. Назначение

Миграция `003_security_user_approval.sql` расширяет таблицу `users`, чтобы система могла:

- создавать учетные записи в состоянии ожидания подтверждения;
- отличать ожидание подтверждения от блокировки;
- хранить автора создания учетной записи;
- хранить основание добавления учетной записи;
- хранить администратора, подтвердившего учетную запись;
- хранить время подтверждения;
- сохранить совместимость с существующим владельцем и историческими данными.

Миграция не создает пользовательский интерфейс и не реализует операции создания или подтверждения. Она только подготавливает модель данных.

## 2. Имя и порядок

```text
database/migrations/003_security_user_approval.sql
```

Миграция выполняется после:

```text
001_starter_security.sql
002_security_users_management.sql
```

Существующий migration runner автоматически обнаруживает файл по числовому префиксу и записывает его в `schema_migrations` после успешного выполнения.

## 3. Изменения таблицы users

Добавляются поля:

```sql
created_by BIGINT UNSIGNED NULL
creation_reason VARCHAR(500) NULL
approval_status VARCHAR(20) NOT NULL DEFAULT 'approved'
approved_by BIGINT UNSIGNED NULL
approved_at DATETIME NULL
```

Предлагаемый порядок колонок:

```text
...
last_login_at
created_by
creation_reason
approval_status
approved_by
approved_at
created_at
updated_at
deleted_at
```

Физический порядок колонок не является частью бизнес-контракта, но такой порядок облегчает чтение схемы.

## 4. Семантика полей

### 4.1 created_by

ID пользователя, выполнившего создание учетной записи.

```text
NULL
```

допускается для:

- первого владельца, созданного bootstrap-механизмом;
- учетных записей, существовавших до миграции;
- будущих системных операций без пользовательского контекста.

### 4.2 creation_reason

Текстовое основание добавления учетной записи.

Ограничения приложения для новых записей административного интерфейса:

```text
10–500 символов
```

На уровне БД поле остается nullable для обратной совместимости. Пустая строка приложением не сохраняется.

### 4.3 approval_status

Состояние административного подтверждения:

```text
pending
approved
rejected
```

Значение по умолчанию `approved` необходимо только для совместимости старых путей установки и существующих записей. Новый `UserCreateService` обязан явно записывать `pending`.

### 4.4 approved_by

ID пользователя, подтвердившего учетную запись.

Создатель и подтверждающий могут быть одним пользователем.

### 4.5 approved_at

Серверное время подтверждения.

Для ожидающих и отклоненных учетных записей остается `NULL`.

## 5. Внешние ключи

Добавляются самоссылочные внешние ключи:

```sql
FOREIGN KEY (created_by)
    REFERENCES users(id)
    ON UPDATE RESTRICT
    ON DELETE SET NULL

FOREIGN KEY (approved_by)
    REFERENCES users(id)
    ON UPDATE RESTRICT
    ON DELETE SET NULL
```

`ON DELETE SET NULL` сохраняет историческую запись даже при архивировании или будущем физическом удалении администратора.

Имена ограничений:

```text
fk_users_created_by
fk_users_approved_by
```

## 6. Ограничение approval_status

Для MySQL 8.4 добавляется CHECK:

```sql
CONSTRAINT chk_users_approval_status
CHECK (approval_status IN ('pending', 'approved', 'rejected'))
```

Используется `VARCHAR`, а не `ENUM`, чтобы будущие миграции могли расширять модель состояния без изменения типа колонки.

## 7. Индексы

Добавляются индексы:

```text
idx_users_approval_status (approval_status)
idx_users_created_by (created_by)
idx_users_approved_by (approved_by)
```

Индекс состояния нужен для списка и фильтра ожидающих подтверждения учетных записей.

Индексы внешних ключей указываются явно, даже если MySQL способен создать их автоматически, чтобы схема была предсказуемой.

## 8. Совместимость существующих данных

После добавления колонок все существующие строки должны иметь:

```text
approval_status = approved
created_by = NULL
creation_reason = NULL
approved_by = NULL
approved_at = NULL
```

Существующие значения не изменяются:

- `id`;
- логин;
- email;
- пароль;
- роли;
- `is_active`;
- `last_login_at`;
- временность учетной записи;
- требование смены пароля.

Существующий владелец `Admin` остается активным и может продолжить вход в систему.

## 9. Инварианты после миграции

### Новая ожидающая учетная запись

```text
approval_status = pending
is_active = 0
created_by IS NOT NULL
creation_reason IS NOT NULL
approved_by IS NULL
approved_at IS NULL
```

### Подтвержденная учетная запись

```text
approval_status = approved
is_active = 1
approved_by IS NOT NULL
approved_at IS NOT NULL
```

Для исторических записей разрешено:

```text
approval_status = approved
approved_by IS NULL
approved_at IS NULL
```

поскольку подтверждение произошло до появления механизма аудита либо запись была создана bootstrap-операцией.

### Отклоненная учетная запись

```text
approval_status = rejected
is_active = 0
approved_by IS NULL
approved_at IS NULL
```

Действие отклонения не входит в текущий инкремент, но состояние резервируется схемой.

## 10. Взаимодействие с аутентификацией

Текущий запрос `current_user()` уже требует:

```text
is_active = 1
deleted_at IS NULL
```

Поэтому ожидающий пользователь с `is_active = 0` не сможет получить активную сессию.

При реализации формы входа проверку рекомендуется дополнительно сделать явной:

```text
approval_status = approved
```

Это создаст защиту от случайной рассинхронизации `approval_status` и `is_active`.

Миграция сама код аутентификации не изменяет.

## 11. Взаимодействие со списком пользователей

После реализации приложения запрос списка должен дополнительно возвращать:

```text
approval_status
created_by
creation_reason
approved_by
approved_at
created_at
```

Для списка достаточно отображать:

- статус подтверждения;
- автора создания;
- дату создания.

Полное основание и сведения о подтверждении выводятся в карточке пользователя.

Фильтр состояний должен получить отдельное значение:

```text
pending
```

Условие:

```sql
u.approval_status = 'pending' AND u.deleted_at IS NULL
```

## 12. Транзакционность и DDL

MySQL выполняет `ALTER TABLE` с неявным commit. Migration runner рассматривает файл как одну последовательную миграцию и записывает ее в `schema_migrations` только после успешного выполнения всех выражений.

Файл не должен содержать пользовательские данные или операции создания учетных записей.

При ошибке миграция считается непримененной и требует диагностики схемы перед повторным запуском.

## 13. Повторный запуск

Штатная повторная безопасность обеспечивается таблицей `schema_migrations`: уже примененный файл повторно не выполняется.

Сам SQL не обязан быть напрямую идемпотентным через `IF NOT EXISTS`, поскольку MySQL поддерживает не все комбинации `ADD CONSTRAINT IF NOT EXISTS`, а migration runner является источником истины.

## 14. Проверка структуры

Создается или расширяется CLI-проверка, которая подтверждает:

```text
OK migration 003
OK user approval columns
OK user approval constraints
OK existing owners approved
```

Проверка должна убедиться, что:

- запись миграции существует;
- все пять колонок существуют с ожидаемой nullable-семантикой;
- CHECK содержит три допустимых состояния;
- оба внешних ключа используют `ON DELETE SET NULL`;
- существующий активный владелец имеет `approval_status = 'approved'`;
- нет активных пользователей со статусом `pending` или `rejected`.

## 15. Планируемые файлы реализации

```text
database/migrations/003_security_user_approval.sql
database/check-security-rbac.php
```

`database/install.php` изменять не требуется, если текущий migration runner корректно выполняет произвольное число отсортированных миграций.

Изменения сервисов и UI относятся к следующему implementation-инкременту, а не к реализации самой миграции.

## 16. Проверки миграции

Обязательные проверки:

1. установка на существующую БД с одним владельцем;
2. применение ровно одной новой миграции;
3. повторный запуск — новых миграций нет;
4. существующий `Admin` остается активным;
5. пароль и роли `Admin` не изменяются;
6. все существующие пользователи получают `approved`;
7. `creation_reason` для старых записей остается `NULL`;
8. недопустимый `approval_status` отклоняется БД;
9. удаление связанного автора приводит к `created_by = NULL` без удаления целевой учетной записи;
10. PHP syntax, RBAC check и smoke test проходят.

## 17. Критерии приемки

Миграция принята, если:

- добавлены все пять утвержденных полей;
- добавлены внешние ключи и индексы;
- допустимы только `pending`, `approved`, `rejected`;
- существующие учетные записи совместимы;
- владелец продолжает входить;
- повторный запуск установщика безопасен;
- CLI-проверка подтверждает структуру;
- smoke test проходит.

## 18. Решения для Approval

Предлагается утвердить без изменений:

1. `creation_reason` хранится в `VARCHAR(500) NULL`;
2. обязательность основания для новых административных записей обеспечивается приложением;
3. `approval_status` хранится в `VARCHAR(20)` с CHECK;
4. существующие пользователи получают `approved`;
5. `created_by` и `approved_by` используют `ON DELETE SET NULL`;
6. создатель и подтверждающий могут совпадать;
7. исторические записи могут не иметь автора, основания и подтверждающего;
8. добавляются три индекса;
9. миграция не меняет пароль, роли или активность существующих пользователей;
10. после approval реализуется только миграция и ее CLI-проверка, затем отдельно — сервисы и UI.
