# SECURITY REQUIRED PASSWORD CHANGE V1 — REVIEW

Статус: Reviewed
Дата: 2026-07-25
Ветка: `feature/required-password-change`

## 1. Проверка архитектуры

Подтверждено:

- существующие поля `password_hash`, `is_temporary`, `must_change_password`, `updated_at` достаточны;
- новая миграция не требуется;
- текущий `current_user()` получает `must_change_password` из БД на каждом запросе;
- центральный guard в bootstrap закрывает обход через прямые GET и POST-маршруты;
- страница обязательной смены пароля является исключением guard, а logout остается отдельным разрешенным маршрутом;
- роль `system_owner` не должна обходить обязательную смену;
- сервис отделен от HTTP, HTML и сессии;
- транзакция и `FOR UPDATE` исключают гонку между проверкой и обновлением;
- после успешной смены требуется регенерация ID сессии и CSRF-контекста.

## 2. Проверка безопасности

Подтверждено:

- текущий пароль проверяется через `password_verify`;
- новый пароль хэшируется через `password_hash(PASSWORD_DEFAULT)`;
- новый пароль не может совпадать с текущим;
- парольные значения не возвращаются в HTML и не сохраняются во flash/session state;
- изменяющая операция выполняется только POST с CSRF;
- учетная запись повторно проверяется как active, approved и not deleted внутри транзакции;
- permission guard не выполняется до проверки mandatory password change;
- активная сессия ограничивается при установке флага на следующем запросе.

## 3. Проверка совместимости

- текущая схема БД сохраняется;
- существующие роли и разрешения не меняются;
- login сохраняет обновление `last_login_at`;
- существующий logout совместим;
- текущий UI предупреждений становится недостижим для пользователя с флагом до завершения flow, после чего флаги снимаются;
- smoke-маршруты не изменяют контракт HTTP для неавторизованного пользователя.

## 4. Риски и меры

### Redirect loop

Мера: `require_authenticated_user(true)` используется только на странице смены пароля; пользователь без флага перенаправляется в `/admin/`.

### Обход через POST

Мера: `require_permission()` и `require_system_owner()` сначала вызывают центральный guard.

### Потеря сессии после регенерации

Мера: `user_id` сохраняется в текущей сессии; меняется только ID сессии и CSRF-токен.

### Несогласованное состояние пользователя

Мера: блокировка строки `FOR UPDATE`, повторная проверка статуса и единый UPDATE внутри транзакции.

## 5. Границы

Review подтверждает, что административный reset password, voluntary password change, password history, session revocation, MFA и recovery не входят в инкремент.
