## 2. Архитектурные выводы

### 2.1 Мягкое удаление уже заложено в модели

Поле `deleted_at` присутствует с migration 001, список уже умеет фильтровать архивированные строки, а update, role update и status services уже отклоняют архивированную цель.

Создание отдельной сущности пользователя или физическое удаление не требуется.

### 2.2 Существующие permissions должны быть переиспользованы

Коды:

```text
security.users.archive
security.users.restore
```

уже являются системными и назначены роли `administrator`.

Добавление новых дублирующих permissions признано ошибочным. Число системных permissions остается 19.

### 2.3 `deleted_at` остается источником истины состояния

Текущий archive-state определяется только условием:

```text
deleted_at IS NOT NULL
```

`last_archived_at` хранит audit snapshot последней операции после restore, но не участвует в guards или фильтрах.

Такое разделение устраняет неоднозначность:

- `deleted_at` отвечает на вопрос «сейчас в архиве?»;
- `last_archived_at` отвечает на вопрос «когда выполнено последнее архивирование?».

### 2.4 Restore не должен возвращать активный доступ

Автоматическое восстановление `is_active = 1` признано небезопасным: оно могло бы вернуть доступ без отдельного решения администратора и без проверки актуальности ролей.

Принято:

```text
restore -> deleted_at = NULL, is_active = 0
```

Подтвержденная запись после restore является blocked и требует явного unblock.

### 2.5 Workflow подтверждения сохраняется

Archive/restore не меняют `approval_status`.

Это обеспечивает предсказуемую матрицу:

- pending возвращается pending;
- rejected возвращается rejected;
- approved возвращается approved, но blocked.

Смешивание архива с approve/reject workflow признано недопустимым.

### 2.6 Самоархивирование запрещается сервером

Скрытия кнопки недостаточно. `actorId === userId` проверяется сервисом внутри транзакции.

Это исключает внезапное уничтожение собственной административной сессии и потерю контроля над текущей операцией.

### 2.7 Последний активный владелец защищается под блокировкой

Archive active approved system owner использует ту же системную инварианту, что block и снятие owner-role:

```text
в системе должен остаться минимум один active + approved + nonarchived system_owner
```

Проверка выполняется в той же транзакции с `FOR UPDATE`, чтобы параллельные операции не архивировали двух последних владельцев одновременно.

### 2.8 Идентичность не освобождается

Архивная строка продолжает удерживать уникальные логин и email.

Это предотвращает создание нового субъекта с идентификаторами прежней учетной записи и сохраняет достоверность ссылок аудита.

### 2.9 Архивированная карточка должна быть read-only

Существующие сервисы уже содержат server-side guards, однако UI также не должен предлагать:

- update;
- roles;
- approve/reject;
- block/unblock;
- повторный archive.

Единственное административное изменение архивной записи в v1 — restore.

### 2.10 Текущая сессия цели прекращается без нового session storage

`current_user()` повторно загружает пользователя по условиям active + approved + nonarchived.

После archive следующая страница целевого пользователя не проходит аутентификацию. Отдельное хранение серверных сессий для v1 не требуется.

### 2.11 V1 хранит только последний цикл

Поля в `users` не являются append-only журналом. Повторный archive после restore заменяет данные предыдущего цикла и очищает restore-поля.

Ограничение принято явно. Полная история относится к Security User Change History v1.

### 2.12 Архив исключается из default list

Default-список становится рабочим списком неархивированных пользователей. Архив доступен через явный фильтр.

Плитка `Всего` переименовывается в `Не в архиве`, чтобы значение не вводило пользователя в заблуждение.

## 3. Findings и их состояние

### F-01 — противоречие первоначального набора audit-полей

Первичный draft сначала описывал пять полей, а ниже добавлял `last_archived_at`.

Состояние: **устранено**.

Architecture/Specification полностью консолидирован и содержит один окончательный набор из шести полей.

### F-02 — потеря даты archive после очистки `deleted_at`

Без дополнительного snapshot после restore точное время последнего архивирования было бы недоступно.

Состояние: **устранено**.

Добавлен `last_archived_at`, который не участвует в определении состояния.

### F-03 — риск автоматического возврата доступа

Восстановление прежнего `is_active` могло автоматически вернуть доступ.

Состояние: **устранено**.

Restore всегда устанавливает `is_active = 0`.

### F-04 — конкурирующее архивирование последних владельцев

Проверка count без блокировки допускала race condition.

Состояние: **устранено в архитектуре**.

Требуется блокировка строк действующих владельцев в archive-транзакции.

### F-05 — исторические строки с `deleted_at`, но без нового аудита

После migration возможны архивированные записи без actor/reason.

Состояние: **принято как совместимость**.

UI показывает «Системная или историческая операция» и не выдумывает данные.

### F-06 — несколько archive/restore циклов

Модель полей в `users` не сохраняет полный журнал.

Состояние: **принятое ограничение v1**.

Последний цикл хранится достоверно; append-only history вынесена в следующий инкремент.

### F-07 — разрушительная проверка последнего владельца

Проверка guard на рабочей локальной БД могла временно оставить систему без владельца при сбое теста.

Состояние: **устранено требованиями тестирования**.

Сценарий выполняется только в изолированной БД или после проверенной резервной копии. Основной checker не модифицирует единственного владельца.

## 4. Риски и меры

| Риск | Мера |
|---|---|
| Новый вход архивированного пользователя | `is_active = 0` и `deleted_at IS NOT NULL` |
| Продолжение существующей сессии | повторная загрузка `current_user()` на каждом запросе |
| Автоматический доступ после restore | restore всегда оставляет inactive |
| Самоархивирование администратора | service guard `actorId !== userId` |
| Потеря последнего владельца | locked count active owners |
| Race archive/restore | row lock и повторная проверка состояния |
| Race archive/update/roles/status | существующие сервисы повторно проверяют `deleted_at` под lock |
| Подмена личности через повторное использование логина | UNIQUE значения сохраняются архивной строкой |
| XSS через основание | UTF-8/control validation и экранированный вывод |
| Утечка причины operator/viewer | audit только при `includeSensitive` |
| Выдуманный historical audit | nullable поля и явный historical fallback |
| Потеря нескольких циклов | явное ограничение и будущий append-only history |
| Ошибочная работа default list | explicit `deleted_at IS NULL`, отдельный archive filter |

## 5. Требования к реализации

- Не изменять migrations 001–004.
- Не добавлять новые permissions.
- Не увеличивать expected permission count выше 19.
- Не использовать `last_archived_at` для определения archive-state.
- Не восстанавливать прежнее значение `is_active`.
- Не удалять роли при archive.
- Не освобождать canonical login/email.
- Не логировать основания или PII при исключениях.
- Не доверять скрытию UI; все guards должны быть в сервисе/маршруте.
- Не разрешать update/roles/status/approve/reject архивированной записи.
- Не запускать destructive last-owner test на единственной рабочей БД без backup.
- Использовать POST + CSRF + PRG для обеих операций.
- Сохранять введенное основание в одноразовом session-state только при validation error.
- Очищать form-state после чтения и после успеха.

До PR обязательны:

- RBAC regression с 19 permissions;

- self-archive guard;
- safe last-owner guard;

Мобильная приемка не является gate.

## 7. Решение review

Блокирующих архитектурных findings после консолидации не осталось.

Architecture/Specification допускается к утверждению владельцем проекта.

Review **не разрешает реализацию**. Реализация начинается только после отдельной явной фразы владельца проекта и создания approval-документа.

## 8. Вне объема review

Review не разрешает:

- физическое удаление;
- массовые операции;
- автоматическую активацию после restore;
- освобождение логина/email;
- изменение пароля или ролей во время restore;
- email-уведомления;
- полный журнал нескольких циклов;
- общую user change history;
- мобильную приемку.
