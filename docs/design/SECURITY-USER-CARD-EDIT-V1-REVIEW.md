# Review — Security / User Card & Edit v1

Дата review: **2026-07-25**  
Статус: **Reviewed — no blocking issues**  
Рассматриваемый документ: `docs/design/SECURITY-USER-CARD-EDIT-V1-DESIGN.md`

## 1. Проверенные аспекты

Проверены:

- соответствие основной спецификации Security / Users Management v1;
- совместимость с реализованными User List v1 и User Create/Approval v1;
- отсутствие необходимости новой миграции;
- разграничение разрешений просмотра и изменения;
- серверная защита роли `system_owner`;
- защита последнего активного владельца;
- исключение чувствительных сведений из ограниченного представления;
- разделение изменяющих операций на отдельные POST-маршруты;
- адаптивность списка и карточки.

## 2. Результаты review

### 2.1 Компактный список

Решение оставить колонки «Пользователь», «Логин», «Статус» и «Последний вход» принято. Подробные сведения переносятся в карточку. Отдельная колонка действий не требуется: отображаемое имя становится ссылкой.

### 2.2 Видимость последнего входа

Колонка сохраняется для единой структуры интерфейса. Для `viewer` и `operator` реальное значение не выбирается и заменяется текстом «Недоступно».

### 2.3 Редактирование

Основные реквизиты, роли и активность разделены на независимые серверные операции. Это исключает предоставление избыточных прав пользователю, имеющему только одно из разрешений.

### 2.4 Защита владельца

Проверка должна выполняться сервером в транзакции. Скрытие роли или кнопки в интерфейсе не считается защитой.

Невладелец:

- не получает роль `system_owner` в доступном наборе;
- не может передать ее идентификатор прямым POST;
- не может снять уже существующую роль владельца.

### 2.5 Ограниченная карточка

Пользователь только с правом просмотра получает имя, логин, статус и роли. Email, последний вход, основание создания и сведения о подтверждении не должны попадать в возвращаемую структуру репозитория.

## 3. Замечания, не блокирующие реализацию

1. Основная спецификация продолжает содержать устаревший внутренний статус `Draft for review`, хотя отдельное решение имеет статус `Approved`. Это документационный долг общего инкремента и не блокирует настоящую реализацию.
2. Полноценная история изменений пока отсутствует. Поле `updated_at` показывает только время последнего изменения.
3. Операция сброса пароля намеренно вынесена за границы настоящего инкремента.

## 4. Заключение

Архитектура и спецификация согласованы с существующей моделью RBAC и миграциями 001–003. Блокирующих замечаний нет. Документ может быть утвержден для реализации без изменений.
