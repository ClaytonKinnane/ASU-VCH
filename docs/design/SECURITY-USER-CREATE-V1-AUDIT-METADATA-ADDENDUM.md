# Security / User Create v1 — Audit Metadata Addendum

Статус: **Approved refinement**  
Домен: **Security**  
Основной дизайн: `docs/design/SECURITY-USER-CREATE-V1-DESIGN.md`

## 1. Назначение

Документ уточняет обязательные метаданные создания и подтверждения учетной записи.

Утверждено:

- создатель учетной записи может самостоятельно подтвердить ее при наличии `security.users.update`;
- в карточке пользователя обязательно отображается, кто создал учетную запись;
- после подтверждения отображается, кто подтвердил учетную запись;
- при создании обязательно указывается основание добавления учетной записи.

## 2. Изменение модели данных

Миграция `003_security_user_approval.sql` должна добавить в `users`:

```text
created_by BIGINT UNSIGNED NULL
creation_reason VARCHAR(500) NULL
approval_status VARCHAR(20) NOT NULL DEFAULT 'approved'
approved_by BIGINT UNSIGNED NULL
approved_at DATETIME NULL
```

Внешние ключи:

```text
created_by  -> users.id ON DELETE SET NULL
approved_by -> users.id ON DELETE SET NULL
```

`creation_reason` допускает `NULL` только для учетных записей, существовавших до миграции, bootstrap-операций и системных учетных записей, созданных вне административной формы.

Для всех новых учетных записей, создаваемых через административный интерфейс, `creation_reason` является обязательным на уровне приложения.

## 3. Поле «Основание добавления»

Форма создания пользователя содержит обязательное многострочное поле:

```text
creation_reason
```

Требования:

- `trim`;
- длина от 10 до 500 символов;
- управляющие символы запрещены, кроме перевода строки;
- значение хранится как обычный текст;
- HTML всегда экранируется при выводе;
- поле сохраняется после ошибок валидации;
- пароль при ошибке по-прежнему очищается;
- основание нельзя передавать в URL или технические журналы целиком.

Примеры допустимых оснований:

```text
Приказ командира части № 42 от 24.07.2026.
Назначение сотрудника оператором отдела кадров.
Создание служебной учетной записи для ведения справочников.
```

## 4. Создание учетной записи

Новая учетная запись создается со значениями:

```text
approval_status = pending
is_active = 0
created_by = current_user.id
creation_reason = validated form value
```

Создание пользователя, назначение ролей и сохранение основания выполняются одной транзакцией.

Если транзакция завершается ошибкой, ни пользователь, ни роли, ни основание не сохраняются.

## 5. Подтверждение учетной записи

Создатель может подтвердить собственноручно созданную учетную запись, если имеет разрешение:

```text
security.users.update
```

При подтверждении сохраняются:

```text
approval_status = approved
is_active = 1
approved_by = current_user.id
approved_at = server time
```

Повторное подтверждение запрещено.

## 6. Карточка пользователя

Будущая карточка пользователя должна содержать блок **«Создание и подтверждение»**.

Поля блока:

```text
Создал
Дата создания
Основание добавления
Подтвердил
Дата подтверждения
```

Правила отображения:

- для `created_by` и `approved_by` показываются `display_name` и логин;
- если связанная учетная запись недоступна, показывается «Пользователь недоступен»;
- если значение отсутствует из-за bootstrap или старых данных, показывается «Системная операция»;
- до подтверждения поля «Подтвердил» и «Дата подтверждения» показывают «Ожидается»;
- основание отображается полностью в карточке, с сохранением переносов строк и HTML-экранированием.

## 7. Список пользователей

В основном списке не требуется выводить полное основание, чтобы не перегружать таблицу.

Для ожидающей учетной записи достаточно отображать:

- статус «Ожидает подтверждения»;
- автора создания;
- дату создания;
- действие «Подтвердить» при наличии разрешения.

Полное основание выводится в карточке пользователя.

## 8. Совместимость

Для существующих пользователей после миграции:

```text
approval_status = approved
created_by = NULL
creation_reason = NULL
approved_by = NULL
approved_at = NULL
```

Существующий владелец `Admin` остается активным и подтвержденным.

Отсутствие основания у исторической учетной записи не является ошибкой.

## 9. Дополнительные проверки

Необходимо проверить:

1. создание без основания отклоняется;
2. основание короче 10 символов отклоняется;
3. основание длиннее 500 символов отклоняется;
4. валидное основание сохраняется без искажения;
5. HTML в основании отображается как текст;
6. `created_by` соответствует создателю;
7. создатель с `security.users.update` может подтвердить учетную запись;
8. `approved_by` соответствует подтвердившему;
9. карточка показывает автора, подтвердившего, даты и основание;
10. существующий `Admin` продолжает входить после миграции.

## 10. Критерии приемки уточнения

Уточнение принято, если:

- административная форма требует основание добавления;
- основание сохраняется транзакционно вместе с учетной записью;
- карточка показывает автора создания и подтверждения;
- карточка показывает основание добавления;
- создатель может подтвердить учетную запись при наличии права;
- исторические учетные записи и bootstrap остаются совместимыми.
