# Security / User Create v1 — Design

Статус: **Draft for review**  
Домен: **Security**  
Связанная спецификация: `docs/specifications/SECURITY-USERS-MANAGEMENT-V1.md`  
Связанное решение: `docs/decisions/SECURITY-USERS-MANAGEMENT-V1-APPROVAL.md`

## 1. Назначение инкремента

Инкремент добавляет безопасное создание учетной записи из административного интерфейса с обязательным последующим подтверждением администратором.

В инкремент входят:

- форма создания пользователя;
- серверная валидация;
- проверка уникальности логина и email;
- создание безопасного хэша временного пароля;
- назначение одной или нескольких начальных ролей;
- создание учетной записи в состоянии ожидания подтверждения;
- фиксация пользователя, создавшего учетную запись;
- фиксация пользователя, подтвердившего учетную запись;
- защита роли `system_owner`;
- сообщение об успешном создании;
- переход к списку пользователей.

Не входят:

- редактирование существующего пользователя;
- блокировка и архивирование;
- восстановление;
- сброс пароля;
- полноценная карточка пользователя;
- создание и редактирование ролей.

## 2. Маршруты

```text
GET  /admin/users/create.php
POST /admin/users/create.php
POST /admin/users/approve.php
```

После успешного создания выполняется PRG-переход:

```text
302 /admin/users.php
```

Список показывает flash-сообщение:

```text
Пользователь «<username>» создан и ожидает подтверждения.
```

После подтверждения:

```text
Пользователь «<username>» подтвержден и активирован.
```

## 3. Авторизация

Для открытия и отправки формы требуется:

```text
security.users.create
```

Для назначения обычных ролей дополнительно требуется:

```text
security.users.assign_roles
```

Для подтверждения учетной записи требуется:

```text
security.users.update
```

Правило для `system_owner`:

- роль может назначить только пользователь, уже имеющий роль `system_owner`;
- одного разрешения `security.users.assign_roles` недостаточно;
- проверка выполняется сервером;
- скрытие роли в UI не заменяет серверную проверку.

Неаутентифицированный пользователь перенаправляется на `/`. Авторизованный пользователь без разрешения получает HTTP 403.

## 4. Изменение модели данных

Текущая схема не позволяет отличить ожидающую подтверждения учетную запись от заблокированной и не хранит автора создания. Поэтому требуется новая миграция:

```text
003_security_user_approval.sql
```

### 4.1 Новые поля users

```text
created_by BIGINT UNSIGNED NULL
approval_status VARCHAR(20) NOT NULL DEFAULT 'approved'
approved_by BIGINT UNSIGNED NULL
approved_at DATETIME NULL
```

Внешние ключи:

```text
created_by  -> users.id ON DELETE SET NULL
approved_by -> users.id ON DELETE SET NULL
```

Допустимые значения `approval_status`:

```text
pending
approved
rejected
```

Правила совместимости:

- существующие пользователи получают `approval_status = 'approved'`;
- существующий владелец не изменяется;
- для существующих пользователей `created_by`, `approved_by`, `approved_at` могут быть `NULL`;
- новая учетная запись создается с `approval_status = 'pending'` и `is_active = 0`;
- подтверждение устанавливает `approval_status = 'approved'`, `is_active = 1`, `approved_by`, `approved_at`;
- отклонение, если будет реализовано позднее, устанавливает `approval_status = 'rejected'` и оставляет `is_active = 0`.

`created_at` хранит время создания, а `created_by` — автора операции.

## 5. Состояния учетной записи

Приоритет определения состояния в UI:

1. `deleted_at IS NOT NULL` → «Архивирован»;
2. `approval_status = 'pending'` → «Ожидает подтверждения»;
3. `approval_status = 'rejected'` → «Отклонен»;
4. `is_active = 0` → «Заблокирован»;
5. иначе → «Активен».

Ожидающая подтверждения учетная запись не может войти в систему, даже если ей уже назначены роли.

## 6. Поля формы

### 6.1 Обязательные

```text
username
display_name
password
password_confirmation
```

### 6.2 Необязательные

```text
email
role_ids[]
is_temporary
must_change_password
```

### 6.3 Значения по умолчанию

```text
approval_status = pending
is_active = 0
is_temporary = 1
must_change_password = 1
created_by = current_user.id
```

Новая учетная запись создается неактивной, с временным паролем и обязательной сменой пароля после подтверждения и первого входа.

## 7. Валидация логина

`username`:

- обрезается через `trim`;
- длина: от 3 до 100 символов;
- разрешены латинские буквы, цифры, точка, дефис и подчеркивание;
- первый и последний символ — буква или цифра;
- пробелы и управляющие символы запрещены;
- каноническое значение: `mb_strtolower($username, 'UTF-8')`;
- уникальность проверяется по `username_canonical`.

Регулярное выражение:

```text
^[A-Za-z0-9](?:[A-Za-z0-9._-]{1,98}[A-Za-z0-9])?$
```

Проверка уникальности выполняется до INSERT для понятного сообщения и повторно обеспечивается уникальным индексом БД.

## 8. Валидация отображаемого имени

`display_name`:

- `trim`;
- длина: от 1 до 150 символов;
- HTML не допускается как разметка и всегда экранируется при выводе;
- строка может содержать кириллицу, латиницу, цифры, пробелы и обычные знаки пунктуации;
- управляющие символы запрещены.

`display_name` является подписью учетной записи и не заменяет профиль Personnel.

## 9. Валидация email

`email`:

- необязателен;
- пустая строка преобразуется в `NULL`;
- максимальная длина: 255 символов;
- проверяется через `filter_var(..., FILTER_VALIDATE_EMAIL)`;
- каноническое значение: `mb_strtolower($email, 'UTF-8')`;
- уникальность проверяется по `email_canonical`.

В версии 1 адрес не подтверждается отправкой письма.

## 10. Политика временного пароля

- длина от 10 до 128 символов;
- минимум одна буква;
- минимум одна цифра;
- пароль и подтверждение должны совпадать байт-в-байт;
- пароль хэшируется через `password_hash(..., PASSWORD_DEFAULT)`;
- пароль никогда не журналируется и не включается в URL, flash или HTML после отправки;
- существующий пароль невозможно прочитать из БД;
- форма не генерирует пароль автоматически.

## 11. Начальные роли

Форма показывает системные роли:

```text
system_owner
administrator
operator
viewer
```

Правила:

- допускается создание пользователя без роли;
- дубликаты `role_ids[]` нормализуются;
- принимаются только существующие роли;
- ID ролей не считаются доверенными данными;
- `administrator` может назначать `administrator`, `operator`, `viewer`;
- только `system_owner` может назначать `system_owner`;
- роли назначаются в той же транзакции, что и пользователь;
- `user_roles.assigned_at` получает серверное время;
- `user_roles.assigned_by` получает ID создателя учетной записи;
- назначенные роли не дают доступ до подтверждения учетной записи.

При создании без роли UI показывает предупреждение:

```text
Без роли пользователь не получит доступ к административным разделам после подтверждения.
```

## 12. Транзакция создания

Операция выполняется одной транзакцией:

1. повторная проверка полномочий;
2. нормализация входных данных;
3. валидация;
4. проверка ролей;
5. проверка права назначать `system_owner`;
6. проверка уникальности канонического логина и email;
7. INSERT в `users` с `approval_status = 'pending'`, `is_active = 0`, `created_by = current_user.id`;
8. INSERT выбранных ролей в `user_roles`;
9. COMMIT;
10. flash и redirect.

При любой ошибке выполняется rollback.

## 13. Подтверждение учетной записи

Подтверждение выполняется отдельным POST-запросом и одной транзакцией.

Сервер обязан:

- проверить `security.users.update`;
- проверить CSRF;
- загрузить пользователя с блокировкой строки или эквивалентной защитой;
- разрешить подтверждение только при `approval_status = 'pending'`;
- установить `approval_status = 'approved'`;
- установить `is_active = 1`;
- установить `approved_by = current_user.id`;
- установить `approved_at` и `updated_at` серверным временем;
- не изменять пароль и роли;
- отклонять повторное подтверждение как недопустимое состояние.

Создатель может подтвердить собственноручно созданную учетную запись, если у него есть требуемое разрешение. Разделение полномочий «создатель не может подтверждать сам» в v1 не вводится.

## 14. Конкурентные запросы и дубликаты

Даже после предварительной проверки возможна гонка двух запросов.

Сервис обязан:

- перехватить нарушение уникального индекса;
- преобразовать его в понятное сообщение формы;
- не показывать SQLSTATE, запрос или структуру БД;
- сохранить введенные безопасные поля;
- очистить оба поля пароля.

Сообщения:

```text
Пользователь с таким логином уже существует.
Пользователь с таким email уже существует.
```

## 15. CSRF и метод запроса

- все изменяющие операции выполняются только POST;
- POST требует действительный CSRF-токен;
- GET никогда не создает и не подтверждает пользователя;
- при невалидном CSRF возвращается 419;
- формы используют существующий `csrf_token()`.

## 16. Представление формы

Страница сохраняет навигацию Security-раздела.

Основная плитка формы содержит блоки:

### Учетная запись

- логин;
- отображаемое имя;
- email;
- информационное сообщение: «После создания учетная запись будет ожидать подтверждения администратора».

### Начальный пароль

- временный пароль;
- подтверждение;
- подсказка политики;
- флаги «Временная учетная запись» и «Потребовать смену пароля».

### Роли

- checkbox-список доступных ролей;
- отдельная визуальная пометка системного владельца;
- предупреждение при отсутствии выбранных ролей.

Действия:

```text
Создать пользователя
Отмена
```

## 17. Изменения списка пользователей

На `/admin/users.php` появляется активная кнопка:

```text
Создать пользователя
```

Новый пользователь отображается со статусом:

```text
Ожидает подтверждения
```

Для пользователей с `security.users.update` рядом с ожидающей учетной записью доступно действие:

```text
Подтвердить
```

В строке или будущей карточке пользователя выводятся:

- «Создал» — отображаемое имя или логин создателя;
- дата и время создания;
- после подтверждения — «Подтвердил» и дата подтверждения.

Если связанный администратор удален, отображается «Системная операция» или «Пользователь недоступен» без нарушения целостности записи.

## 18. Ошибки формы

Ошибки показываются общим блоком и рядом с соответствующим полем, без технических деталей.

После ошибки сохраняются:

- username;
- display_name;
- email;
- выбранные роли;
- checkbox-флаги.

Не сохраняются и не возвращаются в HTML:

- password;
- password_confirmation.

## 19. Сервисный слой

Предлагается выделить:

```text
app/Security/UserCreateService.php
app/Security/UserApprovalService.php
```

`UserCreateService` отвечает за валидацию, уникальность, роли, транзакционное создание и фиксацию `created_by`.

`UserApprovalService` отвечает за проверку состояния, транзакционное подтверждение и фиксацию `approved_by`/`approved_at`.

Страницы не должны содержать SQL INSERT/UPDATE бизнес-операций.

## 21. Проверки

Автоматические/CLI:

- PHP syntax check;
- миграция `003` применена;
- повторный запуск установщика безопасен;
- существующий Admin остается `approved` и активным;
- создание пользователя дает `pending`, `is_active = 0`, корректный `created_by`;
- ожидающий пользователь не может войти;
- подтверждение дает `approved`, `is_active = 1`, корректные `approved_by` и `approved_at`;
- повторное подтверждение отклоняется;
- создание с email и без email;
- создание без роли и с несколькими ролями;
- дубликаты логина и email в другом регистре;
- несовпадающее подтверждение пароля;
- попытка administrator назначить `system_owner`;
- успешное назначение `system_owner` владельцем;
- rollback при ошибке;
- отсутствие пароля в HTML и диагностике;
- RBAC check и smoke test.

Ручные:

- desktop;
- mobile;
- отображение статуса ожидания;
- отображение автора создания;
- подтверждение учетной записи;
- flash после создания и подтверждения;
- появление пользователя в поиске и фильтрах.

## 22. Критерии приемки

Инкремент принят, если:

1. владелец открывает форму создания;
2. пользователь без `security.users.create` получает 403;
3. валидная учетная запись создается в состоянии `pending`;
4. созданная учетная запись не может войти до подтверждения;
5. `created_by` содержит ID создателя;
6. список показывает автора и время создания;
7. подтверждение активирует учетную запись;
8. `approved_by` и `approved_at` заполняются;
9. пароль хранится только как хэш;
10. дубликаты логина и email отклоняются без раскрытия БД;
11. роли назначаются транзакционно с `assigned_by`;
12. administrator не может назначить `system_owner`;
13. system_owner может назначить `system_owner`;
14. CSRF обязателен;
15. пароль не возвращается после ошибки;
16. desktop и mobile визуально проверены;
17. PHP syntax, migration check, RBAC check и smoke test проходят;
18. существующий Admin продолжает входить в систему.

## 23. Решения для Approval

Предлагается утвердить:

1. отдельный маршрут `/admin/users/create.php`;
2. новая учетная запись создается с `approval_status = 'pending'` и `is_active = 0`;
3. автор создания сохраняется в `users.created_by`;
4. подтверждение сохраняет `approved_by` и `approved_at`;
5. существующие пользователи мигрируются как `approved`;
6. `is_temporary = 1` и `must_change_password = 1` включены по умолчанию;
7. минимальная длина временного пароля — 10 символов, обязательны буква и цифра;
8. допускается пользователь без роли с предупреждением;
9. `administrator` назначает `administrator`, `operator`, `viewer`;
10. `system_owner` назначается только владельцем;
11. создание пользователя и ролей выполняется одной транзакцией;
12. подтверждение выполняется отдельным POST-действием;
13. создатель может подтвердить созданную им учетную запись при наличии `security.users.update`;
14. автогенерация и показ пароля не входят в этот инкремент.
