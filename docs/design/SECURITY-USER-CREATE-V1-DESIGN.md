# Security / User Create v1 — Design

Статус: **Draft for review**  
Домен: **Security**  
Связанная спецификация: `docs/specifications/SECURITY-USERS-MANAGEMENT-V1.md`  
Связанное решение: `docs/decisions/SECURITY-USERS-MANAGEMENT-V1-APPROVAL.md`

## 1. Назначение инкремента

Инкремент добавляет безопасное создание учетной записи из административного интерфейса.

В инкремент входят:

- форма создания пользователя;
- серверная валидация;
- проверка уникальности логина и email;
- создание безопасного хэша временного пароля;
- назначение одной или нескольких начальных ролей;
- фиксация `assigned_by`;
- защита роли `system_owner`;
- сообщение об успешном создании;
- переход к списку пользователей.

Не входят:

- редактирование существующего пользователя;
- блокировка и архивирование;
- восстановление;
- сброс пароля;
- карточка пользователя;
- создание и редактирование ролей.

## 2. Маршруты

```text
GET  /admin/users/create.php
POST /admin/users/create.php
```

После успешного создания выполняется PRG-переход:

```text
302 /admin/users.php
```

Список показывает flash-сообщение:

```text
Пользователь «<username>» создан.
```

## 3. Авторизация

Для открытия и отправки формы требуется:

```text
security.users.create
```

Для назначения обычных ролей дополнительно требуется:

```text
security.users.assign_roles
```

Правило для `system_owner`:

- роль может назначить только пользователь, уже имеющий роль `system_owner`;
- одного разрешения `security.users.assign_roles` недостаточно;
- проверка выполняется сервером;
- скрытие роли в UI не заменяет серверную проверку.

Неаутентифицированный пользователь перенаправляется на `/`.
Авторизованный пользователь без разрешения получает HTTP 403.

## 4. Поля формы

### 4.1 Обязательные

```text
username
	display_name
password
password_confirmation
```

### 4.2 Необязательные

```text
email
role_ids[]
is_temporary
must_change_password
```

### 4.3 Значения по умолчанию

```text
is_active = 1
is_temporary = 1
must_change_password = 1
```

Новая учетная запись создается активной, с временным паролем и обязательной сменой пароля при первом входе.

## 5. Валидация логина

`username`:

- обрезается через `trim`;
- длина: от 3 до 100 символов;
- разрешены латинские буквы, цифры, точка, дефис и подчеркивание;
- первый и последний символ — буква или цифра;
- пробелы и управляющие символы запрещены;
- каноническое значение: `mb_strtolower($username, 'UTF-8')`;
- уникальность проверяется по `username_canonical`.

Предлагаемое регулярное выражение:

```text
^[A-Za-z0-9](?:[A-Za-z0-9._-]{1,98}[A-Za-z0-9])?$
```

Проверка уникальности выполняется до INSERT для понятного сообщения и повторно обеспечивается уникальным индексом БД.

## 6. Валидация отображаемого имени

`display_name`:

- `trim`;
- длина: от 1 до 150 символов;
- HTML не допускается как разметка и всегда экранируется при выводе;
- строка может содержать кириллицу, латиницу, цифры, пробелы и обычные знаки пунктуации;
- управляющие символы запрещены.

`display_name` является подписью учетной записи и не заменяет профиль Personnel.

## 7. Валидация email

`email`:

- необязателен;
- пустая строка преобразуется в `NULL`;
- максимальная длина: 255 символов;
- проверяется через `filter_var(..., FILTER_VALIDATE_EMAIL)`;
- каноническое значение: `mb_strtolower($email, 'UTF-8')`;
- уникальность проверяется по `email_canonical`.

В версии 1 адрес не подтверждается отправкой письма.

## 8. Политика временного пароля

Предлагается принять минимальную политику v1:

- длина от 10 до 128 символов;
- минимум одна буква;
- минимум одна цифра;
- пробелы разрешены внутри, но ведущие и завершающие пробелы не удаляются автоматически;
- пароль и подтверждение должны совпадать байт-в-байт;
- пароль хэшируется через `password_hash(..., PASSWORD_DEFAULT)`;
- пароль никогда не журналируется и не включается в URL, flash или HTML после отправки;
- существующий пароль невозможно прочитать из БД.

Форма не генерирует пароль автоматически в этом инкременте.

## 9. Начальные роли

Форма показывает системные роли:

```text
system_owner
administrator
operator
viewer
```

UI использует checkbox-список и показывает название с описанием.

Правила:

- допускается создание пользователя без роли;
- дубликаты `role_ids[]` нормализуются;
- принимаются только существующие роли;
- ID ролей не считаются доверенными данными;
- `administrator` может назначать `administrator`, `operator`, `viewer`;
- только `system_owner` может назначать `system_owner`;
- роли назначаются в той же транзакции, что и пользователь;
- `user_roles.assigned_at` получает серверное время;
- `user_roles.assigned_by` получает ID действующего администратора.

Создание пользователя без роли допускается, но UI показывает предупреждение:

```text
Без роли пользователь не получит доступ к административным разделам.
```

## 10. Транзакция

Операция выполняется одной транзакцией:

1. повторная проверка полномочий;
2. нормализация входных данных;
3. валидация;
4. проверка ролей;
5. проверка права назначать `system_owner`;
6. проверка уникальности канонического логина и email;
7. INSERT в `users`;
8. INSERT выбранных ролей в `user_roles`;
9. COMMIT;
10. flash и redirect.

При любой ошибке выполняется rollback.

## 11. Конкурентные запросы и дубликаты

Даже после предварительной проверки возможна гонка двух запросов.

Сервис обязан:

- перехватить нарушение уникального индекса;
- преобразовать его в понятное сообщение формы;
- не показывать SQLSTATE, запрос или структуру БД;
- сохранить введенные безопасные поля;
- очистить оба поля пароля.

Сообщения:

```text
Пользователь с таким логином уже существует.
Пользователь с таким email уже существует.
```

## 12. CSRF и метод запроса

- изменяющая операция выполняется только POST;
- POST требует действительный CSRF-токен;
- GET никогда не создает пользователя;
- при невалидном CSRF возвращается 419;
- форма использует существующий `csrf_token()`.

## 13. Представление формы

Страница сохраняет навигацию Security-раздела.

Основная плитка формы содержит блоки:

### Учетная запись

- логин;
- отображаемое имя;
- email.

### Начальный пароль

- временный пароль;
- подтверждение;
- подсказка политики;
- флаги «Временная учетная запись» и «Потребовать смену пароля».

### Роли

- checkbox-список доступных ролей;
- отдельная визуальная пометка системного владельца;
- предупреждение при отсутствии выбранных ролей.

Действия:

```text
Создать пользователя
Отмена
```

`Отмена` ведет на `/admin/users.php` без изменения данных.

## 14. Ошибки формы

Ошибки показываются:

- общим блоком в начале формы;
- рядом с соответствующим полем;
- без технических деталей.

После ошибки сохраняются:

- username;
- display_name;
- email;
- выбранные роли;
- checkbox-флаги.

Не сохраняются и не возвращаются в HTML:

- password;
- password_confirmation.

## 15. Изменения списка пользователей

На `/admin/users.php` появляется активная кнопка:

```text
Создать пользователя
```

Кнопка отображается только при `security.users.create`.

После успешного создания:

- счетчики списка обновляются;
- новый пользователь виден в списке;
- flash-сообщение выводится в стиле темы;
- фильтры не переносятся на redirect.

## 16. Сервисный слой

Предлагается выделить:

```text
app/Security/UserCreateService.php
```

Ответственность сервиса:

- нормализация и валидация;
- проверка уникальности;
- проверка выбранных ролей;
- проверка назначения `system_owner`;
- транзакционное создание;
- перевод ошибок БД в доменные ошибки.

Страница не должна содержать SQL INSERT.

Допускается отдельный тип результата/исключения без создания сложной инфраструктуры.

## 17. Планируемые файлы

```text
app/Security/UserCreateService.php
app/bootstrap.php
public/admin/users/create.php
public/admin/users.php
themes/asu-blue/assets/css/users.css
docs/decisions/SECURITY-USER-CREATE-V1-APPROVAL.md
```

Новая миграция не требуется: все необходимые поля и связи уже существуют.

## 18. Проверки

### Автоматические/CLI

- PHP syntax check;
- RBAC check;
- smoke test;
- создание пользователя с минимально допустимыми данными;
- создание с email;
- создание без роли;
- создание с несколькими ролями;
- дубликат логина в другом регистре;
- дубликат email в другом регистре;
- несовпадающее подтверждение пароля;
- слишком короткий пароль;
- несуществующий role ID;
- попытка administrator назначить `system_owner`;
- успешное назначение `system_owner` владельцем;
- rollback при ошибке назначения роли;
- отсутствие пароля в HTML и диагностике.

### Ручные

- desktop;
- mobile;
- ошибки каждого поля;
- длинные допустимые значения;
- отмена;
- flash после создания;
- появление нового пользователя в поиске и фильтрах.

## 19. Критерии приемки

Инкремент принят, если:

1. владелец открывает форму создания;
2. пользователь без `security.users.create` получает 403;
3. валидная учетная запись создается;
4. пароль хранится только как хэш;
5. дубликаты логина и email отклоняются без раскрытия БД;
6. роли назначаются транзакционно с `assigned_by`;
7. administrator не может назначить `system_owner`;
8. system_owner может назначить `system_owner`;
9. CSRF обязателен;
10. пароль не возвращается после ошибки;
11. список и счетчики обновляются;
12. desktop и mobile визуально проверены;
13. PHP syntax, RBAC check и smoke test проходят;
14. существующий Admin продолжает входить в систему.

## 20. Решения для Approval

Предлагается утвердить:

1. отдельный маршрут `/admin/users/create.php`;
2. пользователь создается активным;
3. `is_temporary = 1` и `must_change_password = 1` включены по умолчанию;
4. минимальная длина временного пароля — 10 символов, обязательны буква и цифра;
5. допускается пользователь без роли с предупреждением;
6. `administrator` назначает `administrator`, `operator`, `viewer`;
7. `system_owner` назначается только владельцем;
8. создание пользователя и ролей выполняется одной транзакцией;
9. после успеха выполняется redirect на список;
10. автогенерация и показ пароля не входят в этот инкремент.
