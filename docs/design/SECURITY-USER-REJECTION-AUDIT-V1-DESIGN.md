# Security User Rejection Audit v1 — Architecture and Specification

Дата: 2026-07-25
Статус: утверждено владельцем проекта
Ветка: `feature/user-rejection-audit`
База: `main` (`8661d34602e07f67b4c0425f62b020f5ec439932`)

## 1. Назначение

Инкремент добавляет контролируемое отклонение новой учетной записи, находящейся в состоянии:

```text
approval_status = pending
deleted_at IS NULL
```

После отклонения:

```text
approval_status = rejected
is_active = 0
```

Отклоненная учетная запись не может войти в систему и не может быть подтверждена существующим маршрутом.

## 2. Миграция 004

Добавляется файл:

```text
database/migrations/004_security_user_rejection_audit.sql
```

В таблицу `users` добавляются:

```text
rejected_by       BIGINT UNSIGNED NULL
rejected_at       DATETIME NULL
rejection_reason  VARCHAR(500) NULL
```

Также добавляются внешний ключ и индексы:

```text
fk_users_rejected_by
idx_users_rejected_by
idx_users_rejected_at
```

Внешний ключ:

```text
rejected_by -> users.id
ON UPDATE RESTRICT
ON DELETE SET NULL
```

Поля nullable для совместимости с историческими или вручную измененными записями. Штатный сервис всегда заполняет субъекта, дату и основание.

## 3. Разрешение

Добавляется системное разрешение:

```text
security.users.reject
```

Назначение: отклонение ожидающей подтверждения учетной записи с фиксацией субъекта, даты и основания.

Разрешение назначается роли `administrator`. Роль `system_owner` получает доступ через существующее `system.*.*`.

После миграции ожидается:

```text
4 системные роли
19 системных разрешений
```

Существующее подтверждение продолжает использовать `security.users.update`.

## 4. Сервис

Добавляется:

```text
app/Security/UserRejectionService.php
```

Метод:

```php
reject(int $userId, int $actorId, string $reason): array
```

Последовательность:

1. Проверить основание.
2. Открыть транзакцию.
3. Загрузить пользователя через `SELECT ... FOR UPDATE`.
4. Проверить существование и отсутствие архивирования.
5. Разрешить операцию только при `approval_status = 'pending'`.
6. Установить rejected-состояние и аудит.
7. Зафиксировать транзакцию.

Обновление:

```text
approval_status  = rejected
is_active        = 0
approved_by      = NULL
approved_at      = NULL
rejected_by      = actorId
rejected_at      = server time
rejection_reason = validated reason
updated_at       = server time
```

Не изменяются:

```text
password_hash
roles
created_by
creation_reason
is_temporary
must_change_password
```

## 5. Маршрут

Добавляется:

```text
POST /admin/users/reject.php
```

Маршрут:

- требует `security.users.reject`;
- принимает изменение только через POST;
- проверяет CSRF;
- валидирует `user_id`;
- передает основание сервису;
- использует redirect-after-POST;
- возвращает пользователя в карточку учетной записи.

GET-запрос не изменяет данные и перенаправляется к списку пользователей.

## 6. Терминальное состояние

В v1 поддерживаются переходы:

```text
pending -> approved
pending -> rejected
```

Не поддерживаются:

```text
rejected -> pending
rejected -> approved
rejected -> active
```

Возврат отклоненной записи потребует отдельного согласованного инкремента.

## 7. Конкурентные действия

Подтверждение и отклонение блокируют одну строку пользователя через `SELECT ... FOR UPDATE`.

Если два администратора одновременно отправят противоположные действия, успешно завершится только первое. Второе получит:

```text
Учетная запись уже обработана.
```

## 8. Основание отклонения

Поле обязательно.

Правила:

- после `trim()` — от 10 до 500 символов;
- разрешен многострочный текст;
- управляющие символы запрещены;
- HTML не интерпретируется;
- вывод только через экранирование.

Ошибка:

```text
Основание отклонения должно содержать от 10 до 500 символов.
```

## 9. Интерфейс pending-пользователя

В карточке сохраняется кнопка:

```text
Подтвердить и активировать
```

При наличии `security.users.reject` добавляется опасная зона:

```text
Основание отклонения
[textarea]

[Отклонить пользователя]
```

Перед отправкой интерфейс показывает подтверждение:

```text
Отклонить учетную запись? В текущей версии вернуть ее в ожидание подтверждения нельзя.
```

JavaScript-подтверждение не заменяет серверную авторизацию и проверку состояния.

## 10. Карточка отклоненного пользователя

Основной статус:

```text
Отклонен
```

В поле «Подтверждение» отображается:

```text
Отклонен
Отображаемое имя отклонившего
```

Имя выводится без логина, является ссылкой на карточку субъекта и доступно только `system_owner` и `administrator`.

Если субъект недоступен:

```text
Субъект недоступен
```

## 11. Аудит

Блок переименовывается в:

```text
Создание и обработка
```

Для approved:

```text
Подтвердил
Дата подтверждения
```

Для rejected:

```text
Отклонил
Дата отклонения
Основание отклонения
```

Для pending:

```text
Решение: Не обработан
```

Подробный аудит доступен только владельцу и администратору. Оператор и viewer видят только общий статус.

## 12. Список пользователей

Добавляется фильтр:

```text
Отклоненные
```

Условие:

```sql
approval_status = 'rejected'
AND deleted_at IS NULL
```

В сводку добавляется шестая плитка «Отклоненные». На мобильном экране используется существующая горизонтальная прокрутка.

## 13. После отклонения

После успешной операции:

- карточка остается открытой;
- выводится сообщение `Учетная запись «<логин>» отклонена.`;
- формы подтверждения и отклонения исчезают;
- кнопки блокировки и разблокировки не показываются;
- вход остается запрещенным;
- роли не удаляются.

Существующие формы редактирования основных данных и ролей не меняются.

## 14. Ошибки

```text
Учетная запись не найдена.
Учетная запись уже обработана.
Основание отклонения должно содержать от 10 до 500 символов.
Недостаточно прав для отклонения пользователя.
Учетная запись не отклонена из-за серверной ошибки.
```

Серверная ошибка журналируется без персональных данных и без текста основания.

## 15. Проверки

Добавляется:

```text
database/check-security-user-rejection.php
```

CLI-проверка подтверждает:

- migration 004 зарегистрирована;
- три новых столбца существуют;
- внешний ключ использует `ON DELETE SET NULL`;
- системных разрешений 19;
- administrator получил `security.users.reject`;
- короткое основание отклоняется;
- pending-пользователь успешно отклоняется;
- `is_active = 0`;
- заполнены `rejected_by`, `rejected_at`, `rejection_reason`;
- `approved_by` и `approved_at` пусты;
- повторное отклонение запрещено;
- подтверждение отклоненной записи запрещено;
- тестовые записи удаляются.

Регрессия:

```text
Test-PhpSyntax.ps1
install.php
check-security-rbac.php
check-security-user-approval.php
check-security-required-password-change.php
Test-LocalSmoke.ps1
```

Ручная проверка включает создание pending-пользователя, валидацию основания, успешное отклонение, аудит, privacy, фильтр, CSRF 419, прямой повторный POST, невозможность входа, desktop, 390 px и 360 px.

## 16. Вне объема

- отмена отклонения;
- повторная подача на подтверждение;
- удаление отклоненной записи;
- архивирование и восстановление;
- email-уведомления;
- история нескольких решений;
- массовое отклонение;
- административный сброс пароля;
- добровольная смена пароля.
