# Security User Rejection Audit v1 — Review

Дата: 2026-07-25
Статус: завершено до реализации
Связанный документ: `SECURITY-USER-REJECTION-AUDIT-V1-DESIGN.md`

## 1. Проверенный объем

Рассмотрены:

- модель состояний `pending`, `approved`, `rejected`;
- существующий `UserApprovalService`;
- структура migration 003;
- текущие разрешения RBAC;
- карточка и список пользователей;
- конфиденциальность аудита;
- конкурентные approve/reject-запросы;
- требования к CSRF, POST и PRG;
- миграционная совместимость;
- тестовые и регрессионные сценарии.

## 2. Архитектурные выводы

### 2.1 Отдельный аудит отклонения обязателен

Использование `approved_by` и `approved_at` для отклонения признано недопустимым: это смешало бы два противоположных решения и сделало аудит недостоверным.

Принято добавить:

```text
rejected_by
rejected_at
rejection_reason
```

### 2.2 Исторические данные не выдумываются

Новые поля nullable. Миграция не заполняет фиктивного субъекта, дату или основание для возможных исторических rejected-записей.

### 2.3 Операция разрешена только из pending

Состояние `rejected` является терминальным в v1. Повторное отклонение, подтверждение отклоненной записи и возврат в pending запрещены.

### 2.4 Rejected всегда inactive

Сервис атомарно устанавливает:

```text
approval_status = rejected
is_active = 0
```

Это сохраняет существующую защиту входа и исключает противоречивое активное rejected-состояние.

### 2.5 Основание обязательно

Для новых штатных отклонений причина должна содержать 10–500 символов после trim. Серверная валидация является обязательной независимо от HTML-атрибутов.

### 2.6 Разрешение проверяется сервером

Новый маршрут использует `security.users.reject`. Наличие формы или кнопки не является источником авторизации.

### 2.7 Транзакция и блокировка строки

`SELECT ... FOR UPDATE` обеспечивает корректное соревнование approve и reject. Первое завершенное решение становится окончательным; второе получает ошибку «Учетная запись уже обработана.».

### 2.8 Privacy сохраняется

Подробности решения — субъект, дата и основание — доступны только `system_owner` и `administrator`. Остальные роли видят общий статус.

### 2.9 Миграции не редактируются задним числом

Migration 003 остается неизменной. Новая схема и разрешение добавляются migration 004.

## 3. Риски и меры

| Риск | Мера |
|---|---|
| Подмена аудита подтверждения данными отклонения | Отдельные поля rejected-аудита |
| Повторная обработка пользователя | Проверка pending под row lock |
| Активация rejected-пользователя | `is_active = 0`, отсутствие block/unblock UI |
| Обход permission через прямой POST | `require_permission('security.users.reject')` |
| CSRF | Обязательный токен и HTTP 419 |
| HTML/скрипт в основании | Экранированный вывод, отсутствие HTML-интерпретации |
| Утечка причины оператору/viewer | Аудит только при `includeSensitive` |
| Потеря тестовых данных | Временные записи и cleanup в `finally` |
| Повреждение истории миграций | Только новая migration 004 |

## 4. Замечания к реализации

- Не логировать текст основания и персональные данные при исключениях.
- Не сохранять основание в session после успешной операции.
- При validation error допустимо вернуть введенное основание через однократное session-state карточки.
- После PRG состояние формы должно быть очищено после чтения.
- Фильтр rejected должен исключать архивированные записи.
- Сводный счетчик rejected также должен исключать архивированные записи.
- Существующий approve-сервис уже запрещает обработку не-pending записей; его поведение должно быть покрыто новым тестом.
- Новый permission должен иметь стабильный код и не дублироваться при повторном install.
