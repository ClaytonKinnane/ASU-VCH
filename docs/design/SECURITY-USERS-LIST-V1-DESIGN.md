# Security / Users List v1 — Design

Статус: **Draft for review**  
Домен: **Security**  
Связанная спецификация: `docs/specifications/SECURITY-USERS-MANAGEMENT-V1.md`  
Связанное решение: `docs/decisions/SECURITY-USERS-MANAGEMENT-V1-APPROVAL.md`

## 1. Назначение инкремента

Инкремент реализует первый рабочий экран Users Management v1.0: список учетных записей с поиском, фильтрацией, ролями и пагинацией.

В этот инкремент не входят создание, редактирование, блокировка, восстановление и назначение ролей. Для них будут подготовлены отдельные design/implementation этапы.

## 2. Маршрут

```text
GET /admin/users.php
```

Текущая обзорная страница раздела пользователей заменяется рабочим списком. Сводные показатели сохраняются над таблицей.

## 3. Авторизация

Для открытия страницы требуется разрешение:

```text
security.users.view
```

Роль `system_owner` получает доступ через `system.*.*`.

До реализации списка необходимо устранить ограничение текущего `current_user()`: запрос использует `LIMIT 1` и возвращает только одну роль, поэтому не поддерживает корректно несколько ролей пользователя.

Предлагаемая модель:

- `current_user()` возвращает только данные учетной записи;
- `current_user_role_codes()` возвращает все коды ролей;
- `current_user_permission_codes()` возвращает все разрешения ролей;
- `has_permission(string $permission)` проверяет точное разрешение или `system.*.*`;
- `require_permission(string $permission)` возвращает HTTP 403 при аутентифицированном пользователе без права и перенаправляет неаутентифицированного пользователя на `/`.

Проверка выполняется сервером до SQL-запроса списка.

## 4. Политика чувствительных данных

Email и дата последнего входа отображаются только пользователям, которые не ограничены ролью `viewer`.

Для v1 применяется утвержденная политика:

- пользователь, имеющий только роль `viewer`, не видит email и `last_login_at`;
- `system_owner`, `administrator` и пользователь с иной административной ролью видят эти поля;
- сокрытие выполняется сервером: значения не включаются в HTML;
- наличие дополнительной роли кроме `viewer` снимает ограничение только при наличии `security.users.view`.

В будущем политику можно заменить отдельным разрешением без изменения структуры страницы.

## 5. Параметры GET

```text
q=<строка поиска>
status=all|active|blocked|archived|temporary|password_change
page=<положительное целое>
```

Значения по умолчанию:

```text
q=
status=all
page=1
per_page=25
```

Неизвестный `status` нормализуется в `all`. Некорректный `page` нормализуется в `1`.

## 6. Поиск

Поиск выполняется без учета регистра по полям:

- `username`;
- `display_name`;
- `email`.

SQL использует один логический поисковый шаблон, но из-за нативных PDO prepared statements каждый placeholder имеет уникальное имя:

```text
:search_username
:search_display_name
:search_email
```

Поисковая строка:

- обрезается через `trim`;
- ограничивается 150 символами;
- экранируется только для HTML при выводе;
- передается в SQL через параметры;
- `%` и `_` в пользовательском вводе трактуются как обычные символы, поэтому должны экранироваться для `LIKE ... ESCAPE`.

## 7. Фильтры состояния

### active

```sql
u.is_active = 1 AND u.deleted_at IS NULL
```

### blocked

```sql
u.is_active = 0 AND u.deleted_at IS NULL
```

### archived

```sql
u.deleted_at IS NOT NULL
```

### temporary

```sql
u.is_temporary = 1 AND u.deleted_at IS NULL
```

### password_change

```sql
u.must_change_password = 1 AND u.deleted_at IS NULL
```

`temporary` и `password_change` являются дополнительными признаками и могут пересекаться с active/blocked. При выборе этих фильтров приоритет имеет соответствующий признак.

## 8. Запрос данных

Для каждой учетной записи возвращаются:

- `id`;
- `username`;
- `display_name`;
- `email` при разрешенной политике;
- `is_active`;
- `is_temporary`;
- `must_change_password`;
- `last_login_at` при разрешенной политике;
- `deleted_at`;
- список ролей.

Роли агрегируются детерминированно:

```sql
GROUP_CONCAT(DISTINCT r.name ORDER BY r.name SEPARATOR ', ')
```

Сортировка пользователей:

```text
system_owner сначала;
затем активные;
затем username_canonical ASC;
затем id ASC.
```

Признак владельца вычисляется через наличие роли `system_owner`, а не через поле в `users`.

## 9. Пагинация

Размер страницы фиксирован:

```text
25
```

Сначала выполняется `COUNT(DISTINCT u.id)` с теми же условиями поиска и фильтра. Затем вычисляются:

```text
total_pages = max(1, ceil(total / 25))
page = min(requested_page, total_pages)
offset = (page - 1) * 25
```

Ссылки пагинации сохраняют `q` и `status`.

Интерфейс показывает:

- текущую страницу;
- общее число страниц;
- «Назад»;
- «Вперед»;
- максимум пять соседних номеров страниц.

## 10. Представление desktop

Над таблицей:

- сводка: всего, активных, заблокированных, архивированных;
- строка поиска;
- select состояния;
- кнопка «Найти»;
- кнопка «Сбросить» при активных параметрах;
- неактивная или скрытая кнопка «Создать пользователя» до следующего инкремента.

Колонки таблицы:

1. Пользователь;
2. Логин;
3. Email — только по политике видимости;
4. Статус;
5. Роли;
6. Последний вход — только по политике видимости;
7. Действие.

Действие «Открыть» в этом инкременте отображается как неактивное с пометкой «Следующий этап» либо не выводится. Предпочтительный вариант: не выводить неработающую ссылку.

## 11. Представление mobile

При ширине до 760 px таблица преобразуется в список карточек.

Каждая карточка содержит:

- display name;
- username;
- статус;
- роли;
- email и последний вход только по политике;
- признаки временного пароля/обязательной смены пароля.

Горизонтальная прокрутка страницы не допускается.

## 12. Статусы и бейджи

Главный статус:

- `Архивирован` — если `deleted_at IS NOT NULL`;
- `Заблокирован` — если `is_active = 0`;
- `Активен` — иначе.

Дополнительные бейджи:

- `Временная` при `is_temporary = 1`;
- `Смена пароля` при `must_change_password = 1`;
- `Владелец` при роли `system_owner`.

## 13. Пустые состояния

Если пользователей нет:

```text
Пользователи пока не созданы.
```

Если поиск/фильтр не дал результатов:

```text
По заданным условиям пользователи не найдены.
```

Предлагается кнопка «Сбросить фильтры».

## 14. Ошибки

- Ошибка запроса БД не раскрывает SQL или реквизиты подключения.
- В development ошибка может быть передана в журнал/стандартный механизм диагностики, но не выводится напрямую в таблице.
- HTTP 403 отображает простую страницу отказа в стиле текущей темы.

## 15. Изменяемые файлы реализации

Планируется:

```text
app/bootstrap.php
public/admin/users.php
themes/asu-blue/assets/css/theme.css
```

Допускается выделение сервиса/репозитория:

```text
app/Security/AuthorizationService.php
app/Security/UserListRepository.php
```

Рекомендуется выделить классы, чтобы не раздувать `bootstrap.php` и страницу. При этом автозагрузка в проекте пока отсутствует, поэтому подключения должны быть явными.

## 16. Проверки

Автоматические/CLI:

- PHP syntax check;
- существующий `check-security-rbac.php`;
- smoke test;
- проверка запроса списка при 0, 1, 25, 26 и более пользователях;
- поиск по username/display_name/email;
- каждый status-фильтр;
- недопустимый `page` и `status`;
- отсутствие повторно используемых именованных PDO-параметров;
- отказ пользователю без `security.users.view`;
- `viewer` не получает email и `last_login_at` в HTML.

Ручные:

- desktop;
- узкий desktop/tablet;
- mobile;
- длинные логины, имена, email и названия ролей;
- пустой результат;
- пагинация с сохранением фильтров.

## 17. Критерии приемки

Инкремент принят, если:

1. владелец открывает `/admin/users.php`;
2. список содержит существующего `Admin`;
3. роли отображаются корректно;
4. поиск работает по трем утвержденным полям;
5. фильтры состояния работают;
6. пагинация использует 25 записей;
7. email и последний вход скрыты для viewer на сервере;
8. прямой запрос без разрешения получает отказ;
9. отсутствует горизонтальное переполнение на mobile;
10. PHP syntax, RBAC check и smoke test проходят;
11. существующая аутентификация владельца не нарушена.

## 18. Решения для Approval

Предлагается утвердить без изменений:

1. заменить обзорную страницу `/admin/users.php` непосредственно списком пользователей;
2. сохранить четыре сводных плитки, но показывать состояния пользователей вместо количества ролей/разрешений;
3. не показывать неработающие действия «Открыть» и «Создать» до соответствующих инкрементов;
4. использовать серверное сокрытие email и последнего входа для viewer;
5. выделить AuthorizationService и UserListRepository в отдельные классы;
6. вернуть HTTP 403 для аутентифицированного пользователя без права.
