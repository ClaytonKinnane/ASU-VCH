# Documents Domain

## Status

**Architecture:** APPROVED  
**Review:** APPROVED  
**Ready for ERD:** YES

## 1. Purpose

The Documents domain is responsible for registering, versioning, storing, retrieving, and relating documents and their physical file representations.

A document is a stable information object. A file is a physical representation of a specific document version.

```text
Document
 ├── DocumentVersion
 │    └── DocumentFile
 └── DocumentRelation
```

## 2. Responsibilities

The domain is responsible for:

- creating document records;
- storing document attributes;
- assigning and preserving registration numbers;
- classifying documents through Reference;
- controlling document lifecycle status;
- creating immutable document versions;
- attaching files to versions;
- validating file integrity;
- retrieving and downloading files;
- relating documents to other documents;
- publishing domain events after successful transactions.

The domain is not responsible for:

- order approval or execution;
- personnel decisions;
- medical conclusions;
- specialized business workflows;
- electronic signatures in version 1;
- OCR;
- antivirus implementation;
- document template generation;
- physical storage implementation details.

## 3. Owned Entities

The Documents domain owns:

- `documents`;
- `document_versions`;
- `document_files`;
- `document_relations`.

`Document` is the aggregate root.

`DocumentVersion`, `DocumentFile`, and `DocumentRelation` must not be modified outside operations coordinated by the aggregate.

## 4. Storage Abstraction

The domain uses a `StorageProvider` abstraction.

Minimum contract:

- `store()`;
- `read()`;
- `exists()`;
- `move()`;
- `deleteTemporary()`.

Version 1 uses `LocalFilesystemStorageProvider`.

The domain stores only a stable `storage_key`. It does not know absolute operating-system paths.

Example:

```text
documents/2026/07/01/8f/8f2c.../document.pdf
```

Storage rules:

- files are stored outside the Apache public directory;
- access is provided only through the application;
- original uploaded names are never used as physical paths;
- storage keys are generated by the system;
- changing the storage provider does not alter the domain model.

## 5. Document Aggregate

A document is a logical record with stable identity.

Conceptual attributes:

- `id`;
- `public_id`;
- `document_type_id`;
- `status_id`;
- `registration_number`;
- `title`;
- `description`;
- `document_date`;
- `registered_at`;
- `current_version_id`;
- `created_by_user_id`;
- `created_at`;
- `updated_at`;
- `deleted_at`.

Rules:

- `id` is the internal technical identifier;
- `public_id` is a stable non-sequential identifier for integrations and external references;
- type and status use Reference values;
- a draft may exist without a version or file;
- `registration_number` may be `NULL` only while the document is a draft;
- registration number becomes immutable after registration;
- registered numbers are never reused, including after cancellation or soft deletion;
- documents use soft delete only where explicitly allowed by lifecycle rules;
- registered, approved, cancelled, and archived documents are never deleted.

## 6. Registration Number

`registration_number` is separate from the primary key.

Rules:

- optional for `draft`;
- mandatory for `registered`, `approved`, `cancelled`, and `archived` documents that were registered;
- normalized by trimming leading and trailing whitespace;
- immutable after registration;
- not automatically generated without an approved numbering policy;
- unique by `(document_type_id, registration_number)` across all historical records, including soft-deleted drafts that reached registration.

## 7. Document Status

Reference group:

```text
document_status
```

Initial values:

- `draft`;
- `registered`;
- `approved`;
- `cancelled`;
- `archived`.

Normal lifecycle:

```text
draft -> registered -> approved -> archived
```

Allowed cancellation transitions:

```text
draft -> cancelled
registered -> cancelled
approved -> cancelled
```

Forbidden reverse transitions include:

- `registered -> draft`;
- `approved -> registered`;
- `archived -> approved`.

Corrections are represented by a new version or a related replacement document, not by rewriting historical state.

## 8. Document Types

Reference group:

```text
document_type
```

Initial neutral values:

- `order`;
- `act`;
- `memo`;
- `instruction`;
- `certificate`;
- `report`;
- `statement`;
- `other`.

Machine codes are lowercase, immutable, and unique within the group.

Business meaning remains in the owning business domain. A type code does not transfer ownership of order, medical, equipment, or other business logic to Documents.

## 9. Document Version

Every material content change creates a new version.

Conceptual attributes:

- `id`;
- `document_id`;
- `version_number`;
- `change_summary`;
- `created_by_user_id`;
- `created_at`.

Rules:

- each version belongs to exactly one document;
- numbering begins at `1`;
- version numbers increase sequentially;
- `(document_id, version_number)` is unique;
- versions are immutable after creation;
- versions of registered documents cannot be deleted;
- the current version is identified by `documents.current_version_id`;
- `current_version_id`, when set, must reference a version belonging to the same document;
- creating a new version uses a transaction and locks the document row to prevent duplicate version numbers.

A version becomes complete only when it has exactly one primary file. Draft preparation may temporarily contain no primary file inside an uncommitted operation, but persisted completed versions must satisfy the invariant.

## 10. Document File

A file is a physical representation of one document version.

Conceptual attributes:

- `id`;
- `document_version_id`;
- `original_filename`;
- `storage_key`;
- `mime_type`;
- `size_bytes`;
- `sha256_hash`;
- `file_role`;
- `created_at`.

Rules:

- each file belongs to one version;
- `storage_key` is globally unique;
- SHA-256 is mandatory and immutable;
- file size is mandatory;
- MIME type is detected by the server;
- client-provided MIME type and extension are not trusted;
- original filename is metadata only;
- file contents are immutable after persistence;
- replacement creates a new file record and, where content changes, a new version;
- identical hashes do not automatically merge records.

Version 1 file roles:

- `primary`;
- `attachment`.

Exactly one active `primary` file is allowed per completed version. Multiple attachments are allowed.

## 11. File Integrity

SHA-256 is calculated before permanent persistence and is used for:

- corruption detection;
- transfer validation;
- integrity checks;
- duplicate-content detection;
- evidence that stored content has not changed.

The hash is not a business identifier and does not imply deduplication.

## 12. Secure Upload

Mandatory implementation rules:

- maximum file size is configuration-driven;
- allowed MIME types are configuration-driven;
- executable uploads are prohibited;
- extension and client `Content-Type` are untrusted;
- original names are sanitized for display;
- storage paths are never constructed from original names;
- uploads first enter temporary storage;
- validation and SHA-256 calculation happen before permanent persistence;
- database failure must not leave an unmanaged permanent file;
- storage failure must not leave an active database record;
- files are served only after authorization checks.

Antivirus scanning is an infrastructure extension outside version 1.

## 13. Cross-Resource Transaction Strategy

MySQL and the filesystem do not provide one atomic transaction. The required workflow is:

1. receive the upload into temporary storage;
2. validate size and MIME type;
3. calculate SHA-256;
4. begin the database transaction;
5. create document/version/file metadata;
6. move the temporary file to its permanent storage key;
7. commit the database transaction;
8. publish domain events after commit.

Failure rules:

- if validation fails, delete the temporary file;
- if the permanent move fails, roll back the database transaction;
- if commit fails after the move, delete the moved file as a compensation action;
- compensation failures must be logged technically and queued for orphan cleanup;
- a scheduled integrity process may identify orphaned files and missing objects without modifying business history automatically.

## 14. Document Relations

Relations are directed links between documents.

Conceptual attributes:

- `id`;
- `source_document_id`;
- `target_document_id`;
- `relation_type_id`;
- `created_by_user_id`;
- `created_at`.

Reference group:

```text
document_relation_type
```

Initial values:

- `supplements`;
- `replaces`;
- `cancels`;
- `references`;
- `attachment_to`;
- `based_on`.

Rules:

- a document cannot relate to itself;
- relations are directed;
- reverse relations are not created automatically;
- duplicate `(source_document_id, target_document_id, relation_type_id)` rows are forbidden;
- both documents must exist;
- cascading deletion is forbidden;
- historical relations remain available when documents are cancelled or archived.

## 15. Integration with Business Domains

Documents does not use polymorphic ownership columns such as `owner_type` and `owner_id`.

The business domain owns its relationship to a document, for example:

```text
orders.document_id
medical_records.document_id
equipment_issues.act_document_id
```

Documents does not know which business aggregate references it.

## 16. User References

Fields such as `created_by_user_id` are integration identifiers and may use physical foreign keys to `users(id)` with `RESTRICT` semantics.

Documents must not call Security domain services or implement Security business rules.

## 17. Domain Events

Initial events:

- `DocumentCreated`;
- `DocumentRegistered`;
- `DocumentApproved`;
- `DocumentCancelled`;
- `DocumentArchived`;
- `DocumentVersionCreated`;
- `DocumentFileAdded`;
- `DocumentRelationCreated`.

Events are published only after successful commit through the infrastructure event mechanism. Documents does not call Audit directly.

## 18. Services

Domain/application services:

- `DocumentService`;
- `DocumentVersionService`;
- `DocumentRelationService`;
- `DocumentQueryService`.

Infrastructure interfaces:

- `StorageProvider`;
- `FileIntegrityService`;
- `MimeTypeDetector`.

## 19. Repositories

- `DocumentRepository`;
- `DocumentVersionRepository`;
- `DocumentFileRepository`;
- `DocumentRelationRepository`.

Separate repositories may be used technically, but mutations of child entities remain coordinated through the Document aggregate.

## 20. Dependencies

Allowed:

- Reference;
- Infrastructure.

External user identifiers are permitted as integration references.

Forbidden direct domain dependencies:

- Security;
- Organization;
- Audit;
- Orders;
- Medical;
- Equipment;
- Transport.

## 21. Version 1 Boundaries

Excluded from version 1:

- digital signatures;
- OCR;
- full-text content search;
- collaborative editing;
- approval workflows;
- templates;
- automatic PDF generation;
- external object storage implementations;
- public links;
- temporary external sharing;
- retention policies;
- physical destruction workflows.

## 22. Architecture Completion Criteria

- Document is the aggregate root.
- Document and File are separate concepts.
- Versions and persisted files are immutable.
- StorageProvider isolates physical storage.
- Registration numbers are immutable and never reused.
- Types, statuses, and relation types use Reference.
- Relations are directed.
- Business domains own references to documents.
- Documents has no direct dependency on Audit.
- Secure upload and compensation rules are defined.
- SHA-256 is mandatory.
- Version 1 boundaries are explicit.
