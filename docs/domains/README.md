# Предметные области АСУ-ВЧ

## 1. Назначение

Каталог `docs/domains` содержит спецификации предметных областей АСУ-ВЧ.

Документы доменов определяют:

- назначение и границы ответственности;
- принадлежащие домену сущности и бизнес-правила;
- допустимые и запрещённые зависимости;
- основные сценарии использования;
- доменные события;
- требования к аудиту, безопасности и тестированию.

Документы доменов не заменяют:

- `docs/ARCHITECTURE.md` — общесистемные архитектурные принципы;
- `docs/DATABASE.md` — структуру хранения данных и ограничения БД;
- `docs/ACCESS.md` — общую модель доступа;
- ADR — обоснования архитектурных решений;
- ERD — визуальное представление связей между сущностями.

## 2. Текущая фаза проекта

Проект находится в фазе **Domain Modeling**.

```text
Architecture        — завершена
Domain Modeling     — текущая
Implementation      — не начата
Evolution           — после первой поставки
```

Изменение фундаментальных принципов после завершения архитектурной фазы допускается только через новое ADR с анализом влияния.

## 3. Правила выделения доменов

Каждая новая функция сначала должна получить ответ на вопрос:

> К какой предметной области относится эта ответственность?

Домен должен:

- иметь чётко сформулированную бизнес-ответственность;
- владеть своими сущностями и правилами;
- предоставлять другим доменам публичные сервисы или события;
- скрывать внутренние репозитории и детали хранения;
- не создавать циклические зависимости;
- не дублировать бизнес-логику другого домена.

Домен не имеет права напрямую изменять таблицы, принадлежащие другому домену.

## 4. Карта доменов

### 4.1 Текущие домены

| Домен | Назначение | Статус спецификации |
|---|---|---|
| Security | Пользователи, аутентификация, авторизация и RBAC | В работе |
| Reference | Универсальные справочники и классификаторы | Запланирована |
| Organization | Воинские части, подразделения, должности, звания и военнослужащие | Запланирована |
| Audit | Неизменяемый журнал значимых действий и результатов операций | Запланирована |
| Infrastructure | Технические механизмы приложения и интеграция с окружением | Запланирована |

### 4.2 Будущие домены

```text
Documents
Orders
Medical
Equipment
Transport
Training
Archive
Notifications
```

Появление нового домена должно сопровождаться:

1. обновлением этой карты;
2. отдельной спецификацией домена;
3. при необходимости — ADR;
4. ER-диаграммой;
5. обновлением `DATABASE.md` до создания миграций.

## 5. Допустимые зависимости

Базовые направления зависимостей:

```text
Security       → Audit
Security       → Reference
Organization   → Reference
Organization   → Audit
Audit          → Infrastructure
Infrastructure → внешние технические системы
```

`Reference` не должен зависеть от прикладных доменов.

`Security` не должен зависеть от `Organization` для выполнения аутентификации и авторизации. Связь пользователя с военнослужащим является необязательной интеграцией данных, а не условием работы подсистемы безопасности.

## 6. Правила взаимодействия

Домен может:

- вызывать публичный прикладной сервис другого домена;
- использовать опубликованный контракт или DTO;
- читать утверждённые справочные значения;
- публиковать доменные события;
- передавать сведения в аудит.

Домен не может:

- обращаться к внутреннему репозиторию другого домена;
- изменять чужие таблицы напрямую;
- использовать внутренние классы другого домена как часть публичного контракта;
- создавать скрытую двустороннюю зависимость;
- копировать чужие правила в свой код.

## 7. Структура спецификации домена

Каждая спецификация должна содержать как минимум:

1. назначение;
2. границы ответственности;
3. термины;
4. сущности и агрегаты;
5. бизнес-правила и инварианты;
6. сценарии использования;
7. разрешения;
8. доменные события;
9. зависимости и интеграции;
10. аудит;
11. ошибки;
12. нефункциональные требования;
13. требования к тестированию;
14. открытые вопросы;
15. критерии готовности к реализации.

## 8. Порядок проектирования домена

```text
Domain Specification
        ↓
Review
        ↓
Approval
        ↓
ERD
        ↓
API/UI Specification
        ↓
Migrations
        ↓
Repository and Service
        ↓
Tests
        ↓
Controller and Frontend
```

Миграции и программная реализация не начинаются до утверждения спецификации и ERD соответствующего домена.
