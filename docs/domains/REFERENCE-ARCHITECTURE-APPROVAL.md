# Утверждение архитектуры домена Reference

## 1. Статус

```text
APPROVED
```

Архитектура домена `Reference` утверждена и считается завершённой для версии v1.

Документ является формальной точкой заморозки архитектурных решений домена. Реализация, миграции, seeders, тесты и интеграции других доменов должны соответствовать утверждённым артефактам.

## 2. Основания для утверждения

Утверждение выполнено на основании следующих документов:

- `docs/DATABASE.md`;
- `docs/NAMING.md`;
- `docs/domains/REFERENCE.md`;
- `docs/domains/REFERENCE-REVIEW.md`;
- `docs/erd/ERD-030-reference.md`;
- `docs/erd/ERD-030-reference-review.md`;
- `docs/erd/diagrams/reference.puml`;
- `docs/migrations/REFERENCE-MIGRATIONS.md`;
- ADR по справочным данным, soft delete, доменно-ориентированной архитектуре и архитектуре как источнику истины.

Противоречий между перечисленными документами, блокирующих реализацию, не выявлено.

## 3. Утверждённые границы домена

Домен `Reference` отвечает за:

- группы справочных данных;
- значения справочных данных;
- стабильные машинные коды;
- получение значений по идентификатору и коду;
- упорядочивание значений;
- необязательное значение по умолчанию;
- защиту системных групп и значений;
- soft delete и восстановление;
- идемпотентную инициализацию системных справочников;
- публикацию справочных данных для других доменов.

Домен не отвечает за:

- пользователей и авторизацию;
- военнослужащих и организационную структуру;
- бизнес-процессы доменов-потребителей;
- вычисления и workflow;
- хранение произвольных JSON-атрибутов;
- локализацию, версии и иерархию справочников в v1.

## 4. Утверждённая модель данных

В состав домена входят две таблицы:

```text
reference_groups
reference_values
```

Связь:

```text
reference_groups 1 ─────< reference_values
```

Каждое значение принадлежит ровно одной группе. Группа может существовать без значений.

Другие домены хранят внешние ключи только на:

```text
reference_values.id
```

Использование `reference_values.code` вместо внешнего ключа запрещено.

## 5. Утверждённые инварианты

### 5.1 Коды

- `reference_groups.code` уникален глобально;
- `reference_values.code` уникален внутри группы;
- коды нормализуются до нижнего регистра и обрезаются по краям;
- код является стабильным машинным контрактом;
- опубликованный код не изменяется;
- код не переиспользуется после soft delete.

### 5.2 Значение по умолчанию

- группа может не иметь default-значения;
- группа может иметь не более одного активного значения с `is_default = true`;
- удалённое значение не участвует в ограничении;
- смена default-значения выполняется транзакционно;
- default-значение не применяется автоматически потребляющими доменами без их собственного правила.

Ограничение обеспечивается generated column:

```text
active_default_group_id
```

и уникальным индексом по этой колонке.

### 5.3 Системные данные

- `is_system = true` обозначает часть системного контракта;
- системные записи не изменяются через обычные административные операции;
- системные записи нельзя удалить;
- системное значение нельзя перенести в другую группу;
- флаг `is_system` не заменяет RBAC и доменную политику;
- системные данные создаются и изменяются управляемыми миграциями и seeders.

### 5.4 Удаление

- обе таблицы используют soft delete;
- физическое удаление опубликованных записей запрещено;
- каскадное удаление запрещено;
- внешние ключи используют `ON DELETE RESTRICT` и `ON UPDATE RESTRICT`;
- группу нельзя удалить при наличии активных значений;
- значение нельзя удалить, если оно используется доменом-потребителем;
- восстановление допускается только после проверки уникальности и остальных инвариантов.

## 6. Утверждённый физический контракт

Для MySQL 8.4 утверждены:

- InnoDB;
- `utf8mb4`;
- единая collation проекта;
- `BIGINT UNSIGNED AUTO_INCREMENT` для первичных ключей;
- `DATETIME(6)` для временных полей;
- `BOOLEAN` как `TINYINT(1)`;
- отсутствие MySQL `ENUM`;
- именованные PK, FK, UQ, CHECK и обычные индексы;
- `STORED` generated column `active_default_group_id`;
- отдельные структурные миграции и seeders;
- идемпотентность seeders по неизменяемым кодам.

Точная реализация должна соответствовать `docs/migrations/REFERENCE-MIGRATIONS.md`.

## 7. Утверждённые начальные данные

Системная группа:

```text
user_status
```

Системные значения:

```text
pending
active
blocked
disabled
```

Default-значение группы:

```text
pending
```

Повторный запуск seeder не должен создавать дубликаты, менять идентификаторы существующих записей или нарушать опубликованные ссылки.

## 8. Зависимости

Домен `Reference` не зависит от бизнес-доменов.

Разрешённые зависимости:

```text
Reference → Infrastructure
```

Основное направление зависимостей системы:

```text
Security      → Reference
Organization  → Reference
Personnel     → Reference
Documents     → Reference
Medical       → Reference
Equipment     → Reference
Transport     → Reference
Orders        → Reference
```

Обратная зависимость `Reference` от перечисленных доменов запрещена.

## 9. Условия реализации

Реализация разрешена после настоящего утверждения.

Перед слиянием реализации обязательны:

- миграции согласно утверждённому порядку;
- идемпотентный seeder;
- доменные сервисы и репозитории в границах `src/Domain/Reference`;
- проверка нормализации кодов;
- проверка защиты системных данных;
- проверка soft delete и восстановления;
- проверка уникальности кодов;
- проверка единственного активного default-значения;
- проверка `RESTRICT`-связей;
- интеграционные тесты MySQL 8.4;
- аудит административных изменений справочников;
- отсутствие запрещённых зависимостей на другие домены.

## 10. Критерии приёмки реализации

Реализация домена принимается только при выполнении всех условий:

1. структура БД совпадает со спецификацией миграций;
2. имена ограничений и индексов совпадают с документацией;
3. seed выполняется повторно без дубликатов;
4. два одинаковых кода значения допустимы в разных группах;
5. два одинаковых кода значения запрещены в одной группе;
6. повторное использование удалённого кода запрещено;
7. второй активный default в группе запрещён на уровне БД;
8. после soft delete default-значения разрешено назначить новое;
9. системные записи защищены доменной политикой и RBAC;
10. потребители используют `reference_values.id`;
11. внешние ключи не используют cascade;
12. все обязательные интеграционные тесты проходят.

## 11. Управление изменениями

После утверждения изменения архитектуры домена выполняются только по процессу:

```text
Architecture change proposal
↓
Documentation update
↓
Review
↓
Approval
↓
Implementation
↓
Testing
```

Запрещено изменять модель данных непосредственно в коде или миграции без предварительного изменения архитектурных документов.

Изменения, требующие повторного архитектурного утверждения:

- добавление или удаление таблиц;
- изменение идентичности справочного значения;
- изменение политики уникальности кодов;
- изменение правил soft delete;
- изменение модели default-значений;
- добавление иерархии, локализации, версий или metadata;
- изменение направления доменных зависимостей;
- изменение контракта ссылок для доменов-потребителей.

## 12. Отложенные возможности

За пределами v1 остаются:

```text
reference_value_translations
reference_versions
reference_imports
reference_exports
reference_hierarchies
reference_metadata
```

Их отсутствие не блокирует реализацию текущего домена.

Добавление любой из этих возможностей требует отдельной спецификации и архитектурного ревью.
