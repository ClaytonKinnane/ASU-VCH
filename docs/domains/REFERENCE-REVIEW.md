# Архитектурное ревью домена Reference

## 1. Статус

Статус: `APPROVED`

Ревью выполнено для документа:

```text
docs/domains/REFERENCE.md
```

Цель ревью — проверить границы домена, непротиворечивость бизнес-правил, пригодность модели для ERD и отсутствие преждевременного усложнения.

## 2. Итог

Архитектура домена `Reference` одобрена для перехода к проектированию ERD.

Базовая модель из двух сущностей признана достаточной для первой версии:

```text
reference_groups
reference_values
```

Дополнительные универсальные таблицы, JSON-метаданные и иерархическая модель на данном этапе не требуются.

## 3. Проверка границ домена

Границы определены корректно.

`Reference`:

- владеет справочными группами и значениями;
- предоставляет lookup-контракты другим доменам;
- не содержит бизнес-логику потребителей;
- не зависит от `Security`, `Organization` и других прикладных доменов;
- публикует события через абстракцию Audit.

Нарушений принятого направления зависимостей не выявлено.

## 4. Принятые решения

### 4.1 Универсальная модель

Для первой версии утверждена универсальная структура:

```text
reference_groups 1 ─── * reference_values
```

Специализированные таблицы справочников создаются только тогда, когда соответствующий объект имеет собственную бизнес-логику и перестает быть простым справочным значением.

### 4.2 Внешние ссылки

Домены-потребители ссылаются на:

```text
reference_values.id
```

Ссылки по `code` запрещены на уровне внешних ключей.

`code` остается стабильным машинным контрактом для поиска, конфигурации и seed-данных.

### 4.3 Уникальность кодов

Утверждено:

```text
reference_groups.code — глобально уникален
reference_values(group_id, code) — уникален внутри группы
```

Коды не переиспользуются после soft delete.

### 4.4 Значение по умолчанию

В группе допускается не более одного активного значения по умолчанию.

Для физической модели необходимо выбрать надежный способ обеспечения этого инварианта в MySQL 8.4.

Предпочтительный кандидат:

```text
default_group_id = IF(deleted_at IS NULL AND is_default = 1, group_id, NULL)
UNIQUE (default_group_id)
```

Точное выражение, тип generated column и имя индекса фиксируются в ERD review и migration specification после технической проверки.

### 4.5 Soft delete

Soft delete применяется к обеим сущностям.

Поскольку коды не переиспользуются, уникальные ограничения должны быть глобальными и не включать `deleted_at` как способ разрешить повторное использование кода.

### 4.6 Системные записи

`is_system` является признаком защиты, а не механизмом авторизации.

Запрет изменения и удаления системных данных обеспечивается:

- доменными сервисами;
- разрешениями Security;
- аудитом попыток нарушения;
- ограниченным системным процессом для seed-обновлений.

DB-триггеры для запрета изменения `is_system` на данном этапе не требуются.

### 4.7 Неизменяемость code

Неизменяемость опубликованных кодов является доменным инвариантом.

Для первой версии она обеспечивается прикладным сервисом и тестами.

Введение DB-триггеров допускается только при выявленной необходимости дополнительной защиты от прямых SQL-изменений.

### 4.8 Удаление используемых значений

Внешние ключи доменов-потребителей должны использовать:

```text
ON DELETE RESTRICT
ON UPDATE RESTRICT
```

Soft delete значения также должен блокироваться доменным сервисом, если значение продолжает использоваться активными бизнес-записями и его сокрытие нарушит работу системы.

Поскольку `Reference` не должен зависеть от потребителей, проверка использования выполняется через отдельные контракты/policies на прикладном уровне либо определяется правилами конкретного домена-потребителя.

### 4.9 Audit

Reference публикует события, но не содержит реализацию Audit.

До появления домена Audit допускается инфраструктурная заглушка/dispatcher при условии сохранения публичного контракта событий.

## 5. Замечания к будущей физической модели

ERD и спецификация миграций должны явно определить:

1. точные SQL-типы и длины строк;
2. collation и нормализацию кодов;
3. имена PK, FK, UQ и индексов;
4. способ обеспечения одного default-значения на группу;
5. обязательность и default для `sort_order`;
6. FK `reference_values.group_id`;
7. правила `RESTRICT`;
8. индексы lookup-операций;
9. seed-стратегию для системных справочников;
10. rollback и тесты ограничений.

## 6. Риски и предотвращение

### Риск: превращение Reference в универсальное хранилище

Предотвращение:

- отсутствие JSON/metadata в первой версии;
- запрет прикладных вычислений;
- архитектурное ревью перед расширением модели.

### Риск: хранение бизнес-сущностей как справочных значений

Предотвращение:

Объект должен быть вынесен в отдельную доменную сущность, если у него появляются:

- собственный жизненный цикл;
- сложные связи;
- история состояний;
- операции и правила;
- значимый набор атрибутов.

### Риск: изменение code ломает интеграции

Предотвращение:

- code неизменяем;
- опубликованные коды считаются системным контрактом;
- замена выполняется созданием нового значения.

### Риск: несколько default-значений

Предотвращение:

- доменная транзакция;
- DB unique constraint через generated column;
- конкурентный интеграционный тест.

## 7. Отложенные возможности

Подтверждено, что в первую версию не входят:

- `parent_id` и деревья;
- произвольные атрибуты;
- локализация отдельными таблицами;
- версии и периоды действия;
- импорт через UI;
- внешняя синхронизация.

Их отсутствие не является архитектурным долгом без подтвержденной потребности.

## 8. Решение ревью

Документ `REFERENCE.md` утвержден.

Следующий артефакт:

```text
docs/erd/ERD-030-reference.md
```

Нумерация `030` соответствует принятой карте ERD:

```text
ERD-010-security
ERD-020-organization
ERD-030-reference
ERD-040-audit
```

ERD должен содержать логическую и физически значимую структуру двух таблиц, связи, ограничения и список вопросов для migration design review.
