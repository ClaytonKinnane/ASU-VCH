# Архитектурное ревью домена Security

## 1. Статус

Архитектурное ревью базовых решений домена `Security` проведено и одобрено.

Этот документ дополняет `SECURITY.md` и фиксирует решения по вопросам, которые не должны определяться неявно в миграциях или программном коде.

## 2. Жизненный цикл пользователя

Утверждены состояния учетной записи:

```text
pending
active
blocked
disabled
```

Семантика состояний:

- `pending` — учетная запись создана, но еще не активирована;
- `active` — учетная запись допущена к интерактивному входу и работе в системе;
- `blocked` — учетная запись временно заблокирована и может быть разблокирована;
- `disabled` — учетная запись выведена из эксплуатации и не используется для интерактивного доступа.

Статусы хранятся через домен `Reference` по неизменяемым кодам. MySQL `ENUM` не используется.

Только активный и логически не удаленный пользователь может пройти интерактивную аутентификацию.

## 3. Регистрация пользователей

Самостоятельная публичная регистрация обычных пользователей запрещена.

Обычная учетная запись создается только административным сценарием пользователем с соответствующим разрешением либо владельцем системы.

Утвержденный поток:

```text
Администратор
    ↓
создание учетной записи
    ↓
назначение ролей
    ↓
активация пользователя
    ↓
доступ к системе
```

Первоначальная регистрация владельца допускается только в контролируемом состоянии первичной инициализации, когда активный владелец отсутствует. После завершения инициализации этот сценарий недоступен.

## 4. Парольная политика

На архитектурном уровне утверждены следующие обязательные правила:

- пароль хранится исключительно в виде стойкого хеша;
- открытый пароль, его производные и секреты восстановления не журналируются;
- временный пароль, если он используется при административном создании пользователя, должен быть заменен при первом успешном входе;
- администратор может инициировать принудительный сброс, но не получает доступ к текущему паролю;
- после смены или административного сброса обновляется `password_changed_at`;
- конкретные требования к длине, проверке распространенных паролей и параметрам хеширования фиксируются отдельной спецификацией безопасности до реализации форм и API;
- изменение минимальных криптографических требований в сторону ослабления допускается только через ADR.

## 5. Аутентификация и сессии

Аутентификация и сессия рассматриваются как разные понятия.

`Security` принимает решение о подлинности и допустимости доступа пользователя. `Infrastructure` предоставляет техническое хранение и инвалидацию HTTP-сессий.

Архитектура должна поддерживать:

- завершение текущей сессии;
- завершение всех активных сессий пользователя;
- принудительный выход после блокировки или отключения;
- отзыв остальных сессий после смены или административного сброса пароля;
- различение активных сессий, необходимое для аудита и будущего управления устройствами;
- защиту от фиксации сессии и регенерацию идентификатора после входа.

Точная продолжительность сессии и тайм-аут бездействия будут определены в спецификации инфраструктуры до реализации.

## 6. Многофакторная аутентификация

MFA не является обязательной функцией первой версии.

При этом модель `users` и публичные контракты Security не должны препятствовать последующему подключению факторов аутентификации, включая:

```text
TOTP
аппаратные ключи
одноразовые коды
```

Данные MFA в будущем должны храниться в отдельных сущностях, а не в виде набора специализированных колонок таблицы `users`.

## 7. Начальные роли

Утвержден минимальный начальный каталог ролей:

```text
system_owner
administrator
operator
viewer
```

Правила:

- `system_owner` — системная роль единственного владельца системы;
- `administrator` — управление пользователями, ролями и настройками в пределах выданных разрешений;
- `operator` — выполнение рабочих операций предметных доменов без управления моделью безопасности;
- `viewer` — доступ только на чтение в пределах назначенных разрешений.

Роль не является должностью военнослужащего и не заменяет сущность `positions`.

Точный набор разрешений каждой роли фиксируется перед созданием сидеров и может расширяться по мере утверждения предметных доменов.

## 8. Авторизация

Утвержден единый алгоритм авторизации:

```text
User
    ↓
Active role assignments
    ↓
Roles
    ↓
Permissions
    ↓
Authorization decision
```

Обязательные правила:

- разрешения предоставляются пользователю только через роли;
- прямые назначения разрешений пользователю в текущей модели отсутствуют;
- решение принимается серверным сервисом авторизации;
- контроллеры, UI и клиентский JavaScript не принимают окончательное решение о доступе;
- неизвестное разрешение и отсутствие данных трактуются как `deny`;
- проверка выполняется по неизменяемому коду разрешения;
- для `system_owner` допускается контролируемое короткое замыкание, которое не отменяет CSRF, валидацию, бизнес-инварианты, транзакции и аудит.

## 9. Аудит

Обязательному аудиту подлежат:

- создание, активация, блокировка, разблокировка, отключение и логическое удаление пользователя;
- успешные и неуспешные попытки входа;
- выход и принудительное завершение сессий;
- смена и административный сброс пароля;
- назначение и отзыв ролей;
- изменение разрешений роли;
- попытки недопустимого изменения системных ролей и разрешений;
- передача роли `system_owner`;
- значимые отказы авторизации при административных операциях.

Журнал не содержит паролей, хешей паролей, полных токенов, секретов восстановления и избыточных персональных данных.

## 10. Разделение ответственности

Утверждено следующее разделение:

- `Security` владеет правилами учетных записей, аутентификации, авторизации и RBAC;
- `Reference` хранит статусы и классификаторы по неизменяемым кодам;
- `Audit` хранит неизменяемый журнал событий и результатов;
- `Infrastructure` предоставляет сессии, cookies, CSRF, rate limiting, временные токены и криптографическую конфигурацию;
- `Organization` предоставляет необязательную связь пользователя с военнослужащим, но не является условием аутентификации и авторизации.

## 11. Решения, отложенные до детальной спецификации

Следующие вопросы не изменяют утвержденную архитектуру, но должны быть закрыты до соответствующей реализации:

1. физическая структура внешнего ключа статуса пользователя на `reference_values`;
2. точная минимальная парольная политика;
3. продолжительность сессии и тайм-аут бездействия;
4. канал и сценарий восстановления доступа;
5. точная семантика административного сброса пароля;
6. политика временной блокировки после неудачных входов;
7. поведение критических команд при недоступности Audit;
8. точный каталог разрешений начальных ролей;
9. необходимость хранения истории предыдущих паролей.

Эти решения должны быть отражены в профильной спецификации, ADR или ERD до создания соответствующих миграций и кода.

## 12. Результат ревью

Базовая архитектура домена `Security` одобрена.

Следующий допустимый этап:

```text
Security ERD
    ↓
API/UI Specification
    ↓
Migrations
```

Начало миграций до утверждения ERD запрещено.
