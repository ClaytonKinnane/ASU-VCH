# Домен Security

## 1. Назначение

Домен `Security` отвечает за управление учетными записями, аутентификацию, авторизацию и ролевое разграничение доступа в АСУ-ВЧ.

Домен должен обеспечивать:

- безопасное создание и обслуживание учетных записей;
- проверку подлинности пользователя;
- управление жизненным циклом учетной записи;
- назначение и отзыв ролей;
- выдачу разрешений через роли;
- проверку прав доступа;
- защиту системной роли владельца;
- формирование событий для аудита.

## 2. Границы ответственности

### 2.1 Входит в домен

```text
users
roles
permissions
user_roles
role_permissions
```

К ответственности домена относятся:

- регистрация учетной записи;
- активация, блокировка и отключение пользователя;
- вход и выход;
- проверка пароля;
- смена пароля;
- фиксация времени последнего успешного входа;
- назначение и отзыв ролей;
- управление разрешениями ролей;
- вычисление эффективных разрешений пользователя;
- передача роли `system_owner` другому активному пользователю;
- защита системных ролей и разрешений от недопустимых изменений.

### 2.2 Не входит в домен

Домен не отвечает за:

- кадровый учет военнослужащих;
- организационную структуру;
- медицинские, служебные и иные предметные данные;
- хранение полного журнала аудита;
- отправку уведомлений;
- управление HTTP-сессиями как техническим хранилищем;
- восстановление пароля через конкретный канал доставки;
- интерфейс пользователя.

Связь `users.soldier_id` является необязательной интеграцией с кадровой моделью. Аутентификация и авторизация должны работать для технических пользователей без связанного военнослужащего.

## 3. Термины

**Пользователь** — учетная запись, через которую субъект получает доступ к системе.

**Роль** — именованный набор полномочий, назначаемый пользователю.

**Разрешение** — атомарное право на действие над ресурсом.

**Системная роль** — роль, созданная системой и защищенная от удаления или изменения критических свойств.

**Владелец системы** — единственный активный пользователь с ролью `system_owner`.

**Эффективные разрешения** — объединение разрешений всех действующих ролей пользователя с учетом специальных правил владельца системы.

**Действующее назначение роли** — запись `user_roles`, у которой `revoked_at IS NULL`.

## 4. Сущности и отношения

### 4.1 users

```text
id
soldier_id
username
email
password_hash
status
last_login_at
password_changed_at
created_at
updated_at
deleted_at
```

Основные правила:

- `username` уникален среди неудаленных учетных записей;
- `email` при наличии уникален среди неудаленных учетных записей;
- `soldier_id` nullable и unique;
- пароль хранится только как стойкий хеш;
- удаление выполняется логически;
- удаленная учетная запись не может пройти аутентификацию;
- статус сравнивается по неизменяемому коду, а не по отображаемому названию.

Предварительный набор статусов:

```text
pending
active
blocked
disabled
```

Значения статусов должны храниться в подсистеме справочных данных. MySQL `ENUM` не используется.

### 4.2 roles

```text
id
code
name
description
is_system
created_at
updated_at
deleted_at
```

Основные правила:

- `code` уникален и неизменяем после создания;
- системная роль не может быть физически удалена;
- системные свойства роли изменяются только контролируемой системной операцией;
- удаленная роль не учитывается при авторизации;
- роль `system_owner` создается миграцией и имеет `is_system = true`.

### 4.3 permissions

```text
id
code
name
description
module
is_system
created_at
updated_at
```

Формат кода:

```text
module.resource.action
```

Примеры:

```text
users.view
users.create
users.update
roles.assign
permissions.manage
audit.view
```

Основные правила:

- `code` уникален и неизменяем;
- системные разрешения создаются миграциями или сидерами;
- разрешение не удаляется, если это разрушает действующий системный контракт;
- прикладной код сравнивает разрешения по `code`.

### 4.4 user_roles

```text
id
user_id
role_id
assigned_by
assigned_at
revoked_at
```

Основные правила:

- история назначений сохраняется;
- отзыв выполняется заполнением `revoked_at`;
- одновременно допускается только одно действующее назначение одной роли одному пользователю;
- `assigned_by` указывает пользователя, выполнившего операцию, либо специальное системное значение, определенное реализацией;
- назначение и отзыв выполняются транзакционно и аудируются.

### 4.5 role_permissions

```text
role_id
permission_id
```

Первичный ключ:

```text
role_id + permission_id
```

Основные правила:

- surrogate `id` не используется;
- одна связь роли и разрешения существует не более одного раза;
- изменение набора разрешений системной роли требует специальных полномочий;
- изменение разрешений `system_owner` не должно лишать владельца возможности управления системой.

## 5. Агрегаты и владельцы инвариантов

### 5.1 User aggregate

Корень агрегата: `User`.

Отвечает за:

- состояние учетной записи;
- возможность аутентификации;
- смену пароля;
- блокировку и отключение;
- список действующих назначений ролей.

### 5.2 Role aggregate

Корень агрегата: `Role`.

Отвечает за:

- неизменяемость кода;
- системный статус;
- набор разрешений;
- допустимость удаления или деактивации.

### 5.3 System ownership policy

Правило единственного владельца рассматривается как отдельная доменная политика, поскольку охватывает нескольких пользователей и назначения ролей.

Передача владения должна выполняться одной транзакцией.

## 6. Бизнес-правила и инварианты

### 6.1 Общие правила

1. Только активный и неудаленный пользователь может пройти аутентификацию.
2. Статусы `pending`, `blocked` и `disabled` запрещают интерактивный вход.
3. Ошибка входа не должна раскрывать, существует ли указанный пользователь.
4. Пароль в открытом виде не сохраняется и не записывается в журнал.
5. Роли назначаются только существующим неудаленным пользователям.
6. Удаленные или отозванные роли не дают разрешений.
7. Проверка авторизации выполняется на сервере независимо от состояния интерфейса.
8. Все критические изменения выполняются в транзакциях.
9. Все значимые операции передаются в Audit с результатом выполнения.
10. CSRF, валидация входных данных и ограничения транзакций применяются также к владельцу системы.

### 6.2 Владелец системы

1. Роль определяется по `roles.code = system_owner`.
2. Признак владельца не хранится в `users`.
3. В системе должен существовать ровно один активный владелец.
4. Первый зарегистрированный пользователь получает роль владельца только в состоянии первоначальной инициализации системы.
5. После завершения инициализации новые пользователи не получают роль автоматически.
6. Владельца нельзя удалить, отключить, заблокировать или лишить роли до успешной передачи владения.
7. Передача владения включает назначение роли новому владельцу и отзыв у прежнего в одной транзакции.
8. Новый владелец должен быть активным и неудаленным пользователем.
9. Код роли и ее системный признак неизменяемы.
10. Авторизация может использовать короткое замыкание для владельца, но это не отменяет бизнес-валидацию, CSRF, транзакции и аудит.

### 6.3 Пароли

1. Хеширование выполняется стандартным API PHP с алгоритмом, рекомендованным текущей версией среды.
2. Параметры хеширования не задаются слабее безопасных значений по умолчанию без ADR.
3. При успешном входе устаревший хеш может быть обновлен.
4. После смены пароля обновляется `password_changed_at`.
5. Новый пароль не должен совпадать с текущим после проверки хеша.
6. Политика сложности не должна поощрять предсказуемые шаблоны; конкретные требования фиксируются до реализации формы регистрации.
7. Секреты восстановления и токены хранятся в виде хеша и относятся к инфраструктурным таблицам с ограниченным сроком жизни.

### 6.4 Назначение ролей

1. Назначать роли может пользователь с соответствующим разрешением или владелец системы.
2. Нельзя повторно создать действующее назначение той же роли.
3. Повторная команда назначения должна завершаться предсказуемо: либо идемпотентным успехом, либо доменной ошибкой, определенной API-спецификацией.
4. Отзыв уже отозванного назначения не изменяет историю.
5. Пользователь не может изменить свои роли, если это не разрешено отдельным бизнес-правилом.
6. Назначение системной роли может иметь дополнительные ограничения.

### 6.5 Разрешения

1. Разрешение предоставляется только через роль.
2. Прямые назначения разрешений пользователям в текущей модели отсутствуют.
3. Эффективные разрешения вычисляются из действующих ролей.
4. Проверка выполняется по неизменяемому коду разрешения.
5. Отсутствие разрешения означает запрет.
6. Неизвестный код разрешения не должен интерпретироваться как разрешение.

## 7. Основные сценарии использования

### SEC-UC-001 — Первоначальная регистрация владельца

Предусловия:

- система находится в состоянии первоначальной инициализации;
- активный владелец отсутствует.

Основной поток:

1. Пользователь передает регистрационные данные.
2. Система валидирует уникальность имени и email.
3. Система безопасно хеширует пароль.
4. Создается активная либо требующая активации учетная запись согласно утвержденной политике запуска.
5. Пользователю назначается роль `system_owner`.
6. Создание пользователя и назначение роли фиксируются одной транзакцией.
7. В Audit передается успешный результат.

Постусловие:

- существует ровно один активный владелец.

### SEC-UC-002 — Регистрация обычного пользователя

1. Принимаются регистрационные данные.
2. Проверяются формат, уникальность и политика пароля.
3. Создается пользователь со статусом `pending`, если автоматическая активация не разрешена.
4. Системные роли автоматически не назначаются.
5. Операция аудируется.

### SEC-UC-003 — Вход

1. Принимаются идентификатор и пароль.
2. Пользователь ищется по нормализованному имени либо email.
3. Проверяются хеш пароля, статус и `deleted_at`.
4. При успехе создается аутентифицированная сессия инфраструктурным механизмом.
5. Обновляется `last_login_at`.
6. При необходимости обновляется устаревший хеш.
7. Успех или отказ передается в Audit без записи пароля.

### SEC-UC-004 — Выход

1. Текущая сессия инвалидируется.
2. Результат передается в Audit.
3. Выход должен быть идемпотентным.

### SEC-UC-005 — Смена собственного пароля

1. Пользователь подтверждает текущий пароль.
2. Новый пароль проверяется политикой безопасности.
3. Создается новый хеш.
4. Обновляется `password_hash` и `password_changed_at`.
5. По утвержденной политике остальные активные сессии могут быть отозваны.
6. Операция аудируется.

### SEC-UC-006 — Административная блокировка

1. Проверяются полномочия инициатора.
2. Проверяется, что цель не является единственным владельцем.
3. Статус меняется на `blocked`.
4. Активные сессии блокируемого пользователя инвалидируются.
5. Операция и результат аудируются.

### SEC-UC-007 — Назначение роли

1. Проверяются полномочия инициатора.
2. Проверяются пользователь и роль.
3. Проверяется отсутствие действующего назначения.
4. Создается запись `user_roles`.
5. Операция аудируется.

### SEC-UC-008 — Отзыв роли

1. Проверяются полномочия инициатора.
2. Находится действующее назначение.
3. Проверяются ограничения системных ролей.
4. Заполняется `revoked_at`.
5. Операция аудируется.

### SEC-UC-009 — Изменение разрешений роли

1. Проверяются полномочия.
2. Проверяется системный статус роли.
3. Рассчитывается требуемое изменение.
4. Связи `role_permissions` изменяются транзакционно.
5. Кэш авторизации инвалидируется, если он существует.
6. Операция аудируется.

### SEC-UC-010 — Передача владения системой

1. Текущий владелец проходит повторное подтверждение личности.
2. Выбирается активный новый владелец.
3. Проверяются все инварианты.
4. Новому владельцу назначается `system_owner`.
5. У прежнего владельца роль отзывается.
6. Оба изменения фиксируются одной транзакцией.
7. После фиксации существует ровно один активный владелец.
8. Операция подробно аудируется.

### SEC-UC-011 — Проверка разрешения

1. Принимаются пользователь и код разрешения.
2. Проверяются состояние пользователя и действующая аутентификация.
3. Для владельца может применяться утвержденное короткое замыкание.
4. Для остальных пользователей загружаются действующие роли и разрешения.
5. Возвращается решение allow или deny.
6. Отсутствие данных или ошибка разрешения трактуется как deny.

## 8. Разрешения домена

Начальный каталог должен быть уточнен перед созданием сидеров.

```text
security.users.view
security.users.create
security.users.update
security.users.block
security.users.disable
security.users.delete
security.roles.view
security.roles.create
security.roles.update
security.roles.assign
security.roles.revoke
security.permissions.view
security.permissions.manage
security.owner.transfer
```

Коды после появления в миграциях считаются публичным системным контрактом и не переименовываются без миграционного плана и ADR.

## 9. Доменные события

Минимальный набор событий:

```text
UserRegistered
UserActivated
UserBlocked
UserDisabled
UserDeleted
UserAuthenticated
UserAuthenticationFailed
UserLoggedOut
UserPasswordChanged
RoleAssigned
RoleRevoked
RolePermissionsChanged
SystemOwnershipTransferred
```

Событие должно содержать только необходимые данные и не должно включать:

- пароль;
- хеш пароля;
- полный токен;
- секрет восстановления;
- лишние персональные сведения.

События публикуются только после успешной фиксации транзакции либо через механизм, обеспечивающий согласованность с транзакцией.

## 10. Интеграции и зависимости

### 10.1 Reference

Security использует Reference для статусов и небольших классификаторов.

Минимальная группа:

```text
user_status
```

Security сравнивает значения по неизменяемым кодам.

### 10.2 Audit

Security передает Audit:

- инициатора;
- время;
- операцию;
- тип сущности;
- идентификатор сущности;
- результат;
- безопасный контекст запроса;
- причину отказа в объеме, не раскрывающем секреты.

Audit не должен использоваться как источник текущего состояния Security.

### 10.3 Organization

`users.soldier_id` связывает учетную запись с военнослужащим.

Правила:

- связь необязательна;
- один военнослужащий связан не более чем с одной активной учетной записью;
- удаление или кадровое изменение военнослужащего не должно автоматически удалять пользователя;
- Security не вызывает внутренние репозитории Organization для проверки разрешений.

### 10.4 Infrastructure

Infrastructure предоставляет:

- HTTP-сессии;
- cookies;
- CSRF-защиту;
- rate limiting;
- хранение временных токенов;
- конфигурацию криптографических параметров;
- время и генераторы случайных значений.

Бизнес-решения остаются в Security.

## 11. Аудит операций

Обязательно аудируются:

- успешные и неуспешные входы;
- регистрация;
- активация, блокировка и отключение;
- смена и административный сброс пароля;
- назначение и отзыв ролей;
- изменение разрешений ролей;
- попытки изменить системные роли;
- передача владения;
- удаление пользователя;
- значимые отказы авторизации для административных операций.

Журнал не должен содержать секреты и не должен позволять восстановить пароль или токен.

## 12. Доменные ошибки

Минимальный каталог:

```text
UserNotFound
UserAlreadyExists
UsernameAlreadyExists
EmailAlreadyExists
UserNotActive
UserBlocked
UserDisabled
InvalidCredentials
InvalidCurrentPassword
PasswordPolicyViolation
RoleNotFound
RoleAlreadyAssigned
RoleAssignmentNotFound
PermissionNotFound
AccessDenied
SystemRoleImmutable
SystemOwnerRequired
SystemOwnerAlreadyExists
SystemOwnerTransferRequired
InvalidSystemOwnerTarget
ConcurrentSecurityModification
```

Внешний интерфейс не обязан раскрывать точный внутренний тип ошибки. Например, ошибки поиска пользователя и неверного пароля при входе должны возвращать единое безопасное сообщение.

## 13. Нефункциональные требования

### 13.1 Безопасность

- принцип deny by default;
- серверная проверка каждого защищенного действия;
- защита от CSRF для изменяющих запросов;
- ограничение частоты попыток входа;
- безопасные cookie и параметры сессии;
- защита от фиксации сессии;
- повторная генерация идентификатора сессии после входа;
- нейтральные сообщения об ошибках входа;
- отсутствие секретов в логах;
- параметризованные запросы;
- защита массового присваивания полей;
- минимальные полномочия технических компонентов.

### 13.2 Целостность

- уникальные ограничения обеспечиваются БД;
- внешние ключи обеспечивают ссылочную целостность;
- критические операции выполняются транзакционно;
- конкурентная передача роли владельца должна быть защищена блокировкой или эквивалентным механизмом;
- после любой подтвержденной транзакции инвариант единственного владельца сохраняется.

### 13.3 Производительность

- проверка разрешений не должна выполнять запрос на каждое разрешение отдельно;
- роли и разрешения загружаются пакетно;
- допустимо кэширование эффективных разрешений с обязательной инвалидизацией после изменений;
- ключевые поля поиска и связей индексируются;
- конкретные целевые показатели фиксируются после появления нагрузочного профиля.

### 13.4 Наблюдаемость

- технические ошибки имеют корреляционный идентификатор;
- события безопасности доступны для расследования;
- метрики не содержат персональных секретов;
- всплески неудачных входов должны быть обнаружимы.

### 13.5 Отказоустойчивость

- ошибка Audit не должна незаметно приводить к неаудированному критическому изменению;
- политика поведения при недоступности Audit определяется до реализации критических команд;
- ошибка отправки уведомления не откатывает успешно выполненную смену пароля, если уведомление не является частью бизнес-инварианта;
- частично выполненная передача владения запрещена.

## 14. Требования к тестированию

### 14.1 Модульные тесты

Обязательны для:

- переходов статусов пользователя;
- проверки пароля;
- неизменяемости системной роли;
- назначения и отзыва ролей;
- вычисления эффективных разрешений;
- политики единственного владельца;
- передачи владения;
- безопасного отображения ошибок.

### 14.2 Интеграционные тесты

Обязательны для:

- уникальности username, email и soldier_id;
- внешних ключей;
- транзакционного назначения ролей;
- конкурентной передачи владения;
- выборки действующих ролей;
- исключения удаленных сущностей;
- интеграции Security с Audit и Reference.

### 14.3 Тесты безопасности

Минимальный набор:

- SQL injection;
- CSRF;
- session fixation;
- brute force и rate limiting;
- обход блокировки пользователя;
- horizontal и vertical privilege escalation;
- изменение идентификаторов в запросах;
- попытка удалить единственного владельца;
- попытка присвоить `system_owner` второму пользователю;
- утечка различий между несуществующим пользователем и неверным паролем.

## 15. Открытые вопросы

До начала миграций необходимо отдельно утвердить:

1. точную модель хранения статуса пользователя: `status_id` или иной внешний ключ на `reference_values`;
2. правила автоматической активации первого владельца;
3. политику обычной регистрации: открытая, по приглашению или только административная;
4. минимальную политику паролей;
5. продолжительность и отзыв сессий;
6. сценарий восстановления доступа и каналы доставки;
7. необходимость многофакторной аутентификации в первой версии;
8. семантику административного сброса пароля;
9. политику блокировки после неудачных входов;
10. поведение критических команд при недоступности Audit;
11. точный начальный каталог ролей и разрешений;
12. необходимость хранения истории предыдущих паролей.

Открытые вопросы не должны решаться неявно в миграциях или коде.

## 16. Критерии готовности к ERD и реализации

Спецификация считается готовой к следующему этапу, когда:

- устранены или явно отложены открытые вопросы;
- утверждены статусы пользователя;
- утверждены сценарии регистрации, входа и восстановления;
- утвержден каталог начальных разрешений;
- подтверждены инварианты владельца;
- согласованы границы Security, Audit, Reference и Infrastructure;
- определены все необходимые таблицы и связи;
- отсутствуют противоречия с `DATABASE.md`, `ACCESS.md`, `ARCHITECTURE.md` и ADR;
- проведено архитектурное ревью;
- получено явное одобрение.

После этого создается ERD домена Security. Миграции до утверждения ERD не создаются.
