# Ревью ERD-010 — Security

## 1. Статус

Архитектурное ревью логической ERD домена `Security` завершено.

Ревью относится к:

```text
docs/erd/ERD-010-security.md
docs/erd/diagrams/security.puml
```

Состав сущностей, кардинальности и границы домена утверждены. Настоящий документ фиксирует решения по вопросам миграционного дизайна, которые должны быть отражены в спецификации миграций.

## 2. Уникальность username и email при soft delete

### Решение

`username` и `email` не переиспользуются после логического удаления учетной записи.

Ограничения:

```text
UNIQUE users(username)
UNIQUE users(email)
```

`email` остается nullable; несколько `NULL` допустимы.

### Обоснование

- имя входа остается однозначным в истории и аудите;
- исключается присвоение прежнего идентификатора другому субъекту;
- восстановление логически удаленной учетной записи не создает конфликт идентичности;
- миграция не зависит от условных уникальных индексов.

Освобождение ранее использованного имени или email допускается только отдельной административной процедурой с аудитом и явным изменением архивной записи. Такая процедура не входит в первую версию.

## 3. Единственное действующее назначение роли

### Решение

В `user_roles` создается служебная генерируемая колонка:

```text
active_role_id = IF(revoked_at IS NULL, role_id, NULL)
```

На нее создается уникальный индекс:

```text
UNIQUE (user_id, active_role_id)
```

Такой индекс запрещает два действующих назначения одной роли одному пользователю и допускает любое количество исторических строк, поскольку для отозванных назначений `active_role_id` равен `NULL`.

Колонка является технической деталью хранения и не входит в публичную доменную модель.

Доменный сервис дополнительно проверяет отсутствие действующего назначения и преобразует конфликт уникальности в предсказуемую доменную ошибку.

## 4. Длины и нормализация строк

Утверждаются базовые размеры:

| Поле | Типовая длина |
|---|---:|
| `users.username` | 64 |
| `users.email` | 254 |
| `users.password_hash` | 255 |
| `roles.code` | 128 |
| `roles.name` | 255 |
| `roles.description` | TEXT |
| `permissions.code` | 191 |
| `permissions.module` | 64 |
| `permissions.name` | 255 |
| `permissions.description` | TEXT |

Правила канонизации:

- входные значения очищаются от внешних пробелов;
- `username` хранится в нижнем регистре;
- `email` хранится в нижнем регистре после синтаксической проверки;
- машинные коды ролей, разрешений и модулей хранятся в нижнем регистре ASCII;
- коды используют только символы `a-z`, `0-9`, `_`, `-` и `.` согласно назначению поля;
- нормализация выполняется прикладным сервисом до записи;
- база данных использует согласованную `utf8mb4` collation, обеспечивающую регистронезависимую уникальность пользовательских идентификаторов.

Отображаемые названия и описания не приводятся к нижнему регистру.

## 5. Действия внешних ключей

Для внутренних рабочих сущностей Security утверждается явное поведение:

| Связь | ON DELETE | ON UPDATE |
|---|---|---|
| `users.status_id → reference_values.id` | RESTRICT | RESTRICT |
| `users.soldier_id → soldiers.id` | RESTRICT | RESTRICT |
| `user_roles.user_id → users.id` | RESTRICT | RESTRICT |
| `user_roles.role_id → roles.id` | RESTRICT | RESTRICT |
| `user_roles.assigned_by → users.id` | RESTRICT | RESTRICT |
| `role_permissions.role_id → roles.id` | RESTRICT | RESTRICT |
| `role_permissions.permission_id → permissions.id` | RESTRICT | RESTRICT |

Причины:

- идентификаторы сущностей считаются неизменяемыми;
- рабочие сущности используют soft delete или сохраняются как системный контракт;
- история назначений не должна разрушаться каскадными действиями;
- физическое удаление выполняется только отдельной контролируемой процедурой очистки, если она когда-либо будет введена.

## 6. Принадлежность статуса группе user_status

Обычный внешний ключ `status_id → reference_values.id` подтверждает существование значения, но сам по себе не подтверждает его принадлежность нужной группе.

### Решение

Целостность обеспечивается двумя уровнями:

1. доменный сервис разрешает присваивание только значений группы с кодом `user_status`;
2. миграция создает триггер `BEFORE INSERT/UPDATE` для `users`, который отклоняет `status_id`, не принадлежащий активной группе `user_status`.

Триггер не содержит бизнес-переходов между статусами. Он контролирует только классификационную принадлежность внешнего ключа.

До появления общей унифицированной стратегии составных ссылок на `reference_values` это считается допустимым инфраструктурным ограничением БД.

## 7. Первичное создание системных данных

Ответственность разделяется следующим образом:

### Миграции

Создают:

- таблицы;
- ключи и ограничения;
- технические генерируемые колонки;
- индексы;
- триггеры целостности.

### Идемпотентный системный seeder

Создает или синхронизирует по неизменяемым кодам:

- группу `user_status`;
- статусы `pending`, `active`, `blocked`, `disabled`;
- роли `system_owner`, `administrator`, `operator`, `viewer`;
- начальный каталог разрешений;
- связи системных ролей с разрешениями.

### Команда первоначальной установки

Первый владелец не создается обычной миграцией и не хранится в исходном коде.

Отдельная одноразовая команда установки:

1. проверяет отсутствие действующего владельца;
2. интерактивно или через защищенный канал принимает данные первого пользователя;
3. создает активного пользователя;
4. назначает ему `system_owner`;
5. фиксирует обе операции одной транзакцией;
6. помечает первоначальную инициализацию завершенной;
7. передает событие в Audit.

Повторный запуск после завершения инициализации запрещен.

## 8. Оптимистическая блокировка

### Решение

Поля `version` в таблицы `users` и `roles` в первой версии не добавляются.

Для критических конкурентных операций используются:

- транзакции;
- блокировки строк `SELECT ... FOR UPDATE`;
- уникальные ограничения;
- повторная проверка инвариантов перед фиксацией.

Передача `system_owner` обязательно использует пессимистическую блокировку соответствующих ролей и действующих назначений.

Оптимистическая блокировка может быть добавлена позднее, если реальные сценарии редактирования покажут риск потерянных обновлений. Такое изменение предварительно отражается в ERD и спецификации API.

## 9. Семантика assigned_by = NULL

`user_roles.assigned_by` остается nullable.

`NULL` допускается только для:

- первоначальной установки;
- миграции или системного seeder;
- автоматической системной операции без аутентифицированного пользователя.

Обычная административная операция обязана сохранять идентификатор инициатора.

Для каждой операции с `assigned_by = NULL` Audit должен содержать машинный код источника, например:

```text
installation
migration
system_seeder
system_process
```

`NULL` не означает неизвестного инициатора и не может использоваться для обхода аудита.

## 10. Итог ревью

Утверждены:

- пять внутренних таблиц Security;
- две внешние интеграционные связи;
- сохранение истории назначений;
- отсутствие прямых разрешений пользователям;
- модель единственного владельца через RBAC;
- непереиспользование логинов и email;
- уникальность действующих назначений через генерируемую колонку;
- явные действия FK без каскадного удаления;
- проверка группы статуса на уровне сервиса и БД;
- разделение миграций, системного seeder и первоначальной установки;
- отсутствие optimistic locking в первой версии;
- ограниченная и аудируемая семантика `assigned_by = NULL`.

## 11. Решение о готовности

ERD домена `Security` архитектурно одобрена.

Следующий обязательный артефакт:

```text
docs/migrations/SECURITY-MIGRATIONS.md
```

В нем должны быть зафиксированы:

- порядок миграций;
- точные типы колонок;
- имена ограничений и индексов;
- SQL-выражения генерируемых колонок;
- определения триггеров;
- порядок отката;
- системные seed-данные;
- проверки после миграции.

SQL-миграции и PHP-код не создаются до утверждения этой спецификации.
