# ERD-010 — Security

## 1. Назначение

Документ фиксирует логическую модель данных домена `Security` после утверждения его спецификации и архитектурного ревью.

Источники требований:

- `docs/DATABASE.md`;
- `docs/domains/SECURITY.md`;
- `docs/domains/SECURITY-REVIEW.md`;
- `docs/ACCESS.md`;
- ADR по RBAC, владельцу системы, soft delete и справочным данным.

ERD является проектным контрактом для последующих миграций. Изменения состава таблиц, связей и ключевых ограничений сначала вносятся в этот документ.

## 2. Границы диаграммы

Внутри домена `Security` находятся:

```text
users
roles
permissions
user_roles
role_permissions
```

Внешние сущности, показанные только как точки интеграции:

```text
reference_values
soldiers
```

HTTP-сессии, токены восстановления, MFA-факторы, rate limiting и временные секреты в текущую ERD не входят. Они относятся к `Infrastructure` и будут проектироваться отдельными диаграммами.

## 3. Диаграмма

Исходный файл PlantUML:

```text
docs/erd/diagrams/security.puml
```

Логическая структура:

```text
reference_values 1 ─────< users
soldiers         0..1 ── 0..1 users
users            1 ─────< user_roles >───── 1 roles
users            0..1 ──< user_roles.assigned_by
roles            1 ─────< role_permissions > 1 permissions
```

## 4. Таблицы

### 4.1 users

Назначение: текущее состояние учетной записи.

| Поле | Обязательность | Назначение |
|---|---:|---|
| `id` | да | Внутренний идентификатор |
| `soldier_id` | нет | Необязательная связь с военнослужащим |
| `status_id` | да | Ссылка на значение группы `user_status` |
| `username` | да | Уникальное имя входа |
| `email` | нет | Адрес электронной почты |
| `password_hash` | да | Стойкий хеш пароля |
| `must_change_password` | да | Требование сменить временный пароль |
| `last_login_at` | нет | Время последнего успешного входа |
| `password_changed_at` | нет | Время последней смены пароля |
| `created_at` | да | Время создания |
| `updated_at` | да | Время изменения |
| `deleted_at` | нет | Время логического удаления |

Ключи и ограничения:

- PK: `id`;
- FK: `soldier_id → soldiers.id`;
- FK: `status_id → reference_values.id`;
- `soldier_id` должен быть уникальным при наличии значения;
- `username` должен быть уникальным в соответствии с утвержденной политикой повторного использования после soft delete;
- `email` должен быть уникальным при наличии значения в соответствии с той же политикой;
- значение `status_id` обязано принадлежать группе `user_status`;
- `must_change_password` по умолчанию имеет значение `false`;
- физическое удаление рабочих учетных записей запрещено.

Утвержденные коды статусов:

```text
pending
active
blocked
disabled
```

### 4.2 roles

Назначение: именованные наборы разрешений.

| Поле | Обязательность | Назначение |
|---|---:|---|
| `id` | да | Внутренний идентификатор |
| `code` | да | Неизменяемый машинный код |
| `name` | да | Отображаемое название |
| `description` | нет | Описание назначения |
| `is_system` | да | Признак защищенной системной роли |
| `created_at` | да | Время создания |
| `updated_at` | да | Время изменения |
| `deleted_at` | нет | Время логического удаления |

Ключи и ограничения:

- PK: `id`;
- UQ: `code`;
- код не изменяется после создания;
- системная роль не может быть физически удалена;
- роль `system_owner` создается миграцией и имеет `is_system = true`.

Начальный каталог ролей:

```text
system_owner
administrator
operator
viewer
```

### 4.3 permissions

Назначение: атомарные права на действия над ресурсами.

| Поле | Обязательность | Назначение |
|---|---:|---|
| `id` | да | Внутренний идентификатор |
| `code` | да | Неизменяемый код разрешения |
| `name` | да | Отображаемое название |
| `description` | нет | Описание разрешения |
| `module` | да | Код модуля или домена |
| `is_system` | да | Признак системного разрешения |
| `created_at` | да | Время создания |
| `updated_at` | да | Время изменения |

Ключи и ограничения:

- PK: `id`;
- UQ: `code`;
- формат кода: `module.resource.action`;
- код не изменяется после публикации;
- физическое удаление системного разрешения запрещено.

### 4.4 user_roles

Назначение: история назначения ролей пользователям.

| Поле | Обязательность | Назначение |
|---|---:|---|
| `id` | да | Идентификатор назначения |
| `user_id` | да | Пользователь, получивший роль |
| `role_id` | да | Назначенная роль |
| `assigned_by` | нет | Пользователь-инициатор либо `NULL` для системной операции |
| `assigned_at` | да | Время назначения |
| `revoked_at` | нет | Время отзыва |

Ключи и ограничения:

- PK: `id`;
- FK: `user_id → users.id`;
- FK: `role_id → roles.id`;
- FK: `assigned_by → users.id`;
- одновременно разрешено не более одного действующего назначения пары `user_id + role_id`;
- отзыв не удаляет строку, а устанавливает `revoked_at`;
- `revoked_at` не может быть раньше `assigned_at`;
- каскадное удаление пользователей и ролей запрещено.

Ограничение единственного действующего назначения должно быть обеспечено БД совместимым с MySQL способом и дополнительно проверяться доменным сервисом.

### 4.5 role_permissions

Назначение: состав разрешений роли.

| Поле | Обязательность | Назначение |
|---|---:|---|
| `role_id` | да | Роль |
| `permission_id` | да | Разрешение |

Ключи и ограничения:

- составной PK: `role_id + permission_id`;
- FK: `role_id → roles.id`;
- FK: `permission_id → permissions.id`;
- одна связь существует не более одного раза;
- каскадное физическое удаление системных записей запрещено.

## 5. Кардинальности

| Связь | Кардинальность | Правило |
|---|---|---|
| `reference_values → users` | `1 : N` | Один статус используется многими пользователями |
| `soldiers ↔ users` | `0..1 : 0..1` | Технический пользователь может не иметь военнослужащего |
| `users → user_roles` | `1 : N` | Пользователь имеет историю назначений |
| `roles → user_roles` | `1 : N` | Роль назначается многим пользователям |
| `users → user_roles.assigned_by` | `0..1 : N` | Инициатор может отсутствовать у системной операции |
| `roles → role_permissions` | `1 : N` | Роль содержит разрешения |
| `permissions → role_permissions` | `1 : N` | Разрешение входит во многие роли |

## 6. Инвариант system_owner

ERD отражает хранение владельца через обычные таблицы RBAC:

```text
roles.code = system_owner
user_roles.revoked_at IS NULL
```

Отдельный флаг в `users` не создается.

Инвариант:

> После завершения первоначальной инициализации в системе существует ровно один активный и неудаленный пользователь с действующим назначением роли `system_owner`.

Этот инвариант охватывает несколько таблиц и не выражается одним обычным внешним ключом. Он обеспечивается совокупностью:

- транзакционной доменной политики;
- блокировок при передаче владения;
- ограничений уникальности действующих назначений;
- проверок перед блокировкой, отключением, удалением и отзывом роли;
- интеграционных тестов конкурентных операций.

## 7. Правила удаления

- `users` и `roles` используют soft delete;
- `permissions` не удаляются физически после публикации системного контракта;
- `user_roles` сохраняет историю и не удаляется при обычном отзыве;
- `role_permissions` удаляется физически только как управляемое изменение состава роли;
- внешние ключи не должны использовать `ON DELETE CASCADE` для рабочих сущностей Security;
- предпочтительное поведение FK — `RESTRICT` или эквивалентное явное управление.

## 8. Индексы

Минимально необходимы:

```text
users(status_id)
users(soldier_id)
users(username)
users(email)
users(deleted_at)
roles(code)
roles(deleted_at)
permissions(code)
permissions(module)
user_roles(user_id, revoked_at)
user_roles(role_id, revoked_at)
user_roles(assigned_by)
role_permissions(permission_id, role_id)
```

Точный набор, порядок колонок и стратегия уникальности при soft delete утверждаются в спецификации миграций после проверки запросов и ограничений MySQL 8.4.

## 9. Решения, отложенные до проектирования Infrastructure

В эту ERD намеренно не включены:

```text
sessions
password_reset_tokens
user_mfa_factors
recovery_codes
login_attempts
remember_tokens
```

Их добавление не должно менять базовую RBAC-модель и не должно приводить к хранению секретов в `users` в открытом виде.

## 10. Вопросы миграционного дизайна

До написания миграций необходимо технически утвердить:

1. способ обеспечения уникальности `username` и `email` при soft delete;
2. способ обеспечения одного действующего назначения `user_id + role_id` в MySQL 8.4;
3. длины строковых полей и правила нормализации регистра;
4. точные действия FK при удалении и обновлении;
5. способ проверки принадлежности `status_id` группе `user_status`;
6. стратегию начального создания ролей, разрешений и первого владельца;
7. необходимость поля версии для оптимистической блокировки агрегатов;
8. допустимость `assigned_by = NULL` для миграций и системных операций.

Эти вопросы не изменяют логическую ERD, но обязаны быть закрыты в спецификации миграций.

## 11. Критерии утверждения

ERD готова к переходу к миграциям после подтверждения, что:

- все пять таблиц соответствуют спецификации Security;
- внешние границы с Reference и Organization согласованы;
- кардинальности и nullable-связи утверждены;
- инвариант `system_owner` не ослаблен;
- история назначений ролей сохраняется;
- нет прямых назначений разрешений пользователям;
- сессии и временные токены остаются в Infrastructure;
- вопросы миграционного дизайна получили явные решения;
- проведено архитектурное ревью ERD.
