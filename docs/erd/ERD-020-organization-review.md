# ERD-020: Review домена Organization

## 1. Статус документа

```text
REVIEW RESULT: APPROVED
ERD STATUS: READY FOR MIGRATION SPECIFICATION
```

Документ фиксирует результаты архитектурного и физического ревью `docs/erd/ERD-020-organization.md`.

После утверждения данного ревью структура таблиц, связей, ограничений и защитных механизмов домена `Organization` считается замороженной для версии 1. Изменения допускаются только через отдельное архитектурное решение и синхронное обновление доменной документации, ERD, миграционной спецификации и тестовых сценариев.

## 3. Область утверждения

Утверждена модель следующих таблиц:

```text
military_units
departments
ranks
positions
soldiers
identifier_types
soldier_identifiers
```

Внешние зависимости:

```text
reference_values

```

`users` не является частью ERD домена `Organization`. Связь остается однонаправленной со стороны `Security`:

```text
users.soldier_id → soldiers.id
```

Обратная ссылка из `soldiers` в `users` запрещена.

- правилам именования;

## 5. Утвержденные решения

### 5.1 Воинские части

Для `military_units` утверждено:

- `code` обязателен;
- `code` уникален глобально;
- `code` нормализуется как `trim + lowercase ASCII`;
- опубликованный код неизменяем;
- код не переиспользуется после soft delete;
- `short_name` допускает `NULL`;
- удаление выполняется через `deleted_at`;
- физическое каскадное удаление запрещено.

### 5.2 Подразделения

Для `departments` утверждено:

- каждое подразделение принадлежит одной воинской части;
- `parent_id` допускает `NULL` для корневого подразделения;
- родитель и дочернее подразделение должны принадлежать одной части;
- `parent_id = id` запрещено;
- циклы в иерархии запрещены;
- `code` уникален в пределах `military_unit_id`;
- код не переиспользуется после soft delete;
- `short_name` допускает `NULL`;
- удаление выполняется логически;
- удаление запрещено при наличии активных дочерних подразделений, должностей или военнослужащих.

Проверка циклов и принадлежности родителя той же части должна выполняться как доменным сервисом, так и защитными триггерами базы данных.

### 5.3 Воинские звания

Для `ranks` утверждено:

- звания являются собственной сущностью `Organization`, а не универсальным справочником `Reference`;
- `code` обязателен, уникален и неизменяем;
- `seniority_order` обязателен и уникален;
- `short_name` допускает `NULL`;
- `is_system` обязателен;
- `deleted_at` отсутствует в версии 1;
- опубликованные системные звания не удаляются физически;
- изменение кода системного звания запрещено;
- изменения системного набора выполняются миграциями и идемпотентными сидерами.

Полный перечень званий не фиксируется в ERD. Он должен быть определен в миграционной спецификации как отдельный версионируемый seed-набор.

### 5.4 Должности

Для `positions` утверждено:

- должность принадлежит одному подразделению;
- принадлежность воинской части определяется через подразделение;
- `rank_id` допускает `NULL`, так как рекомендуемое или требуемое звание может быть не задано;
- `code` уникален в пределах подразделения;
- код не переиспользуется после soft delete;
- должность может быть вакантной;
- soft-deleted должность не может назначаться;
- удаление занятой должности запрещено;
- физическое каскадное удаление запрещено.

### 5.5 Военнослужащие

Для `soldiers` утверждено:

- `military_unit_id` обязателен;
- `department_id` допускает `NULL`;
- `position_id` допускает `NULL`;
- `rank_id` обязателен;
- `status_id` обязателен;
- `last_name` и `first_name` обязательны;
- `middle_name` допускает `NULL`;
- `birth_date` допускает `NULL`;
- составное поле ФИО не хранится;
- полное имя формируется прикладным слоем;
- военнослужащий занимает не более одной должности;
- должность занята не более чем одним активным военнослужащим;
- военнослужащий, подразделение и должность должны относиться к одной воинской части;
- назначенная должность должна принадлежать назначенному подразделению;
- soft-deleted часть, подразделение или должность не могут использоваться для новых назначений;
- удаление военнослужащего выполняется логически.

Уникальность занятия должности обеспечивается уникальным ограничением на nullable-поле:

```text
UNIQUE (position_id)
```

Поведение MySQL с несколькими `NULL` допускает любое количество военнослужащих без назначенной должности и не более одной строки для конкретного `position_id`.

### 5.6 Статус военнослужащего

`status_id` ссылается на `reference_values.id`.

Утверждена системная группа Reference:

```text
soldier_status
```

Минимальный seed-набор версии 1:

```text
active
suspended
dismissed
```

Значение `active` является значением по умолчанию.

Семантика:

- `active` — действующий военнослужащий;
- `suspended` — временно не участвует в штатных операциях, но остается учетной сущностью;
- `dismissed` — исключен из действующего состава, запись сохраняется.

Коды статусов неизменяемы и не переиспользуются. Принадлежность `status_id` группе `soldier_status` должна контролироваться триггерами и доменным сервисом.

Изменение статуса на `dismissed` не выполняет автоматический soft delete. Освобождение должности и иные организационные последствия выполняются явной транзакционной доменной операцией.

### 5.7 Типы идентификаторов

Для `identifier_types` утверждено:

- `code` обязателен, уникален и неизменяем;
- `allows_multiple` обязателен;
- `is_system` обязателен;
- `description` допускает `NULL`;
- `validation_pattern` допускает `NULL`;
- регулярное выражение является прикладным правилом и не исполняется как динамический SQL;
- `deleted_at` отсутствует в версии 1;
- системные типы не удаляются и не меняют машинный код.

Минимальный seed-набор:

```text
personal_number
dog_tag_number
```

Для обоих типов:

```text
allows_multiple = false
is_system = true
```

Паспортные и иные государственные реквизиты не включаются в обязательный стартовый seed и могут добавляться отдельными утвержденными миграциями с учетом режима защиты персональных данных.

### 5.8 Идентификаторы военнослужащих

Для `soldier_identifiers` утверждено:

- `soldier_id` обязателен;
- `identifier_type_id` обязателен;
- `value` хранит отображаемое значение;
- `normalized_value` хранит каноническое значение для поиска и уникальности;
- нормализация выполняется до записи;
- сочетание типа и нормализованного значения уникально глобально, включая soft-deleted записи;
- идентификатор удаляется логически;
- идентификаторы не используются внешними доменами вместо `soldiers.id`;
- чувствительные значения не отображаются без отдельного разрешения.

Для типов с `allows_multiple = false` используется STORED generated column:

```text
single_type_id
```

и уникальное ограничение:

```text
UNIQUE (soldier_id, single_type_id)
```

Точное выражение generated column и совместимость с MySQL 8.4 должны быть закреплены в миграционной спецификации. Значение колонки должно быть `identifier_type_id` только для активной записи типа, запрещающего множественность; во всех остальных случаях — `NULL`.

Поскольку generated column не может безопасно получать `allows_multiple` из другой таблицы, миграционная спецификация должна выбрать один из следующих эквивалентных механизмов без изменения утвержденного бизнес-инварианта:

1. хранение денормализованного признака множественности в `soldier_identifiers`, поддерживаемого триггерами;
2. отказ от generated column в пользу `BEFORE INSERT/UPDATE` триггеров с блокировкой и проверкой существующей активной записи.

Предпочтительным для версии 1 признан второй вариант: триггерная проверка без денормализации. Поле `single_type_id` из концептуальной ERD в таком случае не создается физически.

## 6. Утвержденные nullable-поля

Следующие поля допускают `NULL` намеренно:

```text
military_units.short_name
departments.parent_id
departments.short_name
ranks.short_name
positions.rank_id
soldiers.department_id
soldiers.position_id
soldiers.middle_name
soldiers.birth_date
identifier_types.description
identifier_types.validation_pattern
soldier_identifiers.deleted_at
```

`department_id = NULL` означает, что военнослужащий еще не распределен по подразделению.

`position_id = NULL` означает отсутствие текущей штатной должности.

Если `position_id` задан, `department_id` также обязан быть задан.

## 7. Утвержденные внешние ключи

Все внешние ключи домена используют:

```text
ON DELETE RESTRICT
ON UPDATE RESTRICT
```

Утвержденные связи:

```text
departments.military_unit_id → military_units.id
departments.parent_id → departments.id
positions.department_id → departments.id
positions.rank_id → ranks.id
soldiers.military_unit_id → military_units.id
soldiers.department_id → departments.id
soldiers.position_id → positions.id
soldiers.rank_id → ranks.id
soldiers.status_id → reference_values.id
soldier_identifiers.soldier_id → soldiers.id
soldier_identifiers.identifier_type_id → identifier_types.id
```

Каскадное удаление и каскадное обновление запрещены.

## 8. Защитные триггеры

Миграционная спецификация обязана определить именованные триггеры для следующих инвариантов.

### 8.1 Подразделения

Перед вставкой и обновлением:

- запрет `parent_id = id`;
- проверка принадлежности родителя той же воинской части;
- запрет циклов;
- запрет использования soft-deleted воинской части или родителя.

Перед soft delete или организационным удалением:

- запрет при активных дочерних подразделениях;
- запрет при активных должностях;
- запрет при активных военнослужащих.

### 8.2 Должности

Перед вставкой и обновлением:

- запрет ссылки на soft-deleted подразделение;
- запрет ссылки на несуществующее звание.

Перед soft delete:

- запрет удаления занятой должности.

### 8.3 Военнослужащие

Перед вставкой и обновлением:

- проверка принадлежности `status_id` группе `soldier_status`;
- запрет ссылки на soft-deleted воинскую часть;
- проверка принадлежности подразделения указанной части;
- проверка принадлежности должности указанному подразделению и части;
- запрет `position_id` при `department_id IS NULL`;
- запрет назначения soft-deleted подразделения или должности;
- проверка занятости должности в дополнение к UNIQUE-ограничению.

### 8.4 Идентификаторы

Перед вставкой и обновлением:

- канонизация или проверка уже канонизированного `normalized_value`;
- запрет пустого нормализованного значения;
- запрет ссылки на soft-deleted военнослужащего;
- проверка системного типа;
- проверка глобальной уникальности `(identifier_type_id, normalized_value)`;
- проверка единственного активного значения для типа с `allows_multiple = false`.

Триггеры являются защитой базы данных и не заменяют доменную валидацию.

## 9. Нормализация данных

### 9.1 Машинные коды

Для кодов применяется:

```text
trim
lowercase
ASCII only
```

Это относится к:

```text
military_units.code
departments.code
positions.code
ranks.code
identifier_types.code
```

### 9.2 Идентификаторы

Нормализация идентификатора зависит от его типа и выполняется зарегистрированной стратегией прикладного слоя.

Минимальные общие операции:

```text
trim
Unicode normalization
удаление разрешенных форматирующих разделителей
регистронезависимое преобразование, если оно допустимо для типа
```

Исходное `value` сохраняется для отображения. Уникальность определяется только по `normalized_value`.

## 10. Seed-данные

Миграционная спецификация должна предусмотреть идемпотентный seeder.

Обязательные данные:

### Reference

```text
group: soldier_status
values:
  active      default=true
  suspended   default=false
  dismissed   default=false
```

### Identifier types

```text
personal_number  allows_multiple=false  is_system=true
dog_tag_number   allows_multiple=false  is_system=true
```

### Ranks

Seed званий должен быть:

- явным;
- упорядоченным;
- идемпотентным;
- версионируемым;
- согласованным с целевой юрисдикцией развертывания.

ERD не утверждает конкретный национальный перечень воинских званий. До реализации рабочий перечень должен быть закреплен отдельным разделом `ORGANIZATION-MIGRATIONS.md`.

## 11. Транзакционные операции

Следующие операции выполняются в одной транзакции:

- назначение военнослужащего в подразделение;
- назначение на должность;
- освобождение должности;
- перевод между подразделениями;
- перевод между воинскими частями;
- изменение статуса с обязательным освобождением должности;
- добавление идентификатора;
- замена единственного идентификатора;
- перемещение подразделения в иерархии.

Для назначения должности требуется блокировка целевой строки `positions` и проверка существующего назначения, чтобы исключить гонку между параллельными транзакциями.

## 12. Решения, отложенные за пределы версии 1

Не входят в ERD версии 1:

- история должностей;
- история переводов;
- история присвоения званий;
- история организационной структуры;
- временное исполнение обязанностей;
- совместительство;
- несколько одновременных штатных назначений;
- штатные расписания и версии штатов;
- географические адреса частей;
- хранение фотографий;
- семейные и контактные данные;
- автоматическое шифрование значений идентификаторов;
- внешняя синхронизация с государственными реестрами;
- closure table или materialized path для иерархии подразделений.

Добавление перечисленных возможностей требует отдельного ADR или изменения архитектурного контракта.

Минимальный набор тестов:

1. создание воинской части с валидным кодом;
2. отказ при повторном коде части;
3. отказ при повторном коде подразделения в одной части;
4. разрешение одинакового кода подразделения в разных частях;
5. создание корневого подразделения;
6. создание дочернего подразделения в той же части;
7. отказ при родителе из другой части;
8. отказ при прямом самоссылочном родителе;
9. отказ при создании цикла;
10. создание вакантной должности;
11. назначение должности одному военнослужащему;
12. отказ при повторном занятии должности;
13. отказ при должности из другого подразделения;
14. отказ при подразделении из другой части;
15. создание военнослужащего без подразделения и должности;
16. отказ при должности без подразделения;
17. отказ при статусе не из группы `soldier_status`;
18. отказ при назначении soft-deleted части;
19. отказ при назначении soft-deleted подразделения;
20. отказ при назначении soft-deleted должности;
21. отказ при удалении занятой должности;
22. отказ при удалении подразделения с активными дочерними объектами;
23. добавление уникального идентификатора;
24. отказ при повторном `(type, normalized_value)`;
25. отказ при втором активном идентификаторе немножественного типа;
26. разрешение нескольких значений множественного типа;
27. повторное выполнение seeder без дублей;
28. параллельное назначение одной должности только одному военнослужащему;
29. освобождение должности и последующее назначение другому военнослужащему;
30. перевод военнослужащего с атомарным обновлением части, подразделения и должности.

## 15. Результат ревью

ERD домена `Organization` утверждена со следующими обязательными уточнениями для физической реализации:

- группа статусов называется `soldier_status`;
- минимальные статусы: `active`, `suspended`, `dismissed`;
- минимальные типы идентификаторов: `personal_number`, `dog_tag_number`;
- конкретный перечень званий фиксируется в миграционной спецификации;
- `department_id`, `position_id`, `middle_name` и `birth_date` являются nullable;
