# ERD-030 — Reference: архитектурное ревью

## 1. Статус

```text
APPROVED
```

ERD домена `Reference` одобрена как логический контракт для подготовки спецификации миграций.

Ревью выполнено для следующих артефактов:

- `docs/domains/REFERENCE.md`;
- `docs/domains/REFERENCE-REVIEW.md`;
- `docs/erd/ERD-030-reference.md`;
- `docs/erd/diagrams/reference.puml`;
- `docs/DATABASE.md`;
- ADR по справочным данным, soft delete и доменно-ориентированной архитектуре.

## 2. Итог ревью

Модель признана достаточной для первой версии домена.

Утверждённый состав таблиц:

```text
reference_groups
reference_values
```

Добавление отдельных таблиц для конкретных справочников не допускается без нового архитектурного решения.

## 3. Подтверждённые решения

### 3.1 Границы домена

`Reference` является независимым поставщиком нормативно-справочных данных.

Домен:

- не зависит от `Security`, `Organization` и других прикладных доменов;
- предоставляет другим доменам ссылки на `reference_values.id`;
- не содержит бизнес-правил доменов-потребителей;
- не моделирует каждый справочник отдельной таблицей.

### 3.2 Идентичность и коды

Подтверждено:

- `reference_groups.code` уникален глобально;
- `reference_values.code` уникален внутри `group_id`;
- коды канонизируются через `trim` и нижний регистр;
- код не изменяется после публикации;
- код не переиспользуется после soft delete;
- уникальные ограничения включают soft-deleted записи и тем самым обеспечивают запрет повторного использования.

`name` и `description` не являются идентификаторами и могут изменяться управляемым процессом.

### 3.3 Ссылки из других доменов

Утверждено правило:

```text
consumer_table.reference_value_id → reference_values.id
```

Хранение `reference_values.code` вместо внешнего ключа запрещено.

Обычный внешний ключ подтверждает только существование значения. Принадлежность требуемой группе проверяется доменным сервисом потребляющего домена.

### 3.4 Default-значение

Группа может иметь:

- ноль активных default-значений;
- одно активное default-значение;
- не более одного активного default-значения.

Для ограничения утверждена служебная generated column:

```text
active_default_group_id =
    IF(is_default = true AND deleted_at IS NULL, group_id, NULL)
```

и уникальный индекс:

```text
UNIQUE(active_default_group_id)
```

Точное SQL-выражение, тип колонки и режим `VIRTUAL` либо `STORED` должны быть подтверждены в `REFERENCE-MIGRATIONS.md` на MySQL 8.4.

Перенос default-значения выполняется транзакционно доменным сервисом.

### 3.5 Soft delete

Обе таблицы используют soft delete.

Подтверждено:

- физическое удаление опубликованных групп и значений не является обычной операцией;
- soft-deleted коды остаются зарезервированными;
- удаление группы запрещено при наличии активных значений;
- удаление значения запрещено, если оно используется внешними доменами;
- восстановление требует проверки уникальности и остальных инвариантов.

Инвариант «удалённая группа не имеет активных значений» является межстрочным и обеспечивается доменным сервисом и интеграционными тестами.

### 3.6 Системные данные

`is_system = true` обозначает часть системного контракта, но не заменяет авторизацию.

Для системных записей запрещены обычные операции:

- изменение `code`;
- изменение `group_id` значения;
- soft delete;
- физическое удаление;
- сброс `is_system`.

Защита обеспечивается совокупностью RBAC, доменных политик, seeders, аудита и тестов.

### 3.7 Внешние ключи

Утверждено:

```text
reference_values.group_id → reference_groups.id
ON DELETE RESTRICT
ON UPDATE RESTRICT
```

Каскадное удаление в домене запрещено.

Домены-потребители также должны использовать `ON DELETE RESTRICT` и `ON UPDATE RESTRICT` для ссылок на `reference_values.id`.

## 4. Проверка нормализации

Модель соответствует требованиям 3NF:

- данные группы хранятся только в `reference_groups`;
- данные значения хранятся только в `reference_values`;
- значения не дублируют код или имя группы;
- связь выражена через `group_id`;
- служебная generated column не является самостоятельным бизнес-атрибутом и используется только для ограничения целостности.

Нарушений нормализации, требующих изменения ERD, не выявлено.

## 5. Проверка кардинальностей

Подтверждена связь:

```text
reference_groups 1 ─────< reference_values
```

Правила:

- каждое значение принадлежит ровно одной группе;
- группа может существовать без значений;
- перенос опубликованного значения между группами запрещён;
- изменение `group_id` системного или опубликованного значения не допускается обычной операцией.

## 6. Проверка индексов

Логически одобрены:

```text
reference_groups(code) UNIQUE
reference_groups(deleted_at)

reference_values(group_id, code) UNIQUE
reference_values(active_default_group_id) UNIQUE
reference_values(group_id, sort_order, id)
reference_values(group_id, deleted_at)
reference_values(deleted_at)
```

Перед реализацией требуется проверить, не является ли отдельный индекс `reference_values(deleted_at)` избыточным относительно фактических административных запросов.

Удаление индекса из физической спецификации допустимо только после анализа запросов; логическая ERD от этого не меняется.

## 7. Замечания, переданные в миграционную спецификацию

Следующие вопросы не блокируют ERD и должны быть решены в `REFERENCE-MIGRATIONS.md`:

1. точные типы и длины строковых полей;
2. collation и регистронезависимая уникальность кодов;
3. timestamp precision и единый тип времени;
4. физический тип `BOOLEAN`;
5. тип `active_default_group_id`;
6. режим generated column: `VIRTUAL` или `STORED`;
7. точные имена ограничений и индексов;
8. необходимость триггеров для защиты неизменяемых и системных полей;
9. порядок `up` и `down` миграций;
10. идемпотентный seed `user_status`;
11. поведение rollback при наличии ссылок из `Security`;
12. интеграционные тесты конкурентного назначения default-значения.

## 8. Обязательные интеграционные тесты

Спецификация миграций должна предусмотреть тесты, подтверждающие:

- невозможность создать две группы с одинаковым кодом;
- невозможность повторно использовать код soft-deleted группы;
- невозможность создать два одинаковых кода значения в одной группе;
- возможность использовать одинаковый код в разных группах;
- невозможность повторно использовать код soft-deleted значения в той же группе;
- невозможность создать два активных default-значения в одной группе;
- возможность иметь default-значения в разных группах;
- возможность назначить новый default после soft delete предыдущего;
- действие `RESTRICT` при удалении группы;
- корректную сортировку по `sort_order, id`;
- корректность идемпотентного seed;
- сохранение системных кодов после повторного запуска seed;
- корректное поведение при конкурентном назначении default-значения.

## 9. Отложенные возможности

Без изменения ERD первой версии отложены:

```text
локализация
версии справочников
иерархические значения
импорт и экспорт
произвольные metadata/JSON
сроки действия значений
история изменения отображаемых названий
```

Их добавление требует отдельной спецификации и, если меняются границы домена или модель хранения, нового ADR либо архитектурного ревью.

## 10. Решение

ERD домена `Reference` утверждена.

Разрешён переход к следующему артефакту:

```text
docs/migrations/REFERENCE-MIGRATIONS.md
```

Реализация таблиц до утверждения спецификации миграций не допускается в соответствии с Documentation First.
