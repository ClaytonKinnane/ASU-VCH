# ERD-030 — Reference

## 1. Назначение

Документ фиксирует логическую модель данных домена `Reference` после утверждения его спецификации и архитектурного ревью.

Источники требований:

- `docs/DATABASE.md`;
- `docs/domains/REFERENCE.md`;
- `docs/domains/REFERENCE-REVIEW.md`;
- ADR по справочным данным, soft delete и доменно-ориентированной архитектуре.

ERD является проектным контрактом для спецификации миграций. Изменения состава таблиц, связей и ключевых ограничений сначала вносятся в этот документ.

## 2. Границы диаграммы

Внутри домена `Reference` находятся:

```text
reference_groups
reference_values
```

Другие домены являются потребителями `reference_values`, но их таблицы в диаграмму не включаются. ERD не моделирует конкретные справочники отдельными таблицами.

В текущую версию намеренно не входят:

```text
reference_value_translations
reference_versions
reference_imports
reference_exports
reference_hierarchies
reference_metadata
```

## 3. Диаграмма

Исходный файл PlantUML:

```text
docs/erd/diagrams/reference.puml
```

Логическая структура:

```text
reference_groups 1 ─────< reference_values
```

Каждое значение принадлежит ровно одной группе. Группа может не иметь значений.

## 4. Таблицы

### 4.1 reference_groups

Назначение: каталог групп справочных значений.

| Поле | Обязательность | Назначение |
|---|---:|---|
| `id` | да | Внутренний идентификатор |
| `code` | да | Неизменяемый машинный код группы |
| `name` | да | Отображаемое название |
| `description` | нет | Описание назначения справочника |
| `is_system` | да | Признак защищённой системной группы |
| `created_at` | да | Время создания |
| `updated_at` | да | Время изменения |
| `deleted_at` | нет | Время логического удаления |

Ключи и ограничения:

- PK: `id`;
- UQ: `code`;
- `code` хранится в нижнем регистре после trim и не изменяется после публикации;
- код не переиспользуется после soft delete;
- `is_system` по умолчанию имеет значение `false`;
- системную группу нельзя удалить или изменить через обычные операции управления справочниками;
- физическое удаление опубликованной группы запрещено.

### 4.2 reference_values

Назначение: значения, принадлежащие группам справочников.

| Поле | Обязательность | Назначение |
|---|---:|---|
| `id` | да | Внутренний идентификатор |
| `group_id` | да | Группа справочника |
| `code` | да | Неизменяемый машинный код значения |
| `name` | да | Отображаемое название |
| `description` | нет | Дополнительное описание |
| `sort_order` | да | Порядок отображения внутри группы |
| `is_default` | да | Признак значения по умолчанию |
| `is_system` | да | Признак защищённого системного значения |
| `active_default_group_id` | нет | Служебная generated column для уникальности активного default-значения |
| `created_at` | да | Время создания |
| `updated_at` | да | Время изменения |
| `deleted_at` | нет | Время логического удаления |

Ключи и ограничения:

- PK: `id`;
- FK: `group_id → reference_groups.id`;
- UQ: `group_id + code`;
- `code` хранится в нижнем регистре после trim и не изменяется после публикации;
- код значения не переиспользуется в той же группе после soft delete;
- `sort_order` по умолчанию имеет значение `0`;
- `is_default` по умолчанию имеет значение `false`;
- `is_system` по умолчанию имеет значение `false`;
- одновременно в группе допускается не более одного активного значения с `is_default = true`;
- системное значение нельзя удалить или изменить через обычные операции управления справочниками;
- физическое удаление опубликованного значения запрещено.

Предлагаемое логическое выражение служебной колонки:

```text
active_default_group_id =
    IF(is_default = true AND deleted_at IS NULL, group_id, NULL)
```

Уникальный индекс по `active_default_group_id` использует способность MySQL хранить несколько `NULL` и запрещает два активных default-значения в одной группе.

Точное SQL-выражение, тип generated column и совместимость с MySQL 8.4 должны быть подтверждены в спецификации миграций и интеграционными тестами.

## 5. Кардинальности

| Связь | Кардинальность | Правило |
|---|---|---|
| `reference_groups → reference_values` | `1 : N` | Каждое значение относится ровно к одной группе |

Удалённая группа не должна иметь активных значений. Это межстрочный инвариант, обеспечиваемый доменным сервисом и тестами.

## 6. Идентичность и ссылки из других доменов

Другие домены должны хранить внешний ключ на:

```text
reference_values.id
```

Они не должны хранить `reference_values.code` как замену внешнему ключу.

`code` используется для:

- идемпотентного seed;
- поиска значения в доменной логике;
- конфигурации;
- стабильного машинного контракта;
- интеграционных тестов.

Перед назначением внешнего ключа домен-потребитель обязан проверить, что значение принадлежит требуемой группе. Обычный FK подтверждает существование значения, но не принадлежность конкретному `reference_groups.code`.

## 7. Правила default-значения

Default-значение является необязательным:

- группа может не иметь default-значения;
- группа может иметь не более одного активного default-значения;
- soft delete текущего default-значения освобождает ограничение;
- назначение нового default должно выполняться транзакционно;
- перенос default между значениями выполняется доменным сервисом;
- потребляющий домен не обязан автоматически использовать default, если это не закреплено его собственной спецификацией.

`is_default` не означает, что значение является обязательным для всех бизнес-процессов.

## 8. Правила системных данных

`is_system = true` означает, что запись является частью системного контракта.

Для системных групп и значений запрещаются обычные операции:

- изменение `code`;
- изменение `group_id` у значения;
- soft delete;
- физическое удаление;
- превращение системной записи в пользовательскую.

Изменение отображаемого `name` и `description` допускается только управляемым процессом, если это не нарушает нормативный или интеграционный контракт.

Защита `is_system` обеспечивается совокупностью:

- доменных политик;
- RBAC;
- миграций и seeders;
- аудита;
- интеграционных тестов.

Сам флаг не является самостоятельным механизмом авторизации.

## 9. Правила удаления

- обе таблицы используют soft delete;
- опубликованные коды после удаления не переиспользуются;
- внешние ключи используют `ON DELETE RESTRICT` и `ON UPDATE RESTRICT`;
- каскадное удаление запрещено;
- группу нельзя удалить, пока существуют активные значения;
- значение нельзя удалить, если его используют записи других доменов;
- восстановление записи допускается только при отсутствии конфликтов и после проверки доменных инвариантов.

Ограничение «значение используется внешним доменом» обеспечивается внешними ключами соответствующих таблиц-потребителей и доменным сервисом.

## 10. Индексы

Минимально необходимы:

```text
reference_groups(code) UNIQUE
reference_groups(deleted_at)

reference_values(group_id, code) UNIQUE
reference_values(active_default_group_id) UNIQUE
reference_values(group_id, sort_order, id)
reference_values(group_id, deleted_at)
reference_values(deleted_at)
```

Индекс `reference_values(group_id, sort_order, id)` поддерживает детерминированную выдачу значений группы.

Точные имена, длины строковых полей и физическая реализация generated column утверждаются в `REFERENCE-MIGRATIONS.md`.

## 11. Основные запросы

Модель должна эффективно поддерживать:

1. получение активной группы по `code`;
2. получение активного значения по `group code + value code`;
3. получение активного значения по `id` с проверкой группы;
4. получение всех активных значений группы в порядке `sort_order, id`;
5. получение default-значения группы;
6. административное получение записей, включая soft-deleted;
7. проверку существования кода при создании и восстановлении.

## 12. Вопросы миграционного дизайна

До реализации миграций необходимо технически утвердить:

1. SQL-типы и длины `code`, `name` и `description`;
2. типы `BOOLEAN`, `DATETIME` и timestamp precision;
3. точное выражение `active_default_group_id`;
4. `VIRTUAL` или `STORED` для generated column;
5. имена PK, FK, UQ и обычных индексов;
6. стратегию триггеров для защиты системных записей, если она потребуется;
7. порядок миграций и rollback;
8. первоначальный seed группы `user_status` и её значений;
9. интеграционные тесты ограничений MySQL 8.4.

## 13. Критерии готовности ERD

ERD готова к архитектурному ревью, если подтверждены:

- состав двух таблиц;
- обязательность полей;
- кардинальность;
- политика уникальности кодов;
- запрет повторного использования кодов;
- правило одного активного default-значения;
- soft delete;
- защита системных записей;
- отсутствие каскадного удаления;
- модель ссылок из других доменов;
- перечень вопросов для спецификации миграций.

После одобрения ERD следующим артефактом является:

```text
docs/erd/ERD-030-reference-review.md
```
