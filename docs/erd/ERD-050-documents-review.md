## Final decisions

### Aggregate boundary

`Document` is the aggregate root. `DocumentVersion`, `DocumentFile`, and `DocumentRelation` are subordinate historical entities and must not be modified independently of the aggregate rules.

### Public identifier

`documents.public_id` uses `BINARY(16)` and stores a UUID generated by the application. It is unique, required, and immutable. External integrations must prefer `public_id` over the internal numeric primary key.

### Registration number

`registration_number` is nullable only while a document is a draft. It becomes required when the document is registered and is immutable thereafter. A registration number is never reused, including after cancellation, archival, or soft deletion.

Historical uniqueness is enforced by a unique key over the applicable registration scope defined in the ERD. Soft deletion does not release the number.

### Version rules

- `version_number` starts at `1`.
- `(document_id, version_number)` is unique.
- Existing versions are immutable.
- A new content state creates a new version.
- Concurrent version creation must lock the parent document row.
- `documents.current_version_id` must refer to a version owned by the same document.

The ownership invariant for `current_version_id` must be enforced by database triggers and integration tests.

### Primary file rule

A version may temporarily have no primary file while the document is an unregistered draft. A version used to register, approve, cancel after registration, or archive a document must contain exactly one active file with the `primary` role.

Only one primary file is allowed per version. The database must enforce this with a generated nullable uniqueness key.

### File roles

File roles are reference data in group `document_file_role`.

Initial values:

- `primary`
- `attachment`

Future values may be added without schema modification. Role group membership must be validated by trigger.

### File integrity

- `sha256_hash` is mandatory and immutable.
- `mime_type` is mandatory and determined by the server.
- `storage_key` is mandatory, unique, and immutable.
- Absolute operating-system paths are forbidden in domain tables.
- Original filenames are metadata only.

### Relations

Relation types use Reference group `document_relation_type`.

Relations are directed, immutable, and unique by:

`(source_document_id, target_document_id, relation_type_id)`

Self-relations are forbidden. Reverse relations are not created automatically.

### Deletion policy

Only `documents` supports soft deletion.

A draft may be soft-deleted only when it has never been registered and is not referenced by another document relation or business object. Registered, approved, cancelled, and archived documents cannot be deleted; their lifecycle is represented by status transitions.

`document_versions`, `document_files`, and `document_relations` have no `deleted_at` column and are append-only historical records.

### Foreign keys

All foreign keys use:

- `ON DELETE RESTRICT`
- `ON UPDATE RESTRICT`

No cascade deletion is permitted.

### Immutability enforcement

Database triggers must reject UPDATE and DELETE operations on:

- `document_versions`
- `document_files`
- `document_relations`

A narrowly scoped installation or maintenance mechanism may be introduced only by a separate approved architectural decision.

### Storage consistency

MySQL and the filesystem do not share a transaction. The approved workflow is:

1. upload to temporary storage;
2. validate size, MIME type, and security policy;
3. calculate SHA-256;
4. start the database transaction;
5. insert metadata;
6. move the file to permanent storage;
7. commit the database transaction;
8. publish domain events after commit.

If the move fails, the transaction is rolled back. If the database commit fails after the move, the permanent file is removed through a compensating action. Failed compensation must be logged and made discoverable by an orphan-file reconciliation process.

## Required indexes

The ERD must include indexes supporting:

- `documents.public_id`
- registration lookup
- `documents.document_type_id`
- `documents.status_id`
- `documents.current_version_id`
- `documents.created_by_user_id`
- `documents.registered_at`
- `(document_id, version_number)`
- `(document_version_id, file_role_id)`
- file hash lookup
- `(source_document_id, relation_type_id)`
- `target_document_id`

## Security review

Confirmed requirements:

- permanent files remain outside the Apache web root;
- downloads are served only through the application authorization layer;
- paths cannot be constructed from client filenames;
- MIME type and extension supplied by the client are untrusted;
- executable uploads are rejected;
- direct public file URLs are not supported in version 1.

## Required integration tests

1. Registration without a registration number is rejected.
2. Registration without exactly one primary file is rejected.
3. A second primary file for one version is rejected.
4. A current version from another document is rejected.
5. Registered document deletion is rejected.
6. Registration number reuse is rejected after cancellation and soft deletion.
7. UPDATE and DELETE of immutable child records are rejected.
8. Reference values from incorrect groups are rejected.
9. Failed storage move rolls back database changes.
10. Failed database commit invokes file compensation.
11. Concurrent version creation produces distinct sequential versions.
12. Self-relations and duplicate relations are rejected.
