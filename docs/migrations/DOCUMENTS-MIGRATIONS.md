# Documents Migration Specification

## Status

- Domain: Documents
- Specification status: APPROVED
- Implementation ready: YES
- Source ERD: `docs/erd/ERD-050-documents.md`
- ERD review: `docs/erd/ERD-050-documents-review.md`

## Purpose

This document defines the required database migration sequence, constraints, triggers, indexes, and seed data for the Documents domain. It is a specification, not executable SQL.

## Migration order

1. Seed required Reference groups and values.
2. Create `documents` without the `current_version_id` foreign key.
3. Create `document_versions`.
4. Add `documents.current_version_id` and its foreign key.
5. Create `document_files`.
6. Create `document_relations`.
7. Create validation and immutability triggers.
8. Create supporting indexes not already created by constraints.
9. Run structural and invariant verification tests.

All migrations must be deterministic, reversible where safe, and executed in the documented order.

## Required Reference data

### Group `document_status`

Values:

- `draft` — default
- `registered`
- `approved`
- `cancelled`
- `archived`

### Group `document_type`

Initial values:

- `order`
- `act`
- `memo`
- `instruction`
- `certificate`
- `report`
- `statement`
- `other`

### Group `document_file_role`

Values:

- `primary` — default
- `attachment`

### Group `document_relation_type`

Values:

- `references`
- `supplements`
- `replaces`
- `cancels`
- `attachment_to`
- `based_on`

Seeder requirements:

- idempotent;
- lowercase immutable codes;
- no duplicate values;
- system data marked with `is_system = true` where applicable;
- exactly one active default for groups that define a default.

## Table `documents`

Required columns:

- `id BIGINT UNSIGNED AUTO_INCREMENT`
- `public_id BINARY(16) NOT NULL`
- `document_type_id BIGINT UNSIGNED NOT NULL`
- `status_id BIGINT UNSIGNED NOT NULL`
- `registration_number VARCHAR(191) NULL`
- `title VARCHAR(255) NOT NULL`
- `description TEXT NULL`
- `document_date DATE NULL`
- `registered_at DATETIME(6) NULL`
- `current_version_id BIGINT UNSIGNED NULL`
- `created_by_user_id BIGINT UNSIGNED NOT NULL`
- `created_at DATETIME(6) NOT NULL`
- `updated_at DATETIME(6) NOT NULL`
- `deleted_at DATETIME(6) NULL`

Constraints:

- primary key on `id`;
- unique key on `public_id`;
- historical unique registration key according to the registration scope defined by the ERD;
- foreign key to `reference_values(id)` for type and status;
- foreign key to `users(id)` for creator;
- later-added foreign key to `document_versions(id)` for current version;
- all FKs use `ON DELETE RESTRICT ON UPDATE RESTRICT`.

Normalization rules:

- `registration_number` is trimmed before persistence;
- blank registration numbers are stored as `NULL`;
- `public_id` is generated by the application and never changed;
- title must not be blank after trimming.

Indexes:

- unique `public_id`;
- registration lookup index/unique constraint;
- `document_type_id`;
- `status_id`;
- `current_version_id`;
- `created_by_user_id`;
- `registered_at`;
- `deleted_at` where useful for active-record queries.

## Table `document_versions`

Required columns:

- `id BIGINT UNSIGNED AUTO_INCREMENT`
- `document_id BIGINT UNSIGNED NOT NULL`
- `version_number INT UNSIGNED NOT NULL`
- `change_summary VARCHAR(1000) NULL`
- `created_by_user_id BIGINT UNSIGNED NOT NULL`
- `created_at DATETIME(6) NOT NULL`

Constraints:

- primary key on `id`;
- unique `(document_id, version_number)`;
- foreign keys to `documents(id)` and `users(id)`;
- `version_number >= 1` through CHECK where supported and trigger/application validation as defense in depth;
- all FKs use RESTRICT.

No `updated_at` or `deleted_at` columns are permitted because records are immutable.

Indexes:

- unique `(document_id, version_number)`;
- `created_by_user_id`;
- `created_at` if required by version-history queries.

## `documents.current_version_id`

After `document_versions` exists:

- add nullable `current_version_id`;
- add index;
- add FK to `document_versions(id)` with RESTRICT;
- install triggers that ensure the referenced version belongs to the same document.

A cyclic FK structure is accepted only because migration order and RESTRICT behavior are explicitly defined.

## Table `document_files`

Required columns:

- `id BIGINT UNSIGNED AUTO_INCREMENT`
- `document_version_id BIGINT UNSIGNED NOT NULL`
- `file_role_id BIGINT UNSIGNED NOT NULL`
- `original_filename VARCHAR(255) NOT NULL`
- `storage_key VARCHAR(512) NOT NULL`
- `mime_type VARCHAR(191) NOT NULL`
- `size_bytes BIGINT UNSIGNED NOT NULL`
- `sha256_hash BINARY(32) NOT NULL`
- `primary_version_id BIGINT UNSIGNED GENERATED ALWAYS AS (CASE WHEN file_role represents primary THEN document_version_id ELSE NULL END) STORED`
- `created_at DATETIME(6) NOT NULL`

Because a generated column cannot safely derive Reference semantics by joining another table, implementation must use one of these approved mechanisms:

1. persist a system-controlled technical boolean `is_primary` validated against `file_role_id`, then generate `primary_version_id` from it; or
2. use a trigger-maintained nullable `primary_version_id` column.

The selected implementation must be documented in the executable migration and preserve the invariant without relying only on application code.

Constraints:

- primary key on `id`;
- unique `storage_key`;
- unique nullable `primary_version_id` to allow only one primary file per version;
- foreign keys to `document_versions(id)` and `reference_values(id)`;
- `size_bytes > 0` unless zero-byte files are explicitly authorized by a later decision;
- all FKs use RESTRICT.

Indexes:

- `document_version_id`;
- `(document_version_id, file_role_id)`;
- `file_role_id`;
- `sha256_hash`;
- unique `storage_key`;
- unique primary-version key.

No `updated_at` or `deleted_at` columns are permitted.

## Table `document_relations`

Required columns:

- `id BIGINT UNSIGNED AUTO_INCREMENT`
- `source_document_id BIGINT UNSIGNED NOT NULL`
- `target_document_id BIGINT UNSIGNED NOT NULL`
- `relation_type_id BIGINT UNSIGNED NOT NULL`
- `created_by_user_id BIGINT UNSIGNED NOT NULL`
- `created_at DATETIME(6) NOT NULL`

Constraints:

- primary key on `id`;
- unique `(source_document_id, target_document_id, relation_type_id)`;
- CHECK `source_document_id <> target_document_id`, reinforced by trigger;
- FKs to both documents, Reference, and users;
- all FKs use RESTRICT.

Indexes:

- `(source_document_id, relation_type_id)`;
- `target_document_id`;
- `relation_type_id`;
- `created_by_user_id`.

No `updated_at` or `deleted_at` columns are permitted.

## Required triggers

Trigger names must follow project naming standards.

### Reference-group validation

Before INSERT and UPDATE on `documents`:

- `document_type_id` must be an active value in `document_type`;
- `status_id` must be an active value in `document_status`.

Before INSERT on `document_files`:

- `file_role_id` must be an active value in `document_file_role`.

Before INSERT on `document_relations`:

- `relation_type_id` must be an active value in `document_relation_type`.

### Current-version ownership

Before INSERT/UPDATE of `documents.current_version_id`:

- allow NULL for a draft without versions;
- otherwise require the referenced version's `document_id` to equal `documents.id`.

### Registration lifecycle

Before UPDATE on `documents`:

- reject changes to `public_id`;
- reject changes to `registration_number` after first registration;
- reject clearing `registered_at` after registration;
- require registration number, registration timestamp, current version, and exactly one primary file when entering `registered` or a later state;
- reject prohibited reverse lifecycle transitions;
- reject soft deletion when the document has ever been registered;
- reject soft deletion when relations reference the document.

The trigger may use status codes resolved through Reference rather than hard-coded numeric IDs.

### Immutable child tables

Reject all UPDATE and DELETE operations on:

- `document_versions`;
- `document_files`;
- `document_relations`.

### Relation validation

Before INSERT on `document_relations`:

- reject self-relation;
- validate relation type group;
- reject links to soft-deleted documents unless explicitly allowed by the approved domain lifecycle.

## Transaction requirements

### Create version

1. begin transaction;
2. lock parent document with `SELECT ... FOR UPDATE`;
3. calculate the next version number;
4. insert version;
5. insert validated files;
6. set `current_version_id`;
7. commit;
8. publish events after commit.

### File persistence

File storage follows the temporary-upload and compensation workflow approved by the ERD review. Database migrations do not manage physical files but must support reconciliation through unique `storage_key`, hash, and timestamps.

## Rollback policy

Rollback is permitted during development before production data exists.

Once production documents exist:

- migrations must not drop Documents tables as routine rollback;
- immutable records must never be rewritten to support rollback;
- destructive rollback requires a separately approved recovery plan and verified backup.

Reference seed rollback must not delete values already used by domain rows.

## Verification queries and tests

The implementation phase must provide automated verification for:

- expected columns and data types;
- FK actions are RESTRICT;
- required unique keys and indexes exist;
- incorrect Reference groups are rejected;
- duplicate public IDs and registration numbers are rejected;
- cross-document current versions are rejected;
- duplicate primary files are rejected;
- immutable table UPDATE/DELETE is rejected;
- registered document soft deletion is rejected;
- concurrent version numbering is safe;
- document relations reject self-links and duplicates.

## Implementation gate

Implementation may start only when:

- executable migrations match this specification;
- seeders are idempotent;
- trigger SQL is reviewed;
- migration tests cover every listed invariant;
- storage configuration remains outside the database schema;
- no MySQL ENUM is introduced.
