# Спецификация миграций Reference

## 1. Статус и назначение

Документ определяет физическую модель миграций домена `Reference` и является обязательным контрактом для последующей реализации миграций, seeders, репозиториев и интеграционных тестов.

Источники требований:

- `docs/DATABASE.md`;
- `docs/NAMING.md`;
- `docs/domains/REFERENCE.md`;
- `docs/domains/REFERENCE-REVIEW.md`;
- `docs/erd/ERD-030-reference.md`;
- `docs/erd/ERD-030-reference-review.md`.

SQL и PHP-код не должны расходиться с этой спецификацией. Изменение структуры, ограничений или системных seed-данных сначала вносится в архитектурную документацию.

## 2. Зависимости

Домен `Reference` не зависит от таблиц других прикладных доменов.

До выполнения миграций должны быть доступны только:

- подключение к MySQL 8.4;
- механизм миграций приложения;
- общесистемная конфигурация charset, collation и UTC.

Миграции `Reference` должны выполняться до миграций доменов, которые создают внешние ключи на `reference_values.id`.

## 3. Общие параметры хранения

- СУБД: MySQL 8.4.
- Engine: InnoDB.
- Character set: `utf8mb4`.
- Общая collation текстовых полей: единая collation проекта.
- Машинные коды используют ASCII lower-case и сравниваются регистронезависимо.
- Время хранится в UTC.
- MySQL `ENUM` не используется.
- Первичные идентификаторы: `BIGINT UNSIGNED AUTO_INCREMENT`.
- Временные поля: `DATETIME(6)`.
- Булевы поля: `BOOLEAN`, физически совместимый с `TINYINT(1)`.
- Все FK используют `ON DELETE RESTRICT` и `ON UPDATE RESTRICT`.
- Каскадное удаление запрещено.

## 4. Порядок миграций

```text
001_create_reference_groups_table
002_create_reference_values_table
003_add_reference_values_default_generated_column
004_add_reference_indexes
```

Системные данные не смешиваются со структурными миграциями.

После структурных миграций выполняются:

```text
ReferenceGroupSeeder
ReferenceValueSeeder
```

Seeders обязаны быть идемпотентными по неизменяемым machine codes.

## 5. Таблица reference_groups

### 5.1 Колонки

| Поле | Тип | Null | Default |
|---|---|---:|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT | нет | — |
| `code` | VARCHAR(128) | нет | — |
| `name` | VARCHAR(255) | нет | — |
| `description` | TEXT | да | NULL |
| `is_system` | BOOLEAN/TINYINT(1) | нет | 0 |
| `created_at` | DATETIME(6) | нет | — |
| `updated_at` | DATETIME(6) | нет | — |
| `deleted_at` | DATETIME(6) | да | NULL |

### 5.2 Ограничения и индексы

```text
pk_reference_groups
uq_reference_groups_code
idx_reference_groups_deleted_at
```

Правила:

- PK: `id`.
- `code` уникален глобально.
- `code` хранится после `trim` в нижнем регистре.
- Допустимый формат кода: `^[a-z][a-z0-9_]*$`.
- Код не изменяется после публикации.
- Код не переиспользуется после soft delete.
- `name` после trim не может быть пустой строкой.
- `is_system = 1` означает системный контракт.
- Опубликованные группы не удаляются физически в обычном жизненном цикле.

Уникальность `code` распространяется на все строки, включая soft-deleted. Для этого используется обычный уникальный индекс без участия `deleted_at`.

## 6. Таблица reference_values

### 6.1 Колонки

| Поле | Тип | Null | Default |
|---|---|---:|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT | нет | — |
| `group_id` | BIGINT UNSIGNED | нет | — |
| `code` | VARCHAR(128) | нет | — |
| `name` | VARCHAR(255) | нет | — |
| `description` | TEXT | да | NULL |
| `sort_order` | INT UNSIGNED | нет | 0 |
| `is_default` | BOOLEAN/TINYINT(1) | нет | 0 |
| `is_system` | BOOLEAN/TINYINT(1) | нет | 0 |
| `active_default_group_id` | BIGINT UNSIGNED GENERATED ALWAYS | да | generated |
| `created_at` | DATETIME(6) | нет | — |
| `updated_at` | DATETIME(6) | нет | — |
| `deleted_at` | DATETIME(6) | да | NULL |

### 6.2 Generated column

Точное выражение:

```sql
IF(
    `is_default` = 1 AND `deleted_at` IS NULL,
    `group_id`,
    NULL
)
```

Колонка:

```text
active_default_group_id BIGINT UNSIGNED
GENERATED ALWAYS AS (...) STORED
```

Для первой реализации утверждается `STORED`, чтобы поведение индексирования было явным и одинаково проверяемым через migration framework и MySQL 8.4.

Уникальный индекс:

```text
uq_reference_values_active_default
UNIQUE (active_default_group_id)
```

MySQL допускает несколько `NULL` в уникальном индексе. Поэтому индекс запрещает более одного активного значения с `is_default = 1` в одной группе, но не ограничивает обычные значения и soft-deleted defaults.

### 6.3 Ограничения и индексы

```text
pk_reference_values
uq_reference_values_group_code
uq_reference_values_active_default
idx_reference_values_group_sort
idx_reference_values_group_deleted
idx_reference_values_deleted_at
fk_reference_values_group_id_reference_groups
```

Определения:

```text
PRIMARY KEY (id)
UNIQUE (group_id, code)
UNIQUE (active_default_group_id)
INDEX (group_id, sort_order, id)
INDEX (group_id, deleted_at)
INDEX (deleted_at)
```

Правила:

- `code` уникален внутри группы.
- Одинаковый `code` допустим в разных группах.
- `code` хранится после `trim` в нижнем регистре.
- Допустимый формат кода: `^[a-z][a-z0-9_]*$`.
- `code` не изменяется после публикации.
- Пара `group_id + code` не переиспользуется после soft delete.
- `group_id` у опубликованного значения не изменяется.
- `name` после trim не может быть пустой строкой.
- `sort_order` не может быть отрицательным.
- `is_default` и `is_system` принимают только `0` или `1`.
- Физическое удаление опубликованных значений запрещено в обычном жизненном цикле.

### 6.4 Внешний ключ

```text
fk_reference_values_group_id_reference_groups
```

Связь:

```text
reference_values.group_id → reference_groups.id
```

Поведение:

```text
ON DELETE RESTRICT
ON UPDATE RESTRICT
```

## 7. CHECK-ограничения

MySQL 8.4 поддерживает исполняемые `CHECK`. Создаются именованные ограничения:

```text
chk_reference_groups_code_not_blank
chk_reference_groups_name_not_blank
chk_reference_groups_is_system

chk_reference_values_code_not_blank
chk_reference_values_name_not_blank
chk_reference_values_is_default
chk_reference_values_is_system
```

Минимальные выражения:

```sql
CHAR_LENGTH(TRIM(`code`)) > 0
CHAR_LENGTH(TRIM(`name`)) > 0
`is_system` IN (0, 1)
`is_default` IN (0, 1)
```

Формат machine code проверяется прикладным слоем. При подтверждённой стабильной поддержке regexp в `CHECK` допускается усиление ограничения отдельной последующей миграцией, но оно не является условием первой реализации.

## 8. Нормализация данных

До записи прикладной сервис обязан:

- выполнить `trim` для `code` и `name`;
- привести `code` к lower-case;
- отклонить пустой `code` и пустой `name`;
- проверить формат `code`;
- не преобразовывать отображаемый `name` в lower-case;
- преобразовать пустое необязательное `description` в `NULL` согласно общей политике проекта.

База данных обеспечивает целостность и уникальность, но не заменяет прикладную нормализацию.

## 9. Защита системных записей

В первой версии триггеры защиты `is_system` не создаются.

Запрет обычного изменения и удаления системных записей обеспечивается:

- доменными сервисами;
- authorization policies и RBAC;
- отсутствием публичных репозиторных операций обхода;
- аудитом;
- интеграционными тестами.

Миграции и управляемые system seeders могут обновлять отображаемые атрибуты системных записей при сохранении machine code и идентичности.

Триггеры защиты допускаются только отдельным архитектурным решением, если прикладной контроль окажется недостаточным. Они не должны мешать rollback, восстановлению backup и управляемому обновлению системного каталога.

## 10. Межстрочные и междоменные инварианты

Следующие правила не выражаются одним обычным FK и обеспечиваются доменными сервисами и тестами:

- удалённая группа не имеет активных значений;
- группу нельзя soft-delete, пока существуют активные значения;
- значение нельзя soft-delete, если оно используется таблицей домена-потребителя;
- восстановление группы или значения разрешено только при отсутствии конфликтов;
- перенос default-значения выполняется транзакционно;
- другой домен обязан проверить принадлежность `reference_values.id` требуемой группе;
- `is_system` нельзя сбросить обычной пользовательской операцией.

Внешние таблицы-потребители обязаны создавать FK на `reference_values.id` с `RESTRICT`.

## 11. Системные seed-данные

### 11.1 Группа user_status

```text
code: user_status
name: Статусы пользователей
is_system: true
```

### 11.2 Значения user_status

| code | name | sort_order | is_default | is_system |
|---|---|---:|---:|---:|
| `pending` | Ожидает активации | 10 | 1 | 1 |
| `active` | Активен | 20 | 0 | 1 |
| `blocked` | Заблокирован | 30 | 0 | 1 |
| `disabled` | Отключён | 40 | 0 | 1 |

`pending` утверждается default-значением группы `user_status` для создания новых учетных записей. Потребляющий домен всё равно обязан явно закрепить использование default в своём use case.

### 11.3 Идемпотентность seeders

Seeder ищет записи по machine code:

```text
reference_groups.code
reference_values(group_id, code)
```

Повторный запуск:

- не создаёт дубликаты;
- не изменяет `id` существующих записей;
- не переиспользует soft-deleted коды автоматически;
- проверяет, что существующая системная запись принадлежит ожидаемой группе;
- восстанавливает или изменяет soft-deleted системную запись только через явно утверждённую стратегию установки;
- не сбрасывает пользовательские значения справочников.

При конфликте machine code с несовместимой записью установка должна завершиться ошибкой, а не молча переписать данные.

## 12. Транзакционность default-значения

Перенос default внутри группы выполняется одной транзакцией.

Предпочтительный порядок:

1. заблокировать активные значения группы, участвующие в операции;
2. снять `is_default` с текущего значения;
3. назначить `is_default` новому значению;
4. зафиксировать транзакцию.

Уникальный индекс является последней линией защиты от конкурентного создания двух defaults.

При конкурирующих операциях одна транзакция должна завершиться успешно, а вторая — получить контролируемую ошибку уникальности или повторить операцию в соответствии с общей retry-политикой.

## 13. Rollback

Порядок rollback структурных миграций:

```text
1. удалить зависимые FK внешних доменов, если они уже существуют;
2. удалить индексы и generated column reference_values;
3. удалить таблицу reference_values;
4. удалить таблицу reference_groups.
```

Rollback seeders не выполняется автоматически в рабочей среде.

Причины:

- значения могут уже использоваться другими доменами;
- удаление системных reference IDs нарушит внешние ключи;
- автоматический откат данных опаснее отказа rollback.

Полный destructive rollback допускается только в тестовой или локальной среде после явной проверки отсутствия зависимостей.

## 14. Валидация после миграции

После применения миграций автоматически проверяются:

- наличие обеих таблиц;
- engine InnoDB;
- charset и collation;
- типы и nullable-свойства колонок;
- PK и AUTO_INCREMENT;
- FK и правила `RESTRICT`;
- уникальность `reference_groups.code`;
- уникальность `reference_values(group_id, code)`;
- generated expression `active_default_group_id`;
- уникальный индекс default-значения;
- обычные индексы;
- CHECK-ограничения;
- seed группы `user_status`;
- seed четырёх статусов;
- единственное active default-значение `pending`;
- идемпотентность повторного запуска seeders.

## 15. Интеграционные тесты

Минимальный обязательный набор:

1. Создание группы с уникальным `code` успешно.
2. Вторая группа с тем же `code` отклоняется.
3. Код удалённой группы нельзя использовать повторно.
4. Одинаковый value code в разных группах разрешён.
5. Одинаковый value code в одной группе отклоняется.
6. Код soft-deleted значения нельзя использовать повторно в той же группе.
7. Значение без существующей группы создать нельзя.
8. Удаление группы с существующими значениями блокируется FK или доменной политикой.
9. Два активных defaults в одной группе создать нельзя.
10. Defaults в разных группах разрешены.
11. Soft delete текущего default освобождает ограничение.
12. После soft delete прежнего default можно назначить новый.
13. Восстановление прежнего default при наличии нового отклоняется.
14. Конкурентное назначение двух defaults сохраняет не более одного.
15. Системную группу нельзя изменить или удалить обычным use case.
16. Системное значение нельзя переместить, изменить code или удалить обычным use case.
17. Повторный запуск seeders не создаёт дубликатов.
18. Seeder обнаруживает несовместимый конфликт machine code и завершает операцию ошибкой.
19. Выдача значений группы детерминирована по `sort_order, id`.
20. Домен-потребитель не может физически удалить используемое reference value из-за `RESTRICT`.

## 16. Критерии готовности реализации

Миграции готовы к реализации, если:

- документ утверждён;
- имена таблиц, колонок, ограничений и индексов зафиксированы;
- generated column подтверждена для MySQL 8.4;
- seed-каталог утверждён;
- rollback-политика утверждена;
- интеграционные сценарии приняты;
- реализация не требует изменения ERD.

## 17. Решения, отложенные за пределы v1

В первую версию не входят:

```text
reference_value_translations
reference_versions
reference_imports
reference_exports
reference_hierarchies
reference_metadata
```

Также не вводятся:

- generic JSON-поля;
- parent-child иерархия;
- автоматическая локализация;
- отдельная таблица истории изменений Reference;
- database triggers для полной защиты `is_system`.

История изменений обеспечивается доменом `Audit`, а расширение модели требует отдельного архитектурного цикла.
