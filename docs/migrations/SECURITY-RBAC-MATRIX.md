# Начальная матрица RBAC домена Security

## 1. Статус и назначение

Документ утверждает начальную матрицу разрешений для системных ролей домена `Security`.

Матрица используется как обязательный контракт для реализации:

```text
SecurityRoleSeeder
SecurityPermissionSeeder
SecurityRolePermissionSeeder
AuthorizationService
Policy
интеграционных тестов доступа
```

Источники требований:

- `docs/domains/SECURITY.md`;
- `docs/domains/SECURITY-REVIEW.md`;
- `docs/erd/ERD-010-security.md`;
- `docs/erd/ERD-010-security-review.md`;
- `docs/migrations/SECURITY-MIGRATIONS.md`;
- `docs/migrations/SECURITY-RBAC-REVIEW.md`.

## 2. Начальные роли

В первой версии существуют четыре системные роли:

```text
system_owner
administrator
operator
viewer
```

Обычных эксплуатационных ролей три:

```text
administrator
operator
viewer
```

Дополнительные роли не создаются до появления подтвержденной бизнес-потребности.

Все четыре начальные роли создаются как системные:

```text
is_system = true
```

Их машинные коды неизменяемы. Системные роли нельзя физически удалить, переименовать или преобразовать в пользовательские роли.

## 3. Каталог разрешений Security

Утверждается следующий начальный каталог:

```text
security.users.view
security.users.create
security.users.update
security.users.block
security.users.disable
security.users.delete
security.roles.view
security.roles.create
security.roles.update
security.roles.assign
security.roles.revoke
security.permissions.view
security.permissions.manage
security.owner.transfer
```

Все разрешения имеют:

```text
module = security
is_system = true
```

Коды разрешений являются неизменяемым системным контрактом.

## 4. Семантика ролей

### 4.1 system_owner

`system_owner` — единственный владелец установленной системы.

Авторизация использует утвержденный policy short-circuit: действующий владелец получает полный доступ независимо от наличия отдельных строк в `role_permissions`.

Ограничения short-circuit:

- он не отменяет аутентификацию;
- он не отменяет проверку статуса пользователя;
- он не отменяет CSRF-защиту;
- он не отменяет валидацию команд;
- он не отменяет аудит;
- он не позволяет нарушать инвариант единственного владельца.

`security.owner.transfer` является семантическим разрешением критической операции, но само по себе не дает обычной роли права передавать владение. Операция дополнительно требует, чтобы текущий пользователь был действующим `system_owner`.

### 4.2 administrator

`administrator` управляет учетными записями, ролями и каталогом разрешений, но не может:

- передавать роль `system_owner`;
- назначать или отзывать роль `system_owner`;
- блокировать, отключать или удалять действующего владельца;
- изменять защищенные свойства системных ролей и разрешений;
- обходить аудит и доменные инварианты.

### 4.3 operator

`operator` выполняет повседневное администрирование учетных записей без управления моделью RBAC.

Он может просматривать пользователей, создавать учетные записи, изменять разрешенные реквизиты и блокировать учетные записи.

Он не может:

- отключать или логически удалять учетные записи;
- создавать или изменять роли;
- назначать или отзывать роли;
- управлять разрешениями;
- передавать владение.

### 4.4 viewer

`viewer` имеет только доступ на чтение к данным Security.

Он не может изменять пользователей, роли, разрешения и назначения ролей.

## 5. Матрица разрешений

Обозначения:

```text

— — разрешение не назначается роли
S — доступ через policy short-circuit system_owner
```

| Разрешение | system_owner | administrator | operator | viewer |
|---|:---:|:---:|:---:|:---:|
| `security.users.view` | S | ✓ | ✓ | ✓ |
| `security.users.create` | S | ✓ | ✓ | — |
| `security.users.update` | S | ✓ | ✓ | — |
| `security.users.block` | S | ✓ | ✓ | — |
| `security.users.disable` | S | ✓ | — | — |
| `security.users.delete` | S | ✓ | — | — |
| `security.roles.view` | S | ✓ | — | ✓ |
| `security.roles.create` | S | ✓ | — | — |
| `security.roles.update` | S | ✓ | — | — |
| `security.roles.assign` | S | ✓ | — | — |
| `security.roles.revoke` | S | ✓ | — | — |
| `security.permissions.view` | S | ✓ | — | ✓ |

## 6. Явные ограничения поверх матрицы

Наличие разрешения не является единственным условием выполнения операции.

### 6.1 Управление владельцем

Только действующий `system_owner` может:

- передать владение другому активному пользователю;
- назначить роль `system_owner` в рамках транзакции передачи;
- отозвать собственное назначение `system_owner` в рамках той же транзакции.

Нельзя выполнить отдельное назначение или отзыв `system_owner` через обычные операции `roles.assign` и `roles.revoke`.

### 6.2 Защита системных объектов

Даже `administrator` не может:

- изменить `roles.code` системной роли;
- удалить системную роль;
- изменить `permissions.code` системного разрешения;
- удалить опубликованное системное разрешение;
- снять с себя последнюю роль, необходимую для завершения текущей критической операции, если это нарушает доменный инвариант.

### 6.3 Операции над собственной учетной записью

Пользователь не может через обычное администрирование:

- заблокировать самого себя;
- отключить самого себя;
- логически удалить самого себя;
- отозвать собственную критическую роль, если операция оставит систему без администратора или владельца согласно действующим политикам.

Изменение собственного пароля и профиля регулируется отдельными use case и не выводится из разрешения `security.users.update` автоматически.

### 6.4 Область действия operator

`security.users.update` для роли `operator` не включает:

- изменение статуса на `disabled`;
- логическое удаление;
- изменение назначений ролей;
- изменение пароля без специализированного сценария сброса;
- изменение защищенных атрибутов владельца системы.

Точные изменяемые поля фиксируются в API/UI Specification.

### 6.5 Область чтения viewer

Роль `viewer` может просматривать:

- список и карточки пользователей;
- назначенные пользователям роли;
- каталог ролей;
- каталог разрешений.

Секреты и чувствительные технические данные не выдаются независимо от `security.users.view`:

```text
password_hash
временные пароли
токены
секреты MFA
служебные данные сессий
```

## 7. Правила seeder

`SecurityRolePermissionSeeder` выполняется идемпотентно по кодам ролей и разрешений.

Seeder должен:

1. проверить наличие всех системных ролей;
2. проверить наличие всех системных разрешений;
3. создать недостающие связи для `administrator`, `operator` и `viewer`;
4. удалить только лишние системные seed-связи, если включен режим строгой синхронизации;
5. не удалять пользовательские роли и их связи;
6. не назначать роль пользователям;
7. не создавать первого владельца;
8. фиксировать результат синхронизации в Audit или установочном журнале.

Для `system_owner` строки полного набора разрешений в `role_permissions` не обязательны. Источником полного доступа является policy short-circuit.

## 8. Проверки и тесты

Обязательные проверки:

- `administrator` получает все разрешения Security, кроме `security.owner.transfer`;
- `operator` получает только `users.view`, `users.create`, `users.update`, `users.block`;
- `viewer` получает только `users.view`, `roles.view`, `permissions.view`;
- обычная роль не получает `security.owner.transfer`;
- `administrator` не может назначить или отозвать `system_owner`;
- `operator` не может изменять роли и разрешения;
- `viewer` не может выполнять операции записи;
- `system_owner` проходит authorization short-circuit;
- заблокированный, отключенный или удаленный владелец не проходит аутентификацию и авторизацию;
- передача владения сохраняет ровно одного действующего владельца;
- все отказанные и успешные критические операции аудируются.

## 9. Решение

Начальная матрица RBAC домена `Security` утверждена.

Она закрывает последний содержательный вопрос спецификации миграций и разблокирует реализацию:

```text
SecurityRoleSeeder
SecurityPermissionSeeder
SecurityRolePermissionSeeder
```

Следующий этап — техническое ревью `docs/migrations/SECURITY-MIGRATIONS.md`, после которого могут создаваться структурные миграции и интеграционные тесты. Контроллеры и пользовательский интерфейс на этом этапе не реализуются.
