# Решение по начальному каталогу ролей Security

## 1. Статус

Начальный каталог ролей домена `Security` утвержден для первой версии АСУ-ВЧ.

Решение дополняет:

```text
docs/domains/SECURITY.md
docs/domains/SECURITY-REVIEW.md
docs/erd/ERD-010-security.md
docs/erd/ERD-010-security-review.md
docs/migrations/SECURITY-MIGRATIONS.md
```

## 2. Утвержденные роли

В первой версии создаются четыре системно определенных кода ролей:

```text
system_owner
administrator
operator
viewer
```

При этом `system_owner` является специальной системной ролью владельца и не рассматривается как обычная эксплуатационная роль.

Набор обычных начальных ролей ограничивается тремя ролями:

```text
administrator
operator
viewer
```

Дополнительные роли на текущем этапе не создаются.

## 3. Назначение ролей

### system_owner

Единственный владелец системы.

Особенности:

- существует ровно одно действующее назначение;
- роль создается как системная;
- передача выполняется отдельной транзакционной операцией;
- авторизация может использовать утвержденный policy short-circuit;
- роль не назначается обычным административным сценарием.

### administrator

Административное управление системой в пределах явно назначенных разрешений.

Роль не получает автоматически специальных полномочий владельца, включая передачу владения, если это право явно не утверждено в матрице разрешений.

### operator

Выполнение повседневных прикладных операций.

Роль не должна получать полномочия управления системными ролями, разрешениями или владельцем системы.

### viewer

Просмотр разрешенных данных без изменяющих операций.

Роль должна соответствовать принципу read-only, кроме технических действий, необходимых для собственной аутентифицированной сессии.

## 4. Правила расширения каталога

Новая роль не добавляется непосредственно в seeder или программный код.

Перед добавлением новой роли требуется:

1. зафиксировать бизнес-потребность;
2. определить границы ответственности роли;
3. утвердить код и отображаемое название;
4. определить матрицу разрешений;
5. проверить отсутствие дублирования существующих ролей;
6. обновить доменную и миграционную документацию;
7. при существенном изменении модели доступа оформить ADR.

Коды опубликованных ролей считаются системным контрактом и не переименовываются без миграционного плана.

## 5. Seed-правила

`SecurityRoleSeeder` должен идемпотентно создавать или синхронизировать только следующие роли:

```text
system_owner
administrator
operator
viewer
```

Не допускаются:

- автоматическое создание дополнительных ролей «на будущее»;
- создание ролей из UI до появления утвержденного сценария управления пользовательскими ролями;
- неявное копирование разрешений между ролями;
- определение полномочий по отображаемому названию вместо неизменяемого `code`.

## 6. Оставшийся вопрос

Количество и состав начальных ролей утверждены.

До реализации `SecurityRolePermissionSeeder` остается отдельно утвердить только распределение разрешений между:

```text
administrator
operator
viewer
```

Это решение определит содержимое `role_permissions`, но не изменит каталог ролей или структуру ERD.

## 7. Итог

Для первой версии принимается модель:

```text
1 специальная роль владельца
+
3 обычные эксплуатационные роли
```

Создание иных ролей откладывается до появления подтвержденной бизнес-потребности.
