# Security / Users Management v1.0

Статус: **Draft for review**  
Домен: **Security**  
Подход: **Documentation First**

## 1. Назначение

Документ определяет границы, модель данных, каталог разрешений, бизнес-правила и критерии приемки первой версии административного модуля управления учетными записями АСУ-ВЧ.

Модуль отвечает за:

- аутентификационные учетные записи;
- состояние доступа пользователя;
- роли;
- разрешения;
- назначение ролей пользователям;
- защиту системного владельца;
- административные операции над учетными записями.

Модуль не хранит предметные сведения о военнослужащем или сотруднике.

## 2. Граница доменов

### 2.1 Security

Security отвечает на вопросы:

- кто может войти в систему;
- активна ли учетная запись;
- какие роли назначены пользователю;
- какие действия разрешены пользователю.

Основные сущности:

- `users`;
- `roles`;
- `permissions`;
- `user_roles`;
- `role_permissions`.

### 2.2 Personnel

Personnel будет отвечать за реальные персональные и служебные сведения:

- ФИО;
- личный номер;
- воинское звание;
- должность;
- подразделение;
- контактные сведения;
- историю службы.

Будущая связь:

```text
users 1 ─── 0..1 user_profiles
```

`user_profiles` не входит в эту спецификацию.

## 3. Область версии 1.0

Администратор должен иметь возможность:

- просматривать список пользователей;
- искать пользователей по логину, отображаемому имени и email;
- открывать карточку пользователя;
- создавать учетную запись;
- изменять логин, email и отображаемое имя;
- блокировать и разблокировать учетную запись;
- назначать и снимать роли;
- устанавливать временный пароль;
- требовать смену пароля при следующем входе;
- видеть дату последнего входа и состояние учетной записи.

## 4. Вне области версии 1.0

Не реализуются:

- LDAP;
- Active Directory;
- SSO;
- двухфакторная аутентификация;
- внешние поставщики идентификации;
- группы пользователей;
- сложное наследование ролей;
- делегирование полномочий;
- полноценный журнал аудита безопасности;
- профиль военнослужащего или сотрудника.

## 5. Текущая модель данных

Миграция `001_starter_security.sql` уже создает базовые таблицы RBAC. Новая миграция не должна создавать их повторно.

### 5.1 users

Текущие поля:

```text
id
username
username_canonical
email
email_canonical
password_hash
display_name
is_active
is_temporary
must_change_password
last_login_at
created_at
updated_at
deleted_at
```

Правила:

- `username_canonical` уникален;
- `email_canonical` уникален при наличии email;
- пароли хранятся только как безопасный хэш;
- физическое удаление учетной записи через интерфейс не выполняется;
- архивирование выражается через `deleted_at`;
- `display_name` относится к учетной записи и не заменяет профиль человека.

### 5.2 Состояния учетной записи

Состояние интерфейса вычисляется из существующих полей:

| Состояние | Условие |
|---|---|
| Активен | `is_active = 1` и `deleted_at IS NULL` |
| Заблокирован | `is_active = 0` и `deleted_at IS NULL` |
| Временная учетная запись | `is_temporary = 1` |
| Требуется смена пароля | `must_change_password = 1` |
| Архивирован | `deleted_at IS NOT NULL` |

Отдельное поле `status` в версии 1.0 не добавляется.

### 5.3 roles

Поля:

```text
id
code
name
description
is_system
created_at
updated_at
```

Начальный набор ролей:

| Код | Назначение | Системная |
|---|---|---|
| `system_owner` | Абсолютный владелец системы | Да |
| `administrator` | Администрирование системы | Да |
| `operator` | Рабочие операции | Да |
| `viewer` | Просмотр разрешенных данных | Да |

### 5.4 permissions

Поля:

```text
id
code
name
description
is_system
created_at
updated_at
```

Формат кода:

```text
<domain>.<resource>.<action>
```

Примеры:

```text
security.users.view
security.users.create
security.users.update
security.users.block
system.settings.view
```

Специальное разрешение:

```text
system.*.*
```

Оно предоставляет полный доступ владельцу системы.

### 5.5 user_roles

Текущие поля:

```text
user_id
role_id
assigned_at
```

Составной первичный ключ:

```text
(user_id, role_id)
```

Миграция `002_security_users_management.sql` должна добавить:

```text
assigned_by BIGINT UNSIGNED NULL
```

Связь:

```text
assigned_by -> users.id
ON DELETE SET NULL
```

`NULL` допустим для bootstrap, миграций и системных назначений.

### 5.6 role_permissions

Текущие поля:

```text
role_id
permission_id
assigned_at
```

Составной первичный ключ:

```text
(role_id, permission_id)
```

Миграция должна добавить:

```text
assigned_by BIGINT UNSIGNED NULL
```

Связь и причины совпадают с `user_roles.assigned_by`.

## 7. Матрица начальных ролей

### system_owner

- получает `system.*.*`;
- полный доступ ко всем текущим и будущим действиям;
- не зависит от явного перечисления остальных разрешений.

### administrator

Получает:

```text
security.users.view
security.users.create
security.users.update
security.users.block
security.users.archive
security.users.reset_password
security.users.assign_roles
security.roles.view
security.roles.create
security.roles.update
security.roles.assign_permissions
security.permissions.view
system.settings.view
system.settings.update
system.diagnostics.view
```

Не получает право удалить или изменить системную роль `system_owner`.

### operator

Минимально получает:

```text
security.users.view
```

Дополнительные предметные разрешения будут добавляться спецификациями соответствующих доменов.

### viewer

В Security v1.0 получает только:

```text
security.users.view
```

Отображение чувствительных полей должно зависеть от серверной политики и будущих отдельных разрешений.

## 8. Правила системного владельца

Роль `system_owner` является единственным источником истины для определения владельца. Отдельный флаг в `users` не создается.

Сервер обязан запрещать:

- удаление роли `system_owner`;
- переименование кода `system_owner`;
- удаление разрешения `system.*.*`;
- блокировку последнего активного владельца;
- архивирование последнего активного владельца;
- снятие роли `system_owner` у последнего активного владельца;
- операцию, после которой в системе не останется активного владельца;
- обход ограничений прямым POST-запросом.

Интерфейс может скрывать недоступные действия, но защита реализуется на сервере.

## 9. Правила административных операций

### 9.1 Создание пользователя

Обязательные поля:

- логин;
- отображаемое имя;
- временный пароль.

Необязательное поле:

- email.

Условия:

- логин нормализуется в `username_canonical`;
- email нормализуется в `email_canonical`;
- проверяется уникальность канонических значений;
- пароль хэшируется через `password_hash`;
- по умолчанию новая учетная запись активна;
- администратор может отметить пароль как временный;
- администратор может потребовать смену пароля при следующем входе.

### 9.2 Редактирование

Разрешено менять:

- `username`;
- `email`;
- `display_name`;
- флаги временной учетной записи и обязательной смены пароля.

Нельзя менять напрямую:

- `password_hash`;
- `created_at`;
- `last_login_at`;
- системные связи без соответствующего разрешения.

### 9.3 Блокировка

Блокировка устанавливает:

```text
is_active = 0
```

Она не удаляет роли, историю входов или учетную запись.

### 9.4 Архивирование

Архивирование устанавливает `deleted_at` и отключает вход.

Восстановление архивированной учетной записи не входит в UI первой версии, но данные сохраняются.

### 9.5 Сброс пароля

Сброс:

- принимает новый временный пароль;
- создает новый безопасный хэш;
- устанавливает `must_change_password = 1`;
- не показывает существующий пароль;
- должен завершаться обновлением `updated_at`.

### 9.6 Назначение ролей

- назначение выполняется транзакционно;
- дубликаты запрещены составным ключом;
- `assigned_at` содержит серверное время;
- `assigned_by` содержит ID действующего администратора;
- для системного назначения допустим `NULL`.

## 10. Авторизация

Проверка доступа выполняется сервером до выполнения операции.

Предлагаемый порядок:

1. пользователь аутентифицирован;
2. учетная запись активна и не архивирована;
3. загружаются роли пользователя;
4. если есть активная роль `system_owner` с `system.*.*`, доступ разрешен;
5. иначе проверяется точное разрешение;
6. при отсутствии разрешения возвращается отказ без изменения данных.

UI не является источником авторизации.

## 12. Требования безопасности

Обязательно:

- все изменяющие операции выполняются только методом POST;
- все POST-операции защищены CSRF;
- SQL выполняется через подготовленные выражения;
- запрещено повторное использование одного именованного PDO-параметра в одном нативном prepared statement;
- входные значения нормализуются и валидируются на сервере;
- ошибки БД не показываются пользователю в production;
- пароль никогда не журналируется и не возвращается в HTML;
- операции с ролями и владельцами выполняются транзакционно;
- проверка последнего владельца выполняется с блокировкой соответствующих строк или эквивалентной защитой от гонки.

## 13. Миграция 002

Имя:

```text
002_security_users_management.sql
```

Миграция должна:

1. добавить `assigned_by` в `user_roles`;
2. добавить `assigned_by` в `role_permissions`;
3. добавить внешние ключи с `ON DELETE SET NULL`;
4. создать или актуализировать роли `administrator`, `operator`, `viewer`;
5. создать каталог разрешений v1.0;
6. гарантировать наличие `system.*.*`;
7. назначить `system.*.*` роли `system_owner`;
8. заполнить начальную матрицу системных ролей;
9. не изменять пароль, логин или данные существующего владельца;
10. не создавать второго владельца;
11. выполняться один раз через существующий механизм таблицы `migrations`.

## 14. Критерии приемки миграции

Миграция считается принятой, если:

- установка на базе с существующим владельцем проходит без потери данных;
- в `migrations` появляется запись `002_security_users_management.sql`;
- все четыре системные роли существуют;
- `system_owner` имеет `system.*.*`;
- каталог разрешений создан без дубликатов;
- внешние ключи `assigned_by` работают;
- повторный запуск установщика не дублирует роли и разрешения;
- вход существующего владельца продолжает работать;
- smoke test продолжает проходить.

## 15. Критерии приемки модуля v1.0

Модуль считается реализованным после подтверждения:

- владелец видит список пользователей;
- поиск и фильтры работают;
- новый пользователь создается;
- дубликат логина или email отклоняется;
- пользователь может войти с выданным паролем;
- заблокированный пользователь не может войти;
- сброс пароля делает старый пароль недействительным;
- роли назначаются и снимаются;
- недопустимые операции над последним владельцем отклоняются сервером;
- пользователь без разрешения не может выполнить административную операцию прямым запросом;
- PHP syntax check проходит;
- локальная инициализация проходит;
- smoke test проходит;
- визуальная проверка desktop и mobile завершена.
